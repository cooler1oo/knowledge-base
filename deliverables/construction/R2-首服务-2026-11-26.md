## 1. 实测输出（原始命令与返回）

### 1.1 R2-1 服务在平板容器内起得来，健康检查返回真实值 ✅

```
$ curl -s http://127.0.0.1:8000/api/health
{"ok":true,"dbOk":true,"meiliOk":true,"workerOk":false,
 "diskFreeGb":163.9,"workerHeartbeatAt":null}
```

`workerOk=false` / `workerHeartbeatAt=null` 是**符合本轮预期的结果**：worker 要到后续轮次才有，
技术方案 §8.2 明写「没有写入方的话这个字段永远 null，健康检查永远通过」，所以
**没有为了让健康检查变绿而写死 `true`**。

### 1.2 R2-2 手机浏览器能打开并登录 ✅（用户本人操作确认）

用户在平板浏览器打开 `http://127.0.0.1:8000`，看到「首次使用 · 创建账号」，自设账号 `却话` 后登录成功。

服务端侧证据（不依赖截图）：

```
$ psql -d kb -tAc "select id, username, created_at from users"
1|却话|2026-11-26 22:51:01.899717+08

$ psql -d kb -tAc "select id, left(token_hash,12)||'...（共 '||length(token_hash)||' 字符）', expires_at > now(), to_char(created_at,'HH24:MI:SS') from sessions"
1|3e6078c32c74...（共 64 字符）|t|22:51:17

$ grep -E "bootstrap|auth/login|GET / " /var/log/kb-api.log
INFO: 127.0.0.1:55980 - "POST /api/auth/bootstrap HTTP/1.1" 201 Created
INFO: 127.0.0.1:55980 - "GET / HTTP/1.1" 303 See Other
INFO: 127.0.0.1:57584 - "POST /api/auth/login HTTP/1.1" 200 OK
INFO: 127.0.0.1:57584 - "GET / HTTP/1.1" 200 OK
```

三条要点：① 库里 `token_hash` 是 **64 字符 SHA-256**，明文令牌只在 Cookie 里；
② 登录后 `GET /` 从 303 变 200，说明中间件真的在校验会话；
③ 会话行 `有效=t`。

### 1.3 全链路边界（在 `kb_test` 库跑，不污染生产库）

```
未登录访问 /            → HTTP 303 → /login
无账号时 /login          → 显示「创建账号」
bootstrap               → 201 {"ok":true,"username":"testuser"}
二次 bootstrap           → HTTP 410
错误密码登录             → HTTP 401
正确登录                 → 200 + Set-Cookie（HttpOnly）
带 Cookie 访问 /         → 200，页面含「你好，testuser」
登出                     → 200
登出后再访问 /           → HTTP 303
```

## 2. 偏离清单（与方案不一致的地方，及理由）

| # | 方案原文 | 实际做法 | 理由 |
|---|---|---|---|
| 1 | 未规定首账号怎么产生 | 登录页在 `users` 为空时**兼作创建账号页**，无需手工调 API | 单人自用，让使用者在手机上自己设密码，比在交付物里留一个默认密码安全 |
| 2 | `Secure` Cookie 属性未定 | 由 `KB_COOKIE_SECURE` 控制，**默认关** | 本机 `http://127.0.0.1` 调试时带 `Secure` 的 Cookie 不会被回传，会表现为「登录成功但立刻掉线」 |
| 3 | 未规定密码长度下限 | 8 位起、72 字节封顶 | bcrypt 只吃前 72 字节，超长必须显式拒绝而不是静默截断 |
| 4 | 未规定部署路径 | 代码在容器 `/opt/kb-app/kb`，由容器内 supervisord 拉起 | 沿用 R0 定型的 runit → proot → supervisord 三层结构，不新造守护方式 |

## 3. 已知坑（都踩过）

- **真实 rootfs 路径是 `$PREFIX/var/lib/proot-distro/containers/debian/rootfs`**，
  不是 `installed-rootfs/debian`（后者是个残留空壳，东西拷进去容器里看不见）。第一次部署就踩了。
- **`sv restart kb-container` 对 proot 无效**：proot 不转发 TERM，`sv status` 会一直显示 `got TERM`。
  必须 `sv force-stop` 再 `sv start`。
- **`supervisorctl status` 在另开的 proot 会话里连不上 socket**（`/var/run` 每会话独立），
  不代表服务有问题，看 `curl /api/health` 为准。
- 容器内 `/var/log/kb-api.log` 在 Termux 侧要看 `$RFS/var/log/kb-api.log`。
- 容器内 `getpass.getuser()` 返回 `root`，PG role 是 `u0_a201`，**必须显式 `KB_PG_USER`**（R1 已踩，R2 沿用）。
