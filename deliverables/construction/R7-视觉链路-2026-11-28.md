## 一、本轮最值得记住的一条

**「能 import」与「能跑」是两件事，本轮的每个决策都是为了让它们分开验证。**

纯逻辑层（选帧、空白判定、文件名）能在毫秒内跑完 104 条断言，因为它不碰
任何视频文件、不装 `cv2`、不装 `scenedetect`。装配层（切镜头、读帧）只能靠
探针脚本在真视频上验。两者混在一起的结果是：改一个选帧阈值要跑 40 秒解码，
最后没人肯改。

具体落到代码上是三条硬约束，都由测试守住：

| 约束 | 守它的测试 | 违反后的真实现象 |
|---|---|---|
| 模块顶层不 import `cv2` / `scenedetect` / `numpy` | `test_顶层不import外部视频库` | 本机没装 scenedetect 时，纯逻辑单测在**收集阶段**就失败 |
| 但 `cut.py` / `grab.py` 方法体内**必须**有这些 import | `test_切镜头与抽帧确实在方法体内import` | 少了这条，把 `detect` 写成空实现也能让上一条通过 |
| `kb/vision/` 不 import `kb.store` | `test_没有文件import_store层` | 视觉层直接写库，store 这层边界形同虚设 |

上表第二行是这份记录里最值得抄走的一条：**只断言「没有坏东西」的测试，
在「压根没有代码」时也是绿的**。反向断言必须成对写。

## 二、实测数据

### 2.1 合成视频（本机 Windows，`opencv-python-headless 5.1.0`、`scenedetect 0.6.6`）

用 `cv2.VideoWriter` 造视频后跑 `scripts/probe_frames_vision.py`，三组输入覆盖三种
完全不同的结论：

| 输入 | 镜头数 | 帧数 | 跳过 | 耗时 | 结论 |
|---|---|---|---|---|---|
| 三镜头 6 秒（640x360，25 fps，每镜头 2 秒，含文字与噪点） | 3 | 3 | 0 | 0.86 s | 切点 `(0,2) (2,4) (4,6)` 精确；帧位 `1.00 / 3.00 / 5.00` 秒；36.5 KB/帧 |
| 静态 3 秒（320x240，画面只变计数文字） | **1** | 1 | 0 | 0.68 s | **`start_in_scene=True` 生效的证据**：0 个切点仍得到 1 个镜头，帧在 1.50 秒 |
| 全黑 2 秒（320x240，无任何内容） | 1 | **0** | 1（`blank`） | 0.70 s | 零帧 + 明确提示，**不抛异常** |
| 非视频文件（`hello world` 重复 1000 次） | — | — | — | — | 退出码 **3**，报 `cv2 打不开（缺编解码或不是视频）` |

三镜头那组连帧文件都落了盘，目录名是中文（`帧输出`），三张 JPEG 都在——
这正是 `imencode` + 自己写文件要证明的事（`cv2.imwrite` 在这个路径下会静默返回
`False`）。

全黑那组是关键对照：**同一个「0 个切点」的输入，静态视频得到 1 帧、全黑得到 0 帧。**
前者是「有画面但没变化」，后者是「画面没信息」。如果缺少 `start_in_scene=True`，
两者的镜头数都会是 0，这两个结论就分不开了。

### 2.2 平板真机

**未跑。** 平板本轮未连接（`tailscale status` 未确认在线），且按 `HANDOFF-2026-11-27.md`
的记载，上一轮结束时平板上装的是 `scenedetect 0.7.3`，本轮代码按 **0.6.6** 的接口写
（`get_seconds()`、`min_scene_len` 整数帧数）。**平板必须先降到 0.6.6 再跑探针**，
否则会直接崩在 `.get_seconds()` 上——0.7.x 虽然也有这个方法，但会发
`DeprecationWarning`，且 `min_scene_len` 的语义从「帧数」变成「秒」，
`int(round(fps * 0.5))` 得到 13 会被当成 13 秒，切点全错。

复跑命令：

```bash
# 1) 平板降到 0.6.6（不让它拉 GUI 版 opencv）
proot-distro login debian -- /opt/kb-venv/bin/pip install --force-reinstall \
    "scenedetect==0.6.6" --no-deps

# 2) 立刻确认 cv2 仍正常 —— 0.7 装过的话 GUI 版可能已经把 cv2/ 目录覆盖过
proot-distro login debian -- /opt/kb-venv/bin/python -c \
    "import cv2; print(cv2.__version__); print('GUI' in cv2.getBuildInformation())"

# 3) 跑探针（真视频路径按实际改）
proot-distro login debian -- /opt/kb-venv/bin/python \
    /opt/kb-app/scripts/probe_frames_vision.py --video /opt/kb-samples/v.mp4 \
    --out /opt/kb-app/.tmp/frames --max-frames 12
```

第 2 步的 `getBuildInformation()` 检查不是多余：0.7.x 会把 `opencv-python`（GUI 版）
作为无条件依赖装进来，而 GUI 版与 headless 版**共用 `cv2/` 目录**，装过之后再
`pip uninstall opencv-python` 会把 `cv2/` 的文件一起删掉——`pip list` 显示 headless
还在，`import cv2` 却 `ModuleNotFoundError`。这一条在 `P2-视觉链路-交接-2026-11-27.md`
§3.1 有完整的复现链。

## 三、实现偏离设计文档的清单（4 处，都已验证）

### 3.1 `merge_shots` 多了「⑤b 拉齐首尾」这一步

**设计文档 §4.3.2 只写了六步。** 第 ③④⑤ 步按设计实现后，测试
`test_覆盖必须从0到scan_sec` 暴露一个问题：检测器不保证首帧恰好是 `0.0`、
末帧恰好等于 `scan_sec`（帧对齐会让末段结尾少半帧）。

差这一点的后果不是「少一帧画面」，而是**最后一层找不到与之重叠的镜头，直接无帧**
——而 `plan_picks` 的兜底分支恰好把这种情况静默吞掉了（它在层内无镜头时取层中点）。
也就是说：**不补这一步，bug 不会报错，只会少抽几帧。**

所以补了一步：`merged[0][0] = 0.0`、`merged[-1][1] = max(merged[-1][1], scan_sec)`。
时间轴连续覆盖是分层抽样的前提，设计文档 §4.3.2 自己也是这么说的（「并进前一段
而不是删掉」的理由就是「时间轴始终连续覆盖」），只是没把「首尾对齐」显式列成一步。

### 3.2 `_retry_pick` 加了「判重」，不是无条件重试

**设计文档 §4.6 写的是**「`plan_picks` 之后如果一帧都没抽到，在 `shots[0]` 的中点
再试一次」。单镜头视频里，`shots[0]` 的中点**就是** `plan_picks` 给出的唯一帧位，
无条件重试等于把同一个失败再演一遍，而且会往 `skipped` 里塞一条重复记录。

实现里加了判重：`abs(retry.at_sec - p.at_sec) > 1e-6` 时才重试。**不做没有信息
增量的重试。**

### 3.3 新增 `SkippedFrame.reason = "write_failed"`

**设计文档 §4.1 只列了 `"blank"` / `"read_failed"` 两类。** 但写盘会因磁盘满或
权限失败，那是真事，混进 `read_failed` 里会让排查方向错掉——编码失败是库的问题，
写盘失败是磁盘或权限的问题。测试 `test_写盘失败记write_failed而不是read_failed`
钉住这条。

### 3.4 新增 `kb/vision/grab.py` 里的 `FrameReadFailed` 异常

设计文档没有定义这个异常类（`models.py` 只列了 `VideoUnreadable`）。但 `read_at`
需要一个「这一帧没有」的信号来让 `frames.py` 记 `SkippedFrame`，而它**不能**用
`VideoUnreadable`——那会触发上抛、整条视频失败，正好违反设计文档 §4.6 的三层口径
（「单帧读失败或空白 → 记 SkippedFrame 继续下一帧」）。

放在 `grab.py` 而不是 `models.py`：它是抽帧这一个装配环节的错误，不是跨文件共享的
值对象。`models.py` 只放会被三个以上文件用到的类型。

## 四、依赖变更与代价

```toml
"scenedetect>=0.6.6,<0.7",
"opencv-python-headless>=4.8",
```

`numpy` 不写第三遍：`opencv-python-headless` 与 `scenedetect` 都依赖它。而且
`kb/vision` 的代码**不 import numpy**（`FrameImage.data` 声明为 `Any`），所以本层
不因 numpy 缺失而挂。

`<0.7` 放弃了三样东西，都不影响本轮能力：

| 放弃的 | 0.6.6 的替代 |
|---|---|
| `ContentDetector(min_scene_len=0.6)` 直接收 float 秒 | 自己乘 fps 取整：`max(1, int(round(fps * min_shot_sec)))` |
| `FrameTimecode.seconds` 属性 | `get_seconds()`（0.6.6 只有这个） |
| 0.7 的 `Backend` 名称探测 | 本轮不用多后端 |

**不做 `.seconds` / `.get_seconds()` 的双版本兼容函数。** 交接文档
`P2-视觉链路-交接-2026-11-27.md` §4.1b 建议写
`float(getattr(tc, "seconds", None) or tc.get_seconds())`，本轮**不采纳**：
项目只锁 0.6.6，写兼容层等于让「版本锁」这件事没有约束力；真升 0.7 时那是一个
独立的升级轮次，该整体改一遍并重跑探针，而不是留一段永远走不到的分支。

## 六、已知缺口（诚实标注，别当已完成）

| 缺口 | 为什么没做 | 怎么补 |
|---|---|---|
| **平板真机未跑** | 平板未连接；且上一轮装的是 0.7.3，需先降到 0.6.6 | 见 §2.2 的三条命令 |
| **不下载视频** | 项目当前只存链接（`kb/store/items.py` 明写「只抓元数据不下载」） | 下载轮次（R8 之后）交付后，本层输入就有了 |
| **不接 worker** | 拿不到视频文件，接进 worker 只是空转，`jobs` 会被标处理失败 | 同上。`extract_frames` 的 `FrameSet` 可直接喂给 visual 步骤 |
| **不调视觉模型** | 视觉通道属 `kb/ai/`，要真实 API 配置 | 配好通道后把 `FrameSet.paths()` 送进去 |
| **视觉模型读画面文字准确率未验** | 没有视觉通道就没有可对照的读数 | 同上 |
| **`max_frames=12` 没有实测成本依据** | 视觉模型单帧单价本轮算不出来 | 配好通道后按真实单价复核；单帧贵就往下调，便宜可到 20 帧 |
| **真视频（抖音）未验** | 交接文档记录的旧抖音链接已失效，本轮没拿到新链接 | 拿到新链接后跑 `probe_frames_vision.py` |

`max_frames=12` 这一条值得单独强调：它是**按成本留余量估的**（方案 §4.11 那 8 帧
成功读到 4 个章节标题，12 是往上留一半），不是实测出来的最优值。设计文档 §9.1
把它列成「需要人拍板的一项」，本轮保持现状。
