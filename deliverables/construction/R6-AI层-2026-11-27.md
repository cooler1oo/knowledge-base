## 一、本轮最值得记住的一条

**「本机测试全绿」与「真库上正确」是两件事，本轮为此吃了 6 次亏。**

每一次的形态都不同，但共同点是：假连接/局部测试验的是「SQL 文本长什么样」，
真库验的是「SQL 执行后数据对不对」。前者不能替代后者。

| # | 问题 | 为什么本机发现不了 | 现在由什么守 |
|---|---|---|---|
| 1 | `_ADD_SQL` 触发 42P08（参数类型无法推断） | 假连接只记 SQL 字符串，不做 PG 解析 | 静态断言「每个占位符都带 `::type`」 |
| 2 | `jobs.error` 缺响应原文 | 测试自己把 snippet 拼进了 `message`，替实现补了缺的那半 | 真库 `B2` + 逐类参数化用例 |
| 3 | `items.py` 入队缺 `on conflict` | 唯一约束只在执行时生效 | 静态断言 + 真库重复入库用例 |
| 4 | `tags.py` DELETE 漏 `origin='ai'` | 假连接的 DELETE 不真的删数据 | 静态断言（`ast` 剥注释后） |
| 5 | `D10_2` 时间戳断言假绿 | 同事务内 `now()` 冻结，「重写」与「冻结」结果相同 | 跨事务 + 变异测试 |
| 6 | `D10_3` `updated_at` 断言假绿 | 触发器无条件维护该字段，断言的对象与代码无关 | 删掉该断言，改由触发器用例负责 |

**建议立成的规则**（比「必须真库跑过」更进一步）：

> 凡是「断言某个值没有变化」或「断言某个值被更新」的用例，
> 必须做一次变异验证（把实现改成错误写法，确认用例变红，再改回）。
>
> 真库能发现「假连接不模拟执行」，但发现不了「断言了数据库自动维护的字段」。
> 后一类只有在变异测试下才会暴露。

## 二、H1–H8：本轮发现的问题与最终判定

每条格式：**现象 / 影响面 / 判定 / 对应验收**。

### H1 `_ADD_SQL` 触发 42P08 参数类型无法推断

- **现象**：平板真库执行 `usage.add` 报 `42P08 could not determine data type of parameter $2`。11 条 `usage` 相关用例全红。
- **根因**：`:d_calls` / `:d_prompt` / `:d_completion` 首次出现在 `jsonb_build_object(...)` 里。该函数签名是 `VARIADIC "any"`，PG 在 `parse_param.c` 的 `check_parameter_resolution_walker` 阶段无法从 `any` 推断类型。`round(:d_cny, 4)` 同理（两个重载选不出）。
- **影响面**：`usage.add` 完全不可用 → 记账失效 → 预算闸门读到 0 → **预算永不生效**。这是功能级故障，不是显示问题。
- **判定**：**已修**。每个占位符的**每一次**出现都带显式转型（`::int` / `::numeric` / `::text`）。
- **对应验收**：`D1` / `D8`–`D12` / `AI-05` / `AI-06`
- **守门**：`test_add的每个占位符都带显式转型_防42P08`（本机，正则逐次检查）

### H2 `jobs.error` 里没有响应原文

- **现象**：真库上解析失败的任务，`jobs.error` 只有 `"AI解析失败：响应不是合法 JSON"`，没有模型的原始响应。`B2` 红。
- **根因**：`AiClient` 把响应原文放在 `SummarizeFailed.snippet` 字段，而 `steps.py` 落库时只写 `message`。拼接责任没有落点。
- **影响面**：排障时只知道「解析失败」，不知道是半截 JSON、HTML 网关页还是别的。**不污染数据**（`summary` 不会被写入），但排障成本显著上升。
- **判定**：**已修**。新增 `ai_runtime.failure_message(failed)`，在唯一写 `jobs.error` 的出口统一拼 `<摘要>；响应前 200 字：<原文>`，四条落地分支（AUTH / CONNECT / 429 / 其余）全部走它。
- **对应验收**：`B1` / `B2` / `B28`、`§8.2`
- **守门**：8 类 × 4 分支的参数化用例 `test_每一类失败写库时都带上响应原文_8点2节`

### H3 `items.py` 的入队 SQL 缺 `on conflict`

- **现象**：同一条目重复入库（用户重复分享同一个链接）时抛 `23505 duplicate key violates unique constraint "jobs_pending_uniq"`，整个 `create_item` 失败。
- **根因**：`_CREATE_SQL` 的 CTE 第二段 `insert into jobs` 是裸插。`kb/store/jobs.py` 的 `enqueue` 写对了（带 `on conflict ... where state in (...)`），但 `items.py` 是**另一条独立的入队路径**（为了入库+入队原子性写成一条 CTE）。
- **影响面**：**用户看到「保存失败」而不是「已存在」**。这是唯一一处会直接影响用户操作的缺陷。
- **判定**：**已修**。补 `on conflict (item_id, step) where state in ('pending','running') do nothing`。
- **对应验收**：`B20`、`AI-07`
- **守门**：
  - 静态：`test_入队SQL带on_conflict_B20`、`test_入队on_conflict必须带state谓词_B20`
  - 真库：`test_重复入库同一条目不抛唯一约束冲突_B20`、`test_首次入库的第二步骤也能入队_B20`

### H4 `tags.py` 的 DELETE 漏 `origin='ai'`

- **现象**：`replace_ai_tags` 会删掉该条目的**所有**标签，包括用户自己加的（`origin='user'`）。
- **根因**：SQL 写成 `delete from item_tags where item_id = :i`，漏了 `and origin = 'ai'`。**docstring 里明确写了要求，代码没做到**。
- **影响面**：**用户手动打的标签在 AI 重跑时被静默删除**。数据丢失，且无任何提示。
- **判定**：**已修**。补 `and origin = 'ai'`。
- **发现过程**：由 `test_tags_store只删origin为ai的行_B19`（静态断言）抓到。值得注意的是：真库用例 `test_真库_replace_ai_tags只删origin_ai保留origin_user_B19` 当时是绿的——因为跑的是改前的代码，不是测试无效。
- **对应验收**：`B19`、`F4`
- **守门**：静态 `test_tags_store源码里没有insert_into_tags_F4`、`test_tags_store只删origin为ai的行_B19` + 真库 B19 用例

### H5 `D10_2` 的「时间戳不变」断言假绿

- **现象**：把实现的冻结分支改成每次写 `now()`（正是 `D10②` 要防的 bug），这条用例**仍然 passed**。
- **根因**：用例复用 `pg_conn` fixture（含 `begin`），整条用例在一个事务里。Postgres 的 `now()` 是 `transaction_timestamp()`，**同事务内恒定不变**。加 `pg_sleep` 也救不了——它取的是事务**开始**时刻。
- **影响面**：测试永久假绿，无人发现。**这是本轮最隐蔽的缺陷**——它不产生错误行为，只让一个守卫失效。
- **判定**：**已修**。改用独立连接（不复用 fixture），每次 `add` 各自提交 = 生产形态，`finally` 清理 key。
- **对应验收**：`D10` ②
- **守门**：`test_连写10次后budgetWarnedAt逐字不变_D10_2` + `test_D10_2的判据在跨事务下真的会变_变异测试前置`（后者守「测试手段」本身有效）
- **红绿验证**：变异后 `FAILED`（时间戳 `21:15:51` → `21:17:30`），恢复后 `7 passed`

### H6 `D10_3` 的 `updated_at` 断言无法测到任何东西

- **现象**：把 `usage.py` 里 `updated_at = now()` 整行删掉，跨事务重写后的用例**仍然 passed**。
- **根因**：`settings` 表有 `before update` 触发器 `settings_touch`（`0002_functions.sql:42-44`）无条件写 `updated_at`。所以**任何**「断言 updated_at 被更新」的用例，测到的都只是触发器在工作，与业务 SQL 无关。
- **影响面**：与本轮 H5 同类，但**根因更根本**：不是「测试环境限制」，而是「断言的对象本身被数据库自动维护」。跨事务也救不了。
- **判定**：**已删掉该断言**（不是「不修」，是「做不到」）。`updated_at` 的正确性由触发器保证，已由 `test_store_pg.py::test_updated_at_trigger_overwrites_stale_value` 覆盖。用例重命名为 `test_连写10次后spentCny严格递增_D10_3`，只验 `spentCny`，并加精确值 `1.09` 校验。
- **对应验收**：`D10` ③ 的 `spentCny` 部分
- **红绿验证**：把累加改成覆盖后 `FAILED`（`1.0 != 0.01`），恢复后 `7 passed`
- **遗留**：`D10b`（「`updated_at` 有变」）现在无用例在 `usage` 层守。**建议把它归到触发器用例**，而不是在业务层守——否则只能写「检查代码里有这行字」的静态断言，那守的不是行为。

### H7 截断点落在多字节字符中间产生 U+FFFD

- **现象**：响应超过 256KB 被截断时，如果截断点落在汉字/emoji 中间，`body` 末尾出现 `U+FFFD`（替换字符）。`test_截断处不产生替换字符_B29` 红。
- **根因**：`max_response_bytes = 262144` 不是 UTF-8 字符宽度的整数倍。中文块（999 字节）场景下 `allowed = 406`，`406 % 3 = 1`，必然切在字符中间。原实现按字节硬切 + `errors="replace"`。
- **影响面**：**不污染数据**（`truncated=True` 时 `client.py` 直接判 `TOO_LARGE` 失败，不解析、不写 `items.summary`）。只影响 `jobs.error` 里拼进去的响应原文，末尾缺一个字。**低严重度但该修**：修成本低，不修会误导排障。
- **判定**：**已修**。新增 `_decode(raw, *, truncated)`：
  - 先试整体解码（快路径）→ 截断点正好在字符边界时一个字节都不丢
  - 失败且 `truncated=True` → 回退 1–4 字节找合法边界
  - 失败且 `truncated=False` → 保留 `errors="replace"`，让上游故障可见
- **对应验收**：`B29`
- **守门**：
  - `test_截断处不产生替换字符_B29`（team-lead 补）
  - `test_块长不整除上限时保留最后一块的余量_B29`（team-lead 补，覆盖原来 `allowed` 恒为 0 的死代码）
  - `test_非截断响应遇非法UTF8仍产生替换字符_B29`（本轮补，反向守门）
  - `test_截断点正好在字符边界时不丢字节_B29`（本轮补，修 `_decode` 时踩到的回归）
- **红绿验证**：把快路径改回 `errors="replace"` → `FAILED`；恢复 → `22 passed`

### H8 词表去重测试假绿 + 去重口径与 docstring 不符

**H8-a 假绿**：
- **现象**：把 `render_vocabulary` 的去重两行删掉，`test_词表最多发200个且按id升序去重` **仍然 passed**。
- **根因**：用例造 251 条，重复项排在 id 248–250，`VOCAB_LIMIT=200` 先截断了。三条断言全靠截断蒙对。
- **判定**：**已修**。原用例收窄为 `test_词表最多发200个且按id升序_2点4节`（只验上限与顺序，用互不相同的词表），删掉「去重」二字。

**H8-b 去重是精确匹配，docstring 说「归一化」**：
- **现象**：输入 `(1, "AI相关")` 与 `(2, "  ai相关 ")`，去重不生效，两条都在。
- **判定**：**只改 docstring，不改实现**。理由：生产**不可达**。
  - 同一父（含都是顶级）下仅差空白/大小写 → `tags_sibling_name_uniq`（`(coalesce(parent_id,0), lower(btrim(name)))`）**拦住**
  - 不同父的同名子 → 渲染结果 `父A › x` ≠ `父B › x`，**本来就不重复**
  - 所以去重在生产上挡不到东西，它是防御性代码（防将来 `vocabulary()` 改成 join 出多行的形状）
- **不为不可达场景加代码**：改成归一化比较会让「词表里有 `AI相关` 与 `ai相关` 时只发一个」变成隐式行为，而它其实已被数据库约束保证。多一层归一化只会让行为更难推理。
- **守门**：`test_去重是防御性的_生产不可达_2点4节`（确认不是死代码）、`test_去重是精确匹配不是归一化匹配_记录现状_2点4节`（记录本口径，防止有人「顺手修」）

## 六、设计偏离记录

| # | 偏离 | 理由 |
|---|---|---|
| 1 | `kb/ai/__init__.py` 用 PEP 562 惰性导出，不是模块级 import | 模块级 import 会让 `from kb.ai import outcomes` 连带拉 `httpx`，缺包时 `python -m kb.worker` 在导入阶段就抛裸 traceback，`ensure_ai_available()` 的友好提示永远执行不到，`B27` 失败 |
| 2 | `kb/worker/{steps,ai_runtime}.py` 用 `Conn = Any` 别名，不 import `pg8000` | `eng_checks --arch` 的 `[[driver_deny]]` 扫字面量、不区分 `TYPE_CHECKING`。这两层从不对 `conn` 调 `run()`，只是转手传给 store |
| 3 | `load_config` 拆成 `load_values` + `build_config` | `E1` 要求错误消息含缺失键名，而 `load_config` 返回 `None` 时拿不到「缺哪个」 |
| 4 | `budget_cny` 为 `0` 返回 `0.0` 而不是默认 20 | `D16` 直译：`0` 是「一分钱都不想花」的明确表达，不能被「0 是假值」的默认值逻辑吃掉 |
| 5 | `loop._now()` → `loop._db_now(conn)` 从数据库取时间 | 平板实测：容器 Python 时区 UTC、PG 时区 PRC，相差 8 小时。每月 1 日 00:00–08:00（PRC）窗口里闸门读的月份键与记账写的不一致 → **预算每月失效 8 小时** |

4. **不要在 `usage` 层断言 `updated_at`**。触发器已经保证它，断言它只会得到假绿（见 H6）。
