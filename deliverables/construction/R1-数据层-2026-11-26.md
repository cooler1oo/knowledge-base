## 二、与设计的偏离清单

### 2.1 修掉技术方案 §6.2 的一处 DDL 错误（已升版 v9.7）

| 项 | 内容 |
|---|---|
| 位置 | `attachments_mime_allowed` 的 CHECK 表达式 |
| 现象 | `MigrationError: 0001_schema.sql 执行失败，已回滚：{'C': '42804', 'M': 'argument of CHECK must be type boolean, not type text'}` |
| 根因 | `~` 的优先级高于 `||`。`mime ~ '^(image/.../text/' || '|application/...'` 被解析成 `(mime ~ '...') || '...'`，左边 boolean、右边 text，拼接后返回 text，CHECK 拿到非布尔值 |
| 修复 | 正则拼接加括号：`mime ~ ('^(image/.../text/' || '|application/...)` |
| 回写 | 技术方案 §6.2 已改并注明原因；§12.1 补了「抽样跑通不等于全部跑通」的教训；§15 记 v9.7 |
| 性质 | 不是抄错，是方案原文的错。R0 的「DDL 逐条跑通」实际未覆盖 `attachments` 这张表 |

### 2.2 本轮新增的实现决策（技术方案未写，属实现细节，不需改方案）

| 决策 | 做法 | 理由 |
|---|---|---|
| 多语句执行 | pg8000 `run()` 直接发整段 SQL | 实测走简单查询协议，多语句与 `$$` 函数体均正常，`BEGIN/ROLLBACK` 能回滚 DDL。**不需要自写 SQL 分割器** |
| 事务边界 | 一个迁移文件一个事务，版本号同事务写入 | 失败整份回滚，不出现「表建一半、版本号已写」 |
| 并发保护 | `pg_advisory_lock(728190001)` | api 与 worker 可能同时启动并各自尝试迁移 |
| 版本表 | 迁移器 bootstrap 建一次，0001 里 `IF NOT EXISTS` 再建一次 | 迁移器必须先有版本表；两处幂等不冲突 |
| 表清单 | `TABLES` 常量放 `migrate.py`，测试与 `--check` 共用 | 一处定义，避免测试与实现各写一份 |
| 连接池 | 自写 30 行 `queue.LifoQueue`，坏连接在异常路径丢弃重建 | 单用户，池只负责复用；不做借出探活，省一次往返 |

# 补记（2026-11-26 22:30）：首次全跳过事故复盘 + 四项修复

> 这一节是 R1 收尾后追加的。上一版交接包把「16 个用例全部 skip」写成「根因未确证」，
> 属于**未查到底就交付**。本节把它查到证据尽头，并把查出的四个真问题一并修掉。

## 补-1 事故本身：连接从未到达数据库

**现象**：同一条命令、相隔 6 秒，结果不同。

| 时刻 | 命令差异 | 结果 | 耗时 |
|---|---|---|---|
| 21:54:09 | 修复 DDL 前 | 16 errors（42804） | 1.40s |
| 21:54:48 | 与下一行完全相同 | **16 skipped** | **0.07s** |
| 21:54:54 | 多一个 `-rs` | 16 passed | 2.19s |

**证据一：数据库没重启、没宕机。**
```
postmaster_start=11-26 21:41:07  已运行=1861s
```
21:54:48 时 PG 已连续运行约 13 分钟，端口在听、前 6 秒后 6 秒都正常应答。

**证据二：那 2 秒内 PG 一条日志都没有。**
PG 输出由 svlogd 落在 `$PREFIX/var/log/sv/postgres/current`（**注意**：不是 `$HOME/pgdata/log`，
上一版交接包说「日志被丢弃」是找错目录，日志一直在写）。时间窗 13:53–13:56（UTC 前缀，比 CST 慢 8 小时）
内只有三条事：
```
21:54:09 [16254] ERROR: argument of CHECK must be type boolean, not type text   ← 第一次运行
21:55:00 [12277] LOG: checkpoint starting
21:55:01 [16502] ERROR: insert or update on table "items" violates foreign ...   ← 第三次运行
```
**21:54:48 前后无任何连接记录** —— 16 次连接尝试没有一次到达 PG 的监听套接字。

**证据三：耗时否掉了「对方拒绝」这个解释。**
本机连一个没人听的端口实测 **2003ms**（Windows 会重试）；连平板成功的连接约 **137ms**（2.19s ÷ 16，
约等于 Tailscale RTT）。事故那次整个会话只花 **70ms**，比单程 RTT 还短，**SYN 根本没发出去**。

**判定**：故障发生在 **Windows 本机出口**，属「无路由 / 网卡不可用」级别的立即失败，
不是数据库问题、不是平板问题、不是测试代码问题、不是环境变量问题。
最可能是 Tailscale 虚拟网卡或路由在那一瞬不可用（约 6 秒后自行恢复）。
**触发点在现有证据下不可判定**：Windows 侧 Tailscale 无 CLI 日志，平板侧 `logcat` 无 tailscaled 记录、
Termux 里也没有 `tailscale` 命令 —— 两边都留不下痕。

**为什么这件事值得写进交接包**：不是因为它多严重，而是因为它暴露了「真实故障可以被伪装成全绿」——
`pytest -q` 当时退出码 0，界面显示 16 个 s，没有任何一处提示这是异常。

## 补-2 修掉的四个真问题

### ① 测试框架把故障伪装成跳过（最要紧）

原实现 `pg_test_config_or_skip()` 捕获**所有**异常并 `pytest.skip`，且 `-q` 下不打印原因。
后果：库连不上 = 退出码 0 = 看起来全绿。

改为按「有没有显式配置」分三态：

| 情形 | 行为 |
|---|---|
| 设了 `KB_PG_*` 任一项但连不上 | **失败**（`pytest.fail`，退出码非 0），消息含「视为承诺连库」 |
| 什么都没设（本机无库） | 跳过，并在 `-ra` 下显示原因 |
| 连得上 | 正常跑 |

配套：
- `pyproject.toml` 加 `addopts = "-ra"`，跳过与失败原因始终可见；
- `kb/store/db.py` 的连接失败改为 `PgUnreachable`，**带 errno 与耗时**，并翻译成人话：
  `errno=10061，连接被拒：对方端口没有服务在监听（Windows）`。下次同类事故一眼可分
  「端口没开」／「无路由」／「被丢包」——这三种在旧实现里都只是同一句「连不上」。

验证（三条边界都实测）：
```

  Failed: 已显式设置 KB_PG_HOST，视为承诺连库；Postgres 不可达（127.0.0.1:5432，
  用户 TB）：…（耗时 2013ms，errno=10061，连接被拒：对方端口没有服务在监听（Windows））
不设 KB_PG_*                                            → 16 skipped，原因可见（-ra 生效）
KB_PG_HOST=100.124.156.47                               → 16 passed
```

### ② `postgresql.conf` 里同名参数定义两次

`max_connections` 在第 65 行是 `100`，文件末尾又被追加成 `20`；`shared_buffers` 同样重复。
PG 遇到重复定义只在**启动日志**打一句 `parameter "max_connections" specified more than once`，
然后按最后一个值生效——而那句日志当时根本没人看。

清理为**每个参数只有一处生效定义**：`max_connections = 40`（原 20 的上限，单用户峰值约 15，
留一倍余量）、`shared_buffers = 128MB` 显式写出（128MB 本就是编译默认值，不该靠记忆）。
验证：`max_connections=40  shared_buffers=128MB`，且新日志中 `specified more than once` 计数为 **0**。

### ③ 启动脚本的幂等判断失效 → 多个 runsvdir 抢锁

boot 脚本用 `pgrep -x runsvdir` 判断「是否已在运行」。但脚本自己是用**绝对路径**
`"$PREFIX/bin/runsvdir"` 启动的，`pgrep -x` 做整串精确匹配，匹配不到 → 判断永远为「没在运行」。
实测：
```
pgrep -x runsvdir : []            ← 明明有 2 个在跑
pgrep -f runsvdir : [12256 12580]
```
后果就是 `runsvdir.log` 里累计 **2076 条** `runsv <服务>: fatal: unable to lock supervise/lock`。
改为 `pgrep -f "$PREFIX/bin/runsvdir"` 并实测命中；清掉孤儿进程后：**1 个 runsvdir + 4 个 runsv**，
6 秒内日志零增长。

### ④ PG 日志落盘位置不显眼 + 成功连接不留痕

`logging_collector=off`、`log_connections=off`，日志只在 svlogd 目录下，且成功连接无记录——
本次事故因此无从取证。现在两者都打开：

```
logging_collector = on          日志落在 $HOME/pgdata/log/postgresql-YYYY-MM-DD.log
log_directory = 'log'
log_connections = on            连上就记，含对端地址与端口
log_disconnections = on
log_min_duration_statement = 1000   慢查询 >1s 也记，R2 调接口用得上
```
验证（真实连接）：
