## 2. 偏离清单

### 2.1 修掉技术方案的一处内部矛盾（已升版 v9.9）

| 项 | 内容 |
|---|---|
| 位置 | 技术方案 §8.2 `POST /api/items` 的响应示例 vs §6.2 的 `items.status` CHECK |
| 现象 | 示例写 `{"status": "pending"}`，而 `items.status` 的 CHECK 只有 `unread/reading/read/archived`。照验收口径去 psql 查 `items`，永远查不到 `pending` |
| 根因 | `status` 一词同时指「处理进度」与「阅读进度」，方案没写清接口返回的是哪一个 |
| 处置 | §8.2 明确：接口 `status` 是**处理**状态（由 jobs 聚合），新增 `readStatus` 表示**阅读**状态；`items.status` 的 CHECK **不加** `pending` |
| 为什么这么定 | 一条内容可以「抓完了但没读」，也可以「读过了还没抓完」。挤进同一列，后写的那一个必然覆盖前一个（用户 2026-11-27 亲自选定此方案） |
| 回写 | 技术方案 §8.2 已改并写明理由；§15 记 v9.9；施工计划 §11 新增本轮明细 |

### 2.2 本轮新增的实现决策（方案未写，属实现细节）

| 决策 | 做法 | 理由 |
|---|---|---|
| 入库 + 入队 | **一条 CTE**（`insert ... on conflict do nothing` + `insert into jobs`） | 单条语句天然原子，不需要手工 `begin/commit`，不会出现「条目进了、job 没进」。已在真库 PG 18.7 实测 |
| 重复提交 | 不重新入队 | 幂等只承诺「不产生第二条」；抓取失败后重试是后续轮次的显式动作，不在本端点暗中再插一个 job |
| 翻页 | id 游标 `before`，不用 offset | 新条目从顶部插入，offset 翻页会漏条与重条 |
| `limit` 越界 | 夹到 1–100，不报错 | 前端传 200 不该变成一次失败 |
| 判空写进 SQL？ | 不写，按有无 `before` 拼两段 SQL | `:before is null` 会让 pg8000 在参数类型推断上卡住（unknown 类型的 `$n` 参与 `is null` 时 PG 无法定类型） |
| `jobs.enqueue` 的冲突谓词 | 必须带 `where state in ('pending','running')` | 唯一索引 `jobs_pending_uniq` 是部分索引，不写谓词 PG 找不到仲裁索引 |

清单里的 10 个文件全部建出/改动，无越界。实际新增 2 个清单内文件之外的东西：无。

### 3.1 定稿后发现的严重 bug：服务只绑回环，外部根本进不来（已修，`8f84abf`）

**现象**：用户报「网址半天进不去」。从 Windows 经 Tailscale 访问 `100.124.156.47:8000`
得到 HTTP 502（代理返回）或直连 HTTP 000。

**根因**（`kb/api/__main__.py`）：

```python
def main(argv: list[str] | None = None) -> int:
    parser_args = list(argv or [])  # argv 为 None → []
    app, host, port = build(parser_args)  # argparse 看不到任何参数，全用默认值
```

`python -m kb.api --host 0.0.0.0 --port 8000` 启动时 `argv` 是 `None`，这行把它变成
`[]`，argparse 于是用默认的 `127.0.0.1`。**supervisor 配置里的参数从 R2 起就一直被丢弃。**

**证据**（uvicorn 自己打印的启动行）：

```
改前  INFO:  Uvicorn running on http://127.0.0.1:8000 (Press CTRL+C to quit)
改后  INFO:  Uvicorn running on http://0.0.0.0:8000   (Press CTRL+C to quit)
```

**为什么两轮没发现**：R2 的验收动作是「在平板浏览器打开 `127.0.0.1:8000`」——回环地址
永远能通，所以这个 bug 在回环下不可见。R2 交接包写的「局域网/Tailscale 内可用」
是**未经验证的推断**，不是实测。已在 R2 交接包里更正。

**判据**：修后从 Windows 直连 `health` → 200、首页 → 303（未登录跳转）；
回归用例 `tests/test_api_main.py` 先红（`assert '127.0.0.1' == '0.0.0.0'`）后绿。

**教训**：验收动作走的是回环地址，就等于没验「别人能不能进来」。凡是「从另一台设备访问」
的判据，必须真的从另一台设备发起。

❌ **本轮失败过的尝试**
- **子代理两次失败于基础设施**：第一次 `502 connect EACCES`（代理 127.0.0.1:12450），第二次 `429 频率限制`。两次都没落盘任何文件，最终由主理人自己实现。不是代码问题，但必须记录——它意味着「派了活」不等于「有产出」。
- **服务只绑回环地址，外部完全进不来**（`8f84abf` 已修）：`kb/api/__main__.py` 把 `argv=None` 转成 `[]`，argparse 用默认 `127.0.0.1`，supervisor 的 `--host 0.0.0.0` 从 R2 起就没生效过。详见 §3.1。这条是本轮最严重的发现——用户「网址进不去」的直接原因。
- 首次真库测试 `errno=13` 全红（客户端出口瞬时故障），重跑即通过
- `sv force-stop` 因缺 `SVDIR` 失败，但健康检查仍返回旧进程结果，差点误判为「重启成功」
- 用 `openssl rand` 造验收会话失败（Termux 无 openssl），插进一行空 hash 脏数据，已清理
- `scp -r /tmp/kbfix2/api` 传到 `~/api` 而非 `~/kbfix2/api`，导致 `cp` 找不到文件、新代码没部署上却以为部署了（日志里还是旧进程的绑定行）。**教训：部署后必须比哈希，不能看「cp 没报错」。**
