## 一、本轮最值得记住的一条

**本机 1021 passed 全绿，真库跑出 3 条红，其中 1 条是真 bug。**

这条不是运气问题，是结构问题：`@pytest.mark.pg` 的用例在本机全部 skip，
而「旧值删不掉」这类缺陷**只存在于真实 SQL 的语义里**，假连接永远碰不到。

发现的真 bug：`kb/store/items.py` 写媒体 props 的 UPDATE 里，`mediaError` 有删除
分支（`props - 'mediaError'`），但 `mediaTruncated` 完全没有删除动作。`payload`
只在本次有截断时才带这个键，于是「上次截了 15 张、这次一张没截」时旧值一直留着
——界面永远显示「已截断 15 张」，而实际全存了。用户会以为丢了图。

修完还做了**变异测试**：把那句 `- 'mediaTruncated'` 去掉，对应用例立刻变红。
证明这条用例不是在走过场。

## 二、范围：为什么不下视频原文件

**结论：只下封面与图文图片。** 依据不是「现在用不上」，那是个会过期的理由。

> PRD `M4-07` 把视频原文件定为 **P2「按需」**，PRD §5.5 成本控制表写
> 「视频 \| 默认不存原文件，只存封面 + 字幕 + 摘要」。这是**产品层已做的决策**。
> 技术方案 §4.6 的「抓到时立即下载，不留外链」约束的是「我们**存**什么」，
> 不约束「我们**不存**什么」——不存的东西没有外链可留。

**对抽帧的影响**：`extract_frames(video_path)` 要本地文件，没有文件跑不了。
但 P2「按需」的语义就是**在那个时刻才下载**：用户点「生成章节」→ 用 `items.url`
重新抓一次拿新签名 URL → 下载到临时文件 → 抽帧 → 临时文件删掉。
代价是**抽帧需要联网重抓一次，不能离线跑**。这是 PRD 定 P2 时就买了的单。

**一个免费的优化**（本轮未实现）：`props.mediaUrls` 里留着抓取那一刻的视频签名 URL，
按需下载时先试它，没过期就省一次重抓。

### 3.1 真实抖音封面下载（本机 Windows，真实网络）

```
guard 判定   → 通过（钉扎生效）
真实下载     → HTTP 200，0.60 秒，44733 字节（43.7 KB）
Content-Type → image/jpeg
前 4 字节    → ffd8ffe0（JPEG 魔数，确认不是伪装）
mime 嗅探    → ('image/jpeg', 'header')
```

**这条是本轮唯一一次真的从互联网下了一张图**，不是假实现。

### 3.2 签名 URL 过期：实测证实

真实抖音封面的 query 含：
```
x-expires=1797048000      → 2026-12-12T04:00:00Z，距抓取约 14 天
x-signature=KT06ee6j43iTHmbuSlgof234VgA%3D
```

**视频 URL 的过期信息加密在 `rc` 参数里**，不可读：
```
rc = ZTRoOWk7Nzc8OzU2ODo5M0BpM2d5Oms5cjxuZTMzNGkzM0A0NT
```

两者机制不同。原设计「不依赖两者相同」的结论仍成立，但现在有了更硬的依据。

### 3.3 封面藏在 `thumb_url`，不在 media 列表里（最关键的发现）

真机抓一条抖音视频（第 12 集 网络协议），`media` **只有 1 条**：

```
media count: 1
[0] role='video' ext='mp4' 768x576
    url   = https://v95-aw-cold.douyinvod.com/...          ← mp4
    thumb = https://p95-zjwztc-sign.douyinpic.com/...jpeg  ← 封面在这
```

代码侧证据链：
- `kb/extract/normalize.py:222`：`default_role = "video" if post_type == "video" else "image"`
  —— **role 永远只会是 video 或 image，不会是 cover**
- 所以 **`role='cover'` 今天没有任何生产者**

照「遍历 media 下载 url」写，结果是把我们决定不下的 mp4 全下了，而封面**零张**。
本轮的 `plan.py` 从 `thumbUrl` 合成一条 `role='cover'`。

## 四、SSRF 防护：为什么是三层，不是一层

下载 URL 来自第三方响应，worker 去请求它天然有 SSRF 风险。判据三层并列：

| 层 | 内容 | 为什么不能省 |
|---|---|---|
| ① 拒内嵌 v4 的 IPv6 形式 | `::ffff:0:0/96`、`64:ff9b::/96`、`64:ff9b:1::/48`、`2002::/16`、`2001::/32` | 无条件拒绝，**不依赖任何 `is_*` 属性** |
| ② 硬编码拒绝段 | 含 `100.64.0.0/10`（本项目 Tailscale 用的 CGNAT 段） | 人写下的安全意图 |
| ③ 白名单 | `is_global` 且非 private/loopback/link_local/multicast/reserved/unspecified | 接住 ② 没想到的段 |

### 只说黑名单为什么不够——实测复现

```
2002:7f00:0001::   → 还原出 127.0.0.1        ┐
2002:6440:9c2f::   → 还原出 100.64.156.47    ├ 纯 IPv4 黑名单全部放行
2002:a9fe:a9fe::   → 还原出 169.254.169.254  ┘
```

`100.64.156.47` 是**本项目平板自己的 Tailscale 段**。打
`http://100.124.156.47:8000/api/items` 就是打自己的 API。

### 只说 `is_global` 也不够

它和黑名单**同源**，都是 CPython 里硬编码的枚举表。源码里 `2002::/16` 那行注释写
「IANA 说 N/A，我们拿不准，保险起见算不可达」——是策略选择不是规范结论，
未来版本可能改掉。所以第 ① 层必须独立存在。

### 钉扎（pinning）

先自己 DNS 解析出**全部** IP，逐个判定，然后**连判定的那个 IP**，不让 httpx 再解析。
否则判定时解析到公网、连接时解析到内网，校验白做。多 IP 要求每一个都合格——
只判第一个会漏掉「第二条是 127.0.0.1」。

## 五、`replace_for_item` 的那行 SQL：真库 A/B 实验

`kb/store/attachments.py` 的 `_REPLACE_SQL` 里有一行：

```sql
where (select count(*) from gone) >= 0
```

**它语义上恒真，但删不得。** 作用是制造求值依赖：PG 必须先算 `gone`（DELETE）
才能判断这个条件，于是 DELETE 必然排在 INSERT 之前。

真库对照实验（平板 PG，同一张表 + 唯一索引，先 `insert ('same-key')` 占位）：

| 写法 | 结果 |
|---|---|
| 保留 `where ... >= 0` | **成功**，最终 1 行 |
| 去掉这一行 | **`ERROR: duplicate key value violates unique constraint`** |

这是本轮我判断差点出错的地方——我一开始认为它是「冗余恒真式」，理由是
`ins` 的 `select ... from unnest` 没引用 `gone`。**漏看了 `where` 子句里的引用。**
架构师坚持后做了实验，才确认它对。**若按我当时的结论删掉，每次覆盖写都会撞索引。**

为什么是 `>= 0` 不是 `> 0`：首次 fetch 时 `gone` 一行都没删，`count(*)` 为 0。
写成 `> 0` 会让**第一次**写入一条都插不进去——把「重跑会撞」换成「首次全丢」，更糟。

## 六、`storage_key` 为什么是「item_id + 内容哈希」

`attachments_key_uniq` 是 `storage_key` 上的**全局**唯一索引，所以：

| 方案 | 问题 |
|---|---|
| 纯内容 sha256 | 两个 item 引用同一份字节时第二条撞索引。补救只有 `on conflict do nothing` → 第二个 item 永远没有封面，而字节明明在磁盘上 |
| 纯随机 | 不撞索引，但重试同一 item 会生成新 key、新文件，旧行还在 → 重试一次多一份封面 + 一个孤儿文件 |
| **item_id + 内容哈希** | 同 item 同内容 → 同 key → 重试天然幂等；不同 item 永不撞索引 |

代价：磁盘上可能存两份同样的字节。为 200 KB 的封面换掉「跨 item 删除竞态」
这一整类问题，划算。

## 七、与设计文档的偏离

| # | 偏离 | 理由 |
|---|---|---|
| 1 | 图文类**不**额外产 `role='cover'` | 那张图与第一张 image 字节相同，会派生同一个 `storage_key` 撞全局唯一索引。图文的展示图由 `primary_cover_id` 回落取第一张 image |
| 2 | `primary_media_id` 命名（设计里叫 `primary_cover_id`） | 「cover」会让人以为只认 `role='cover'`，而它实际回落取 image。名字直接影响语义理解 |
| 3 | 新增 `SkippedMedia` 的 reason 枚举多了 `disk_full` | 磁盘不足与「下载失败」是两种不同的可恢复性，混在一起排查方向会错 |

## 八、已知缺口（诚实标注，别当已完成）

| 缺口 | 为什么没做 | 怎么补 |
|---|---|---|
| **视频原文件不下载** | PRD `M4-07` 定 P2「按需」 | 用户触发抽帧时重抓 URL → 下载临时文件 → 抽帧 → 删除 |
| **没有 retry 端点** | `kb/api/app.py` 路由表里没有（M2-10 未做） | 做 `POST /api/items/{id}/retry`。在此之前媒体失败只记 props，不污染 jobs |
| **抖音图文未实测** | 手上没有图文类样本，只验了视频 | 抓一条小红书/抖音图文，确认 `thumb_url` 为空时走 `media[0]` 那条路 |
| **`max_frames`/图片数量上限未按真实成本校准** | 视觉通道未配，算不出单帧成本 | 配好通道后按真实单价复核 |
| **`/api/media` 前端未接** | 前端在 R7 之后才做 | 卡片 `<img src="/api/media/{key}">`，浏览器自动带 cookie |
