## 一、端到端验收（真机，未人为干预）

这是本轮最硬的一条证据：**通过 API 提交一条链接，等 30 秒，worker 自己抓完了**。

```
$ curl -X POST /api/items -d '{"url":"https://v.douyin.com/5gjBAuYo7PE/",...}'
{"id":17,"kind":"link","status":"pending"}
HTTP=202

$ sleep 30 && psql -d kb
items id=17:
  kind         = image            ← 从 link 自动升级
  title        = 一些基础的一些编程的词。#ai学习指南 #agent工程...
  媒体数       = 1
  失败原因     = (空)

jobs id=7:
  state = done, attempts = 0      ← 一次成功，零重试
```

**没有手动跑 worker、没有改库、没有重启服务**。提交之后它自己完成了。

### 1.1 另一个样本：失败后重试成功

库里原有的 id=16（用户手机提交的那条）经历了完整生命周期：

| 时刻 | 事件 | jobs 状态 |
|---|---|---|
| 部署后首次跑 | `default_extractor` 的 bug（见 §4.1）| `pending, attempts=1, run_after 推后 1 分钟` |
| 修复后重跑 | 抓取成功 | `done, attempts=1, error 清空` |

```
items id=16:
  kind         = video
  title        = 第12集 一口气搞懂支撑现代互联网运转的14个核心网络协议...
  duration_sec = 445                  ← 生成列从 props 算出
  props        = {"platform":"douyin","mediaCount":1,"duration_sec":"445",...}
```

这条同时证明了三件事：退避真的推后了 `run_after`、重试真的会重新领取、
成功后 `error` 真的被清空。

## 二、`workerOk` 首次转绿

R2 以来这个字段一直是 `false`，因为**没有真实的心跳写入方**。
交接包里连续三轮写着「不许为了变绿而写死 true」。现在有真的了：

```
$ curl http://127.0.0.1:8000/api/health
{"ok":true,"dbOk":true,"meiliOk":true,"workerOk":true,
 "diskFreeGb":163.0,"workerHeartbeatAt":"2026-11-27T06:53:44.263092+00:00"}
```

链路：worker 每 30 秒写 `settings('worker_heartbeat')` → `/api/health` 读它 →
90 秒内算活着。键名由测试强制对齐（见 §3.1）。

## 三、模块职责与关键决策

| 文件 | 职责 | 为什么不合并 |
|---|---|---|
| `kb/store/jobs.py`（扩） | 领取、标完成、标失败、恢复卡死 | 所有涉及 `jobs` 的 SQL |
| `kb/store/items.py`（扩） | `apply_extract`：抓取结果落库 | 所有涉及 `items` 的 SQL |
| `kb/worker/loop.py` | 轮询、单条处理、异常兜底 | 纯编排，零 SQL |
| `kb/worker/__main__.py` | 池装配、心跳线程、信号退出 | 与 `kb/api/__main__.py` 对称 |

### 3.1 心跳必须独立线程

一次抓取 10–20 秒（R3 实测）。心跳写在主循环里的话，抓取期间心跳就断了，
health 会误判 worker 死亡。所以心跳走单独线程，间隔 30 秒。

心跳间隔与 api 侧 `WORKER_STALE_AFTER`（90 秒）的关系由测试强制：

```python
assert worker_main.HEARTBEAT_SECONDS < WORKER_STALE_AFTER.total_seconds()
```

不靠注释提醒——注释里的人会改，断言不会。

### 3.2 失败不改 `kind`

`kind='link'` 是入库时按「只有链接」定下的降级结果。抓取失败时把它改成别的
是谎报抓到了东西，改回 `link` 又是空操作。保持原值，让界面只靠
`props.fetchError` 显示「处理失败，可重试」。

### 3.3 媒体不写 `attachments`

那张表要求 `storage_key` / `mime` / `sha256` 三者非空，而三者都要**媒体真正下载后**才有值。
R5 只抓元数据不下载，硬写只能拿 URL 冒充 `storage_key`——那会给将来的
`/api/media` 埋路径穿越风险（方案 §8 的 media 端点靠 `storage_key` 拼路径）。

媒体信息先进 `props.mediaUrls` / `mediaCount`，等下载轮次（R8 之后）转正式附件。

### 3.4 未实现的步骤不假装完成

`summarize` / `ocr` / `tag` / `index` 在 R5 之后才有。现在领到就标 `done` 是谎报——
条目会显示「已完成」但摘要标签全是空的。实现里标回 `pending` 并写明
「步骤 X 尚未实现（R5 之后才有）」。

### 3.5 `props` 用 `(props - 'fetchError') || ...`

`||` 只覆盖同名键、**不删旧键**。成功路径不显式删 `fetchError` 的话，
重试成功后界面会一直显示「处理失败」。

## 四、踩到的坑（都是真机的，不是推演）

### 4.1 `default_extractor` 直接返回 `extract`，每条任务都失败

```python
# 错：
def default_extractor():
    return extract  # extract(url, *, hub=None)！不传 hub →
    # 返回「抓取器未注入，无法抓取」


# 对：包一层，把 parsehub_adapter.parse 作为 hub 传进去
```

**测试为什么没抓到**：原来只断言 `callable(extractor)`。
`extract` 当然是 callable，测试绿，真机全挂。

修的时候先写了失败测试：

```python
assert extractor is not extract, "直接返回了 router.extract，没传 hub"
assert list(inspect.signature(extractor).parameters) == ["url"]
```

**教训**：断言 `callable` 等于没断言。要断到「参数被正确注入」这一层。

### 4.2 proot 下 `supervisord` 的 socket 创建失败，`supervisorctl` 完全不可用

```
$ supervisorctl status
unix:///var/run/supervisor.sock no such file
```

`supervisord` 本身在跑、也能 fork 子进程（api 就是它的子进程），但 unix socket
建不出来，所以 **`supervisorctl reread/update/add` 全部不可用**。
想加一个新 program 唯一的办法是**重启整个容器**，让 supervisord 启动时读配置。

顺带发现：多次 `sv restart` 会留下多个孤儿 supervisord（一次看到 5 个 pid
父进程都是 1），旧的 api 进程也不退。判断「新配置有没有生效」必须看
**pid 变没变**，不能看 health 返回值——旧进程照样响应。

### 4.3 `nohup ... &` 在 `proot-distro login` 会话里活不过退出

```
$ proot-distro login debian -- bash -c "... nohup python -m kb.worker &"
（退出后 ps 查不到进程）
```

proot 带 `--kill-on-exit`，会话结束即清理整棵进程树。**worker 只能由 supervisord
拉起**，不能手动 `nohup` 兜底。

### 4.4 库里有 5 个孤儿 supervisord

`ps -ef | grep supervisord` 看到 pid 2525/5266/9718/9900/12294/28992，多数父进程是 1。
每次 `sv restart` 没清干净就多一个。目前不影响功能（只有 11395 那棵树在服务），
但会慢慢吃内存。**这条留给 R9（运维闭环）处理**。

## 六、诚实标注

✅ **已验证**（每条有真机输出）
- 端到端：API 提交 → 30 秒后 worker 自动抓完（`kind` 从 link → image，`attempts=0`）
- 失败重试：第 1 次失败 → `pending/attempts=1/run_after 推后 1 分钟` → 重试成功 → `done/error 清空`
- `workerOk` 从 `false` 变 `true`，`workerHeartbeatAt` 持续更新
- worker 由 supervisord 常驻（pid 11401，与 api 同父）
- 抓取结果正确落库：`kind`、`title`、`props.mediaCount`、`duration_sec` 生成列（视频 445、图片为空）
- 283 passed / 26 skipped / 3 deselected；覆盖率 82%+
- `ruff` / `mypy`（23 文件）/ `eng_checks --arch` 全过

⚠️ **未验证**
- **`summarize`/`ocr`/`tag`/`index` 四步**：实现里明确标「尚未实现」并退回队列，
  所以这些任务会一直 `pending`。这是有意的，不是 bug
- **并发两个 worker**：`SKIP LOCKED` 的正确性只有假连接断言，没真开两个进程压测
- **长时间运行**：worker 常驻只观察了几分钟，没跑 72 小时
- **`attachments` 表仍是空的**：媒体没下载，这一轮不写（见 §3.3）
- 孤儿 supervisord 的清理（见 §4.4）

❌ **失败过的尝试**
- `default_extractor` 直接返回 `extract` → 真机每条任务都报「抓取器未注入」
- `supervisorctl reread/update` → `no such file or directory: supervisor.sock`
- `proot-distro login ... nohup ... &` → 会话结束进程被杀
- `sv restart kb-container` → 旧 api 进程不退，新配置没生效；必须 `force-stop` + 确认 pid 变化
