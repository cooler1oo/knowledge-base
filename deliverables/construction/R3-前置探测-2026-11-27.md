## 一、结论先行

| 判据 | 结果 | 证据 |
|---|---|---|
| ParseHub 在平板容器内可导入 | ✅ | `Platform 数量: 25` |
| **能抓真实抖音视频** | ✅ | 用户手机提交的真实链接，`title` 非空、`type=video`、`media` 是 dict、7 个字段 |
| **能抓真实抖音图文** | ✅ v9.11 补验 | 用户提供的真实图文链接，`type=image`、`media` 是 **list**、`ext=jpg`、1440×2131 |
| 返回结构符合方案 §4.3 | ❌ **不符合** | 方案写 `media` 是列表，实际视频给 dict、图文给 list、无媒体为 None |
| 小红书能抓 | ❌ **确定抓不到** | 三种 ID × 两种 UA × 两个出口，全部 `error_code=300031`；真实 ID 与编造 ID 响应完全相同 |

**所以 R3 可以按 ParseHub 路线开工**，但映射代码必须兼容三种 `media` 形状，且方案 §4.3 要改。
小红书按 §4.10 降级为「链接 + 记录失败原因」——**入口必须接受，内容抓不到就如实显示抓不到**。

## 三、与设计的偏离清单

### 3.1 方案 §4.3 的调用契约写错了 `media` 的形状（需升版）

| 项 | 内容 |
|---|---|
| 方案原文 | `# result.to_dict() → {platform, type, title, content, raw_url, media}`，暗示 `media` 是列表 |
| 实测真相 | `media` 是**三种形态之一**：`list[dict]` / `dict` / `None` |
| 源码依据 | `parsehub/types/result.py:68-83` |

```python
# 源码原文（parsehub/types/result.py）
media: list[dict] | dict | None = None
if isinstance(self.media, Sequence):
    media = [asdict(m) for m in self.media]  # 图文 → 列表
elif self.media:
    media = asdict(self.media)  # 视频 → 单个 dict
```

| 内容类型 | result 类 | `media` 形状 |
|---|---|---|
| 视频 | `VideoParseResult` | `dict`（单个） |
| 图文 | `ImageParseResult` | `list[dict]`（多张） |
| 多视频/视频+图 | `MultimediaParseResult` | `list[dict]` |
| 无媒体 | — | `None` |

**影响**：只按视频写映射代码，遇到图文会 `AttributeError`（对 list 取 `.get()`）。
**处置**：映射层必须做「先判断类型再取值」，不能用一种形状套全部。

### 3.2 `duration` 的单位，源码注释写错了（需回写方案）

| 项 | 内容 |
|---|---|
| 源码注释 | `duration: 视频时长，单位: 秒`（`media_ref.py:33`） |
| 实测值 | `445071` |
| 核对 | 按毫秒 = **7.4 分钟**（符合「第12集讲解」视频）；按秒 = **123.6 小时**（不可能） |
| 结论 | **实际是毫秒**。注释错了，不能照注释写代码 |

**这直接影响 `items.props.duration_sec` 生成列**：库里那个生成列叫 `duration_sec`，
若把毫秒值直接写进 `props.duration_sec`，一条 7 分钟的视频会被记成 445071 秒（5 天）。
映射时必须 `// 1000`。

### 3.3 `ImageRef` 与 `VideoRef` 的字段差异（**已由实测订正**）

v9.10 时这一节是**读源码推断**的，写「图文没有 `backup_urls`」。用户提供真实图文链接后
实测发现**推断错了**：字段存在，只是值为空列表。

| 字段 | 抖音图文（实测） | 抖音视频（实测） |
|---|---|---|
| `media` 形状 | **list**（长度 1） | **dict** |
| `type` | `image` | `video` |
| `ext` | `jpg` | `mp4` |
| `width` × `height` | 1440 × 2131 | 768 × 576 |
| `duration` | **不存在** | 445071（毫秒） |
| `backup_urls` | **存在，值为空列表（长度 0）** | 存在，3 条 |

**为什么这条值得单独写**：如果按 v9.10 的推断写代码（假设图文没有该键），
`item["backup_urls"]` 在视频上正常、理论上图文会 KeyError；而真相是图文根本不会
KeyError，只是拿到空列表。两种实现都能跑，但**推断与事实不一致**这件事本身会让
后续排障时误判。统一用 `.get("backup_urls", [])`，两种情形都对。

### 3.4 小红书：无 cookie **确定抓不到**（已取证完毕）

v9.10 时我把这条标成「待复验」，理由是「链接是随手编的 ID，可能本身已失效」。
用户要求用真实链接复验，于是做了完整取证。

**取证方法**：不是找一条真链接就下结论，而是做**对照组**——
如果真 ID 与编造 ID 得到相同响应，就说明拦截与内容无关，是反爬机制本身。

| 变量 | 取值 |
|---|---|
| ID | `6553f0e9000000003c00d4ab`（真实格式）、`65c1e4a1000000001102ba7a`（真实格式）、`deadbeefdeadbeefdeadbeef`（**编造**） |
| UA | 桌面 Chrome、移动 iPhone |
| 网络出口 | Windows 本机（代理/直连）、**平板家宽** |
| 路径 | `/explore/<id>`、`/discovery/item/<id>`、带 `xsec_token` |

**结果：全部一致，无例外。**

```
HTTP=302
→ /404/sec_XXXX?error_code=300031&error_msg=当前笔记暂时无法浏览
```

`error_code=300031` 与「当前笔记暂时无法浏览」是小红书风控的统一返回。
**真实 ID 与编造 ID 得到完全相同的响应**，说明拦的是「未登录的一切请求」，
不是「这条不存在」。

补充证据：
- `xhslink.com` 短链（分享出来的真实形态）→ **HTTP 404**
- 未登录访问 `/explore` 首页 → **302 跳 `/`**（33 字节，纯重定向，无内容）
- 三种 UA 均无效（移动 UA 直接 `?source=xhs_sec_server`）
- 两个网络出口（本机、平板家宽）结果相同
- ParseHub 两条 fallback（游客 session / 移动端）均报「被风控拦截」

**结论**：小红书在**不注入 cookie** 的前提下抓不到。这不是「链接不对」。

**处置（v9.11 已定）**：AGENTS.md 写「小红书必须能接」，与「必须能抓到内容」是两件事：

| 层级 | 要求 | 现状 |
|---|---|---|
| 入口 | 用户分享过来**必须能存进去** | ✅ 能存：`kind='link'`，保留 URL + 分享文案原文 |
| 内容 | 抓到标题、封面、正文 | ❌ 抓不到（风控） |
| 界面 | 用户能看到「处理失败，可重试」 | 需 `jobs.error` 记录原因 |

这正是技术方案 §4.10 第三层降级的设计意图——**记录不能丢**。
所以小红书这条不构成产品缺陷，但必须在界面上如实显示「抓不到」，不能假装成功。

## 四、下一轮（R3 正文）的已知坑

| # | 坑 | 现象 | 防法 |
|---|---|---|---|
| 1 | `media` 三种形状 | 对 list 调 `.get()` 报 `AttributeError` | 映射前先判 `isinstance(media, list)` |
| 2 | `duration` 是毫秒 | 时长被记成 445071 秒 | 写库前 `// 1000`；并补一条单测钉住这个换算 |
| 3 | 图文**没有** `duration`，但**有**空的 `backup_urls` | 假设「没有该键」会写错默认值逻辑 | 统一 `.get(k, default)`，不要假设字段存在或不存在 |
| 4 | 小红书无 cookie **确定抓不到** | `error_code=300031`，`FallbackError: 被风控拦截` | 不要试图绕（三种 UA × 两出口已全部失败）；按 §4.10 降级为 `kind='link'` + 记录失败原因 |
| 5 | 单条抓取 10–20 秒 | 同步等待会阻塞 | 抓取放在 worker（R5），API 只入队 |
| 6 | 签名 URL 带 `x-expires` | 过期后 403 | **抓到立刻下载**，不留外链（方案 §4.6） |
| 7 | 探针脚本经三层嵌套引号传参会炸 | `syntax error near unexpected token` | 脚本落盘再执行，不用 `ssh "... python -c \"...\""` |

## 五、诚实标注

✅ **已验证**（每条都有上面的原始输出）
- ParseHub 在平板容器内可导入，`Platform` 25 个
- 真实抖音**视频**能抓到：`title` 非空、`type=video`、`media` 是 dict、7 个字段、`duration=445071`
- 真实抖音**图文**能抓到（用户提供链接 `v.douyin.com/5gjBAuYo7PE/`）：
  `DouyinImageParseResult`、`type=image`、`media` 是 **list**、`ext=jpg`、1440×2131、
  无 `duration`、`backup_urls` 为空列表
- 返回对象的完整属性与方法清单
- `media` 的三种形态由源码 `to_dict()` 确证（不是推测）
- `duration` 实际单位是毫秒（用 7.4 分钟 vs 123.6 小时交叉核对）
- **小红书无 cookie 抓不到**：三种 ID × 两种 UA × 两个网络出口 × 三种路径，
  全部 `error_code=300031`；真实 ID 与编造 ID 响应完全相同

⚠️ **未验证**
- B站、公众号、知乎、微博、快手、头条等其余 14 个平台
- 抖音**多图**图文（实测这条只有 1 张图；源码说图集上限 35 张，未验多图行为）
- 抓取峰值内存（方案 §2.5 的预算是否会破）
- 小红书**注入 cookie 后**能否抓到（本项目不做 cookie 注入，故不验）

❌ **失败过的尝试**
- 小红书抓取（3 个 ID × 2 种 UA × 2 个出口）→ 全部 `302 → /404/sec_*`，`error_code=300031`
- `xhslink.com` 短链 → `HTTP 404`
- 未登录访问小红书 `/explore` → `302` 跳 `/`，33 字节，无内容
- 手编的抖音图文 ID → `ContentUnavailableError: 作品不可用: core_dep`
- 用 `ssh "python -c \"...\""` 传三段嵌套引号的脚本 → bash 语法错，改为落盘执行
- 通过 Bing / 通用搜索找真实小红书笔记 URL → 只返回 SEO 垃圾页，无真实笔记链接
