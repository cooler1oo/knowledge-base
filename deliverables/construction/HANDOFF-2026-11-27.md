## 二、必须先知道的 8 件事（都会踩坑）

### 0. 跑测试不能加 `cd` 前缀（本轮被误判 4 次）

外部 Stop 门禁只解析**第一段**命令，只认 `python` / `pytest` 开头：

```
cd 某目录 && python -m pytest   → 门禁判 FALSE（"没跑验证"），反复拦
python -m pytest                → 门禁判 TRUE
```

要用 `.venv` 的 python 时，写成 `python -m pytest --rootdir=<根> <根>/tests`
或先 `cd` 再单独执行，**不要串成一条 `cd && python`**。
这条已写进 `AGENTS.md` 交付段。

### 0b. git push 必须显式配 `http.proxy`（schannel 不读环境变量）

```bash
# 症状：$ echo $HTTPS_PROXY 有值，但 push 报 schannel/OpenSSL 的 TLS 错
# 根因：Git for Windows 默认 http.sslBackend=schannel，只用 http.proxy 配置项，
#       不读 HTTPS_PROXY 环境变量（curl 是读的）
git config http.proxy "$HTTPS_PROXY"     # 端口每次会话变，别写死
```

**代理本身也不稳定**：实测 3 次里 1 次成功 2 次 `CONNECT tunnel failed, response 502`。
推送失败先重试（间隔几秒），不要以为是自己配置错了。
`python -m tools.eng_checks --pre-push` 现在会检查这个矛盾。

### 2. proot 的后台进程活不过 SSH 会话

`nohup ... &` 和 `setsid` 都试过，**会话结束即被杀**（proot 带 `--kill-on-exit`）。

**大文件下载必须前台跑**（实测可行）：
```bash

```
229 MB / 52 秒，895 MB / 3 分 15 秒，都很稳。

### 3. GitHub Releases 在国内是 0 B/s，必须换镜像

```
github.com                    → HTTP 200（首页能开）
objects.githubusercontent.com → 文件下载 0 B/s（Releases 的实际 CDN）
```

**本机（Windows）与平板都是 0 B/s**，不是设备问题。

**可用镜像**：`hf-mirror.com/csukuangfj/sherpa-onnx-*`，实测 4.6 MB/s。
ModelScope 更快（23 MB/s）但**没有 sherpa-onnx 模型镜像**。

### 4. 900 MB 以上的模型会打挂整个服务

```
fp32 模型 895 MB  → SIGTERM，sshd + api 一起挂，需用户在平板上手动重启 sshd
int8 模型 229 MB  → 正常，RTF 0.148，峰值 2.8 GB
```

**崩溃时仍有 2.9 GB 可用内存 + 5.0 GB swap**，所以瓶颈**不是内存容量**，是 proot 对大内存进程的存活能力。**900 MB 以上一律不用。**

### 5. `supervisorctl` 在 proot 下完全不可用

```
$ supervisorctl status
unix:///var/run/supervisor.sock no such file
```

`supervisord` 能跑也能 fork 子进程（api 就是它的子进程），但 unix socket 建不出来。
**加新 program 只能重启整个容器**（改 `/etc/supervisor/conf.d/` 后 `sv force-stop` + `sv start`）。

且 `sv restart` 不退旧进程——**必须确认 pid 变了**，旧进程照样响应 health，看返回值会误判。

### 6. 抖音视频有音频轨（曾判断错）

**不要用二进制搜索判断文件结构**。我曾搜前 200KB 找 `mp4a` 得出「没有音频轨」的错误结论，
实际第二个 `trak` 在 `off=205676`，差 5676 字节没搜到。

正确解析：
```
moov size=480916 off=32
  trak → mdia → hdlr = "vide"      视频轨
  trak → mdia → hdlr = "soun"      音频轨（mp4a / AAC）
```

### P0：ASR 分段解码（这是 AI 层的前置）—— ✅ **已完成（2026-11-27 下午）**

**已实测的问题**：长音频标点会退化。

| 音频长度 | RTF | 标点 | 术语 |
|---|---|---|---|
| 30 秒 | 0.020（快 50 倍） | 完整 | `TCP/IP` 正确 |
| 445 秒 | 0.148 | 缺失 | 写成 `TcPP` |

**要做的**：切 30 秒一段分别解码，再把结果拼起来。目的**不是省时间，是标点与术语准确率**。

**做完的结论（v9.14，实测推翻了两处原写法）**：

1. **收益比原判断更大**：不只是标点和术语，是**准确率本身**。整段解码稳定把
   「堵」听成「毒」、「10 分钟」听成「十0分钟」/「1分钟」；分段后全对。
2. **不能硬切**：固定 30 秒硬切会在切口补字（428 秒样本多吐 6 字）。
   改成**切点吸附到标称位置 ±2 秒内最安静处**，字数偏差从 +6 降到 −2。
3. **重叠 + 文字去重被否决**：FunASR 官方推荐的「30 秒窗口 + 2 秒重叠」在本项目
   实测更差（多 130 字）。重叠区两次识别不逐字相同，字符串去重找不到该切的地方。

实测数据（448.9 秒合成语音，理论 1665 字，本机 Windows + 同一 int8 模型）：

| 切法 | 耗时 | RTF | 字数 | 偏差 |
|---|---|---|---|---|
| 整段 | 68.22 s | 0.152 | 1624 | −41 |
| **分段吸附静音** | **8.81 s** | **0.020** | **1664** | **−1** |

**代码位置**：`kb/asr/segment.py`（切点规划，纯算术）、`kb/asr/decode.py`（装配解码）、
`tests/test_asr_segment.py`（33 项单测，不加载模型）。

**平板真机复核（2026-11-27 晚，真实抖音视频 445.1 秒，含 BGM）**：

| 方式 | 耗时 | RTF | 字数 | 逗号+句号 |
|---|---|---|---|---|
| 整段 | 64.29 s | 0.144 | 2364 | 34 |
| **分段** | **10.63 s** | **0.024** | **2476** | **132** |

术语：整段 `TcPP`/`httP`/`Https` → 分段 `TCPIP`/`HTTP`/`HTTPS`。

**真机撞出一个 bug（本机测不出，已修）**：首版对 445.1 秒音频切出 **55.1 秒**的段。

**本轮新增两条环境事实，务必记住**：

1. **`scenedetect` 必须锁 0.6.6，不能升 0.7.x。** 0.7.0 起 `Requires-Dist:

   先装 headless 再装 GUI 版，`getBuildInformation()` 从 `GUI: NONE` 变成
   `GUI: WIN32UI`；再 `pip uninstall opencv-python` 之后，headless 版还在 `pip list`
   里但 `import cv2` 变成 `ModuleNotFoundError`（本机已复现）。所以是「**不许装** GUI 版」，
   不是「装错了再卸」。

## 十、与新用户的沟通方式

**用户是非技术背景**，这几点很重要：

1. **术语必须先解释再说结论**。不要直接堆专业名词。
2. **不要问技术细节该怎么做**（如「先做 A 还是 B」）——按最优原则自己判断并执行，
   只在**重大决策或影响使用体验**时才问。
3. **汇报三态**：✅ 已验证（贴输出）／⚠️ 未验证（说原因）／❌ 失败（贴报错 + 已试方案）。
4. **不许虚假汇报**：只报已验证事实，「应该」「大概」不能当结论。
5. **发现自己错了要立刻说清**。本会话里我曾错误判断「抖音没有音频轨」，
   方法错误（搜字节区间），用户指出后实测推翻——这类错误必须当场纠正，不要掩盖。
