## 零、一页人话版

我要做的东西，一句话：**一个能在手机和电脑上打开的私人资料库，看到什么就丢进去，以后凭模糊记忆也能翻出来。**

它和普通收藏夹的区别在三处：

1. **存的时候不用想**——它自己判断这是什么、讲什么、给个摘要。你只在它判错时改一下。
2. **链接挂了也不怕**——正文和摘要存在自己手里，不依赖原网页还活着。
3. **它会主动把旧东西推到你面前**——不是让你去"整理"，而是让你"重新遇到"。

第一版（MVP）只做"存得进、看得见、搜得到"三件事。其余靠时间加。

---

## 一、意图与原因

### 要解决的问题

一个人每天在网上遇到大量"以后可能有用"的东西：文章、视频、截图、链接、文件。存进浏览器书签、微信收藏、相册之后，**六个月后基本等于丢了**——因为：

- 平台会清理（微信收藏有上限、浏览器书签只能按标题搜）
- 内容会消失（公众号删文、视频下架、链接 404）
- 记忆会衰减（只记得"那篇讲 AI 抢设计师饭碗的文章"，标题里一个词都不对）

### 成功长什么样

三个月后，如果发生下面任何一件事，这个项目就算成立：

- 想找一条半年前存的东西，**10 秒内找到**
- 某天闲下来，**主动打开它翻**，而不是被迫整理
- 存一条东西的**动作少于 3 次点击**
- 某条链接的原网页已经 404，但我这里**还能看到当时存了什么**

### 为什么现在做

现有工具全都要么太重（Notion、Obsidian，得先搭系统）、要么只解决一层（Pocket 只管读、Eagle 只管图、浏览器书签只管链接）。没有一个东西同时管住"文章 + 视频 + 图片 + 文件 + 链接"，还按中文习惯来。

## 二、目标 / 非目标 / 反目标

### 目标

| # | 目标 |
|---|---|
| G1 | 任何形态的内容，都能用同样的方式存进来（链接、图片、文件） |
| G2 | 存进来的东西自带摘要、类型、主题标签，不需要用户填写 |
| G3 | 支持四种找回方式：记得片段、记得主题、记得日期、瞎翻 |
| G4 | 手机和电脑看到的是同一份数据 |
| G5 | 数据随时可以完整导出，不锁定在某个平台里 |

### 非目标（这一版明确不做）

- 多人协作、分享给他人
- 公开分享页、社交功能
- 跨库检索、团队知识库
- 移动端离线使用
- 内容编辑（不是笔记软件，不提供富文本编辑器）

### 反目标（就算做出来也算失败）

- **变成"整理工具"**：如果用户 80% 的时间花在分类、打标签、挪位置，这个产品就失败了。整理必须是可选的。
- **变成"收藏黑洞"**：如果存了 500 条却一条都没回看过，等于失败——功能再多也没意义。
- **需要学习成本**：如果第一次用要看教程才懂怎么存，失败。

## 四、方案选型（三条路线）

### 路线 A：文件夹型

左侧目录树，一条内容只能在一个位置。

- **优点**：所有人都会用，有"整理感"
- **缺点**：一条内容只能放一处；跨界内容必须二选一；时间长了目录树必然歪掉，最后还是靠搜索
- **代表**：Eagle、Windows 资源管理器、早期印象笔记

### 路线 B：对象型

类型 + 属性 + 标签 + 查询，四个独立维度。

- **优点**：一条内容可同时属于多个主题；存的时候不用选位置；"查询"自动更新
- **缺点**：概念较多，第一次用会懵
- **代表**：Capacities、Anytype

### 路线 C：流型

一条时间流，无分类，全靠自动标签和搜索。

- **优点**：存的时候零负担
- **缺点**：满足不了"要有结构、能自己建板块"的诉求；内容一多就是黑洞
- **代表**：mymind、flomo

### 选定：B 的底子 + A 的外壳

**底层按 B 建**（四积木），**界面按 A 呈现**（左侧看起来就是类型 → 子分类的树）。

理由：

1. 用户明确要"能自己在宽泛大类里建小分类、看着有条理"——这是 A 的外观能给的心理满足。
2. 用户的内容天然跨类（一篇讲 AI + 设计的文章），A 的单一归属做不到。
3. 纯 C 满足不了"要结构"的诉求，排除。
4. 界面上做成树，底层用标签，用户看到的和想要的完全一致，但不用承担"放错位置"的代价。

## 五、信息架构（四积木）

### 积木 1：类型（固定 6+1，不可增删）

由系统根据抓取到的内容结构判断，**用户不能新建类型**（能新建就会失控）。

| 类型 | 判断依据 | 示例 |
|---|---|---|
| 文章 | 有长正文（>300 字），无视频主体 | 公众号、知乎、新闻、博客 |
| 图文 | 图 ≥3 张且文字 <300 字 | 小红书、微博 |
| 视频 | 存在视频主体元素 | B站、抖音、YouTube |
| 图片 | 单张图片或截图 | 截图、设计稿、照片 |
| 文件 | 上传的 PDF/Word/Excel/压缩包 | 别人发的资料 |
| 链接 | 抓取失败，只有网址 | 需登录、被墙、反爬 |

判断**不依赖域名**。B站的图文笔记会落"图文"，B站的视频会落"视频"——依据是实际内容结构。

**判错怎么被记住**：用户改一次类型后，系统记下一条 `来源域名 → 类型` 的修正规则（例：`mp.weixin.qq.com → 图文`）。
规则优先级高于自动判断，可在设置里查看和删除。
记忆的颗粒是"来源域名 + 类型"，**不是"把修正喂给模型学习"**——前者可控、可撤销、可解释，后者不可靠且做不到"下次一定不错"。

### 积木 2：属性（每个类型自带字段）

| 字段 | 说明 | 谁填 |
|---|---|---|
| 标题 | 抓取或用户修改 | 自动 |
| 来源域名 | bilibili.com / mp.weixin.qq.com | 自动 |
| 作者 | 抓取 | 自动 |
| 封面 | 抓取后存到自己这里，不引用外链 | 自动 |
| 摘要 | AI 生成，100 字以内 | 自动 |
| 正文/字幕全文 | 用于检索 | 自动 |
| 字数 / 时长 | 抓取 | 自动 |
| 收藏时间 | 点保存的那一刻 | 自动 |
| 发布时间 | 原文发布时间 | 自动 |
| 状态 | 未读 / 在读 / 已读 / 归档 | 自动（首次=未读），可改 |
| 评分 | 1-5 星 | 用户（可选） |

### 积木 3：标签（主题，用户可建，二级）

- 两级：`父标签 › 子标签`，例：`AI相关 › skill和插件`
- **一条内容可挂多个标签**，这是和文件夹的根本区别
- 预设一批（用户可删可改）：

```
AI相关 / 工作赚钱 / 学点东西 / 生活过日子
健康 / 好看的东西 / 好玩放松 / 先存着以后用
```

- 标签来源分两种：`ai`（自动打的，可一键否定）、`user`（自己加的）
- **AI 只能从已有标签里挑，不能自己发明新词**。词表里没有合适的就留空，落进"没归好类的"筛子等人处理。
  理由：放开让 AI 造词，两周后就会出现 200 个近义标签（"AI""人工智能""ai工具"），
  正好撞上"不能变成整理工具"这条反目标。**宁可留空，也不生产垃圾。**
- 界面上左侧显示为树，点父标签等于选中所有子标签

### 积木 4：查询（保存的筛子，替代"智能文件夹"）

不是分类，是**存下来的一组筛选条件**，结果永远自动更新。

预置 4 个：

| 名称 | 条件 |
|---|---|
| 待看 | 状态 = 未读，按收藏时间倒序 |
| 这周存的 | 收藏时间在本周内 |
| 没归好类的 | 标签数 = 0，或 AI 置信度低于阈值的 |
| 值得再看 | 评分 ≥ 4 |

用户可以自建任意查询，也可以把它固定到左侧当"入口"。

## 六、数据模型

> 单人使用，不做协作，因此**不使用 CRDT**。冲突用"后写覆盖先写"（LWW）即可。
> 云数据库为唯一权威源，本地不做全量缓存（MVP 不做离线）。

## 七、核心流程

### 7.1 存一条链接（主路径）

```
1. 粘贴 URL / 手机分享过来
2. 立即写入 items（type 临时为空，status=unread，标题先用域名兜底）
   → 列表顶部立刻出现这张卡片，显示"处理中"
3. 入队 jobs
4. 后台：
   a. 抓取 → 标题、作者、封面、正文、发布时间、内容结构
   b. 存封面到对象存储（不引用外链）
   c. 按内容结构判 type
   d. AI 生成摘要
   e. AI 打 1-3 个标签
   f. 写回 items / item_tags
5. 卡片自动刷新：封面出现、类型确定、摘要和标签补上
```

**关键设计：保存动作必须"零等待"。** 用户按下保存，界面立刻出现占位卡片，可以继续做别的事，
抓取与 AI 处理全部在后台跑。**这不是为了省预算，而是为了让"存"这个动作变成肌肉记忆。**

同时明确一条底线：**后台要抓全、抓准，不为求快而砍质量。** 宁可这张卡片晚一分钟补全，也不要抓回半截正文。

**抓取失败降级**：type = `link`，只保留 URL + 域名 + 用户看到时能想起来的一句话（可以让用户手填，也可以留空）。这条**不能消失**，必须留在库里，因为用户确实见过它。

### 7.2 存一张图片

```
1. 上传 / 粘贴截图 / 手机分享图片
2. 立即显示缩略图
3. 后台：**一次视觉模型调用，同时产出「图中文字」和「一句话描述」** → 文字存入 content_text
   （不接第二家专用 OCR 服务：多一个 key、多一条链路、多一处收费，而视觉模型对截图里的小字够用）
4. OCR 出来的文字让「截图里的字」也能被搜到
```

### 7.3 存一个文件

上传 PDF/Word 等 → 抓 PDF 内文字（若能抽）→ 其余同链接流程。

### 7.4 搜索

**三层召回，结果融合排序**（按需要逐步上，不一次全做）：

| 层 | 实现 | 优先级 |
|---|---|---|
| 1 | 标题 / 标签 / 摘要 / 正文的关键词匹配（分词后多词 AND + 覆盖度排序） | P0 |
| 2 | 二字中文词兜底（"矩阵""导数""概率"这类词最短也最有信息量） | P0 |
| 3 | 语义向量（记得意思不记得词） | P2 |

> **工程现实**：数据量在几千条以内，直接用数据库的关键词检索就够快（几十毫秒）。
> 不要为了"显得专业"提早上搜索引擎——那是几万条以后才需要的账。
> 但要**预留升级路径**：检索层做成独立接口，将来换 Meilisearch 只改一处。
>
> **中文的特殊坑**（已查证）：SQLite FTS5 默认分词器对中文无效（整句当一个词）；
> trigram 索引体积翻倍且两字词检索弱；jieba 分词又有词典歧义。
> 所以第一版不做全文索引，用「分词后多词匹配 + 覆盖度排序」，准确率和成本更可控。

### 7.5 找回的四种路径（对应四种记忆）

| 用户记得什么 | 走哪条路 |
|---|---|
| 记得内容片段 | 搜索框（关键词 / 将来的语义） |
| 记得主题 | 左侧标签树点进去 |
| 记得大概哪天 | 时间轴视图，按周/月折叠 |
| 什么都不记得，只想翻 | 首页网格 + "随机漫游"按钮 |

### 7.6 手机端到底能存什么（边界写清，不承诺做不到的事）

| 来源 | MVP 支持 | 说明 |
|---|---|---|
| 链接 / 文本 | ✅ | share_target 收 URL 与文字，这是主力通路 |
| 图片 / 文件 | ❌ 推到二期 | 收文件依赖 service worker 在冷启动时处理 POST，安卓 Chrome 支持有限、容易失败。MVP 手机存图走"应用内上传"，不做系统分享 |

### 8.2 移动端布局

- 单列卡片流，顶部搜索框 + 底部三个 tab：**全部 / 标签 / 筛子**
- 详情页全屏，返回手势

### 8.3 卡片上显示什么

封面（无封面则显示类型图标 + 纯色块）· 标题（最多两行）· 摘要（最多两行，可关）· 类型角标 · 1-3 个标签 · 来源 · 收藏时间（相对："3天前"）

### 8.4 悬停 / 长按的操作

改类型 · 加标签 · 标为已读 · 评分 · 归档 · 删除

### 8.5 详情页

左：封面 / 视频封面+跳转原片 / 图片大图
右：标题（可编辑）· 摘要 · 标签（可增删）· 属性表 · "打开原文"按钮 · "我改过它"提示（当 AI 判错被人工修正时记录）
底部：同标签的其它内容（**这是"意外发现"的入口，成本极低价值极高**）

### 8.6 视觉规格

| 项 | 规定 |
|---|---|
| 主题 | 深色优先（浅色可选，不优先做） |
| 主色 | 单一强调色，用于选中态和主按钮，不做多色体系 |
| 圆角 | 卡片 12px，按钮 8px |
| 间距 | 8px 栅格（8/16/24/32） |
| 字号 | 标题 15-16，正文 13-14，辅助 12 |
| 中文字体 | 系统字体（微软雅黑 / 苹方），不引入网络字体 |
| 卡片比例 | 封面统一 16:10 裁切，避免高度参差 |
| 动效 | 只做两处：卡片进入淡入、保存成功的一次轻微反馈。不做花活 |

## 九、技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 语言 | TypeScript | 类型检查能挡掉大量低级错误；AI 辅助写代码时更不易跑偏 |
| 前端 | React + Vite + Tailwind | 生态最成熟，AI 最熟，出问题好查 |
| 后端 | Node.js 单服务（Hono 或 Express） | 抓取需要服务端（浏览器跨域拿不到别人网页），必须有个轻后端 |
| 数据库 | 云托管 Postgres | 双端一致，不用自己实现同步 |
| 文件存储 | 云对象存储 | 封面、图片、原文件 |
| 抓取 | 服务端解析正文 + 无头浏览器兜底 | 静态页用解析库，动态页才启浏览器 |
| AI | 云端模型 API | 摘要 + 标签 + 描述 |
| 手机端 | **PWA（添加到主屏幕 + Web Share Target）** | 安卓 Chrome 支持把装了的主屏幕网页注册为系统分享目标，**不需要打包 App** |
| 电脑端 | 浏览器直接用；后期 electron-builder 打 exe | Windows 上就能打，无需 Mac |

### 关于双端同步

单人使用，**不做 CRDT、不做离线合并**。云数据库是唯一权威，两端都直连读同一份数据。
本地只做内存缓存，刷新即同步。冲突场景（两台设备同时改同一条）在实践中几乎不存在，用"最后写入赢"即可。

> 这刻意回避了同类产品最容易翻车的地方：同步逻辑。省下的复杂度全部换成功能。

### 关于访问控制（不能省）

后端要上公网（手机要访问），必须有门。

方案：**用云服务自带的账号体系**，登录一次，PWA 保持长期会话。不自建密码系统——重复造轮子且更容易出漏洞。

三条硬要求：

1. 无鉴权的公网知识库，被扫描到就能被人灌内容、烧掉你的 AI 额度。这不是"要不要"的问题。
2. 手机分享冷启动时若会话失效，跳登录，**登录后要回到刚才那条链接**，不能丢。
3. 除登录账号外，服务端还要有基础的写入频率限制，防止意外刷爆。

### 关于手机"一键存"

- 安卓 Chrome 76+ 支持 Web Share Target：PWA 装到主屏后，**出现在系统分享菜单里**
- 需要：HTTPS + manifest 里声明 share_target + 注册 service worker + 用户手动"添加到主屏幕"
- 已知不确定：微信的分享面板可能默认只显示自家渠道，需要点"更多"才进系统分享。**第一版就要实测这条**，若不通，退化为"复制链接 → 打开应用 → 粘贴"

## 十、MVP 范围

### 做（10 项，不多做一项）

9. 手机 PWA 安装 + 分享接收

## 十一、验收标准

第一版做完，用下面这些具体条件检验（不达标就是没做完）：

| # | 条件 |
|---|---|
| V1 | 粘贴一条公众号链接，卡片最终带封面+摘要+标签出现在列表；连续 10 条成功率 ≥ 8 条（**不设时间上限，但必须成功**） |
| V2 | 点保存后，列表**立即**出现占位卡片，界面不被阻塞（不出现全屏 loading） |
| V3 | 存够 500 条后，搜索"按下就出结果"，无感知等待 |
| V4 | 手机上从微信分享一条内容到入库，**≤ 3 次点击** |
| V5 | 任意一条记录，能在详情页看到它的正文或摘要（原链接已 404 也不影响） |
| V6 | 导出的文件包含全部字段与标签关系，结构完整、人可读，且能被将来的导入器直接使用（**MVP 只做导出，不做导入**） |
| V7 | 判错类型时，改一次之后，同来源的同类内容不再判错 |
| V8 | 连续使用一周，**没有一次"必须整理才能继续用"的时刻** |

V8 是最重要的一条。它检验的是这个系统有没有变成"整理负担"。

## 十二、已知风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 公众号反爬 | 抓不到正文，摘要质量下降 | 降级为"链接"类型，保留标题+封面；实测后再定方案 |
| B站/抖音接口变动 | 封面、时长抓不到 | 抓取层做成可替换的适配器，单站点故障不影响其它 |
| 微信分享菜单不显示 PWA | 手机入口体验打折 | 第一版实测；不通则用"复制→粘贴"，或后期打包 APK |
| AI 标签判错 | 需人工修正 | 一键改 + 改动记忆；不追求准确率，只追求改起来便宜 |
| 存了不看 | 库变成黑洞 | 二期必须上随机漫游/回顾；否则功能再多也白做 |
| 云服务免费额度耗尽 | 突然要付费 | 封面图压缩；不默认存视频原文件；导出功能保证随时能走 |
