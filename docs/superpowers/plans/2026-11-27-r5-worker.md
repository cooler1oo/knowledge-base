# R5 worker 实现计划

> **For agentic workers:** 按 task 顺序执行，每个 task 先写失败测试再写实现。
> 步骤用 `- [ ]` 跟踪。

**Goal:** 让 `jobs` 表里的 `fetch` 任务真的被执行——worker 取出任务、调 `kb.extract` 抓取、把结果写回 `items`，失败按指数退避重试，崩溃后能自动恢复。

**Architecture:** worker 是独立进程（不是 api 的一部分），单线程轮询 `jobs` 表。取任务用 `FOR UPDATE SKIP LOCKED` 保证多 worker 不抢同一条。抓取成功后在一个事务里更新 `items` 字段、写 `attachments`、插入下一步任务（`summarize`，图片类同时插 `ocr`）；失败按 `attempts` 指数退避，达 3 次标 `failed`。心跳写 `settings` 表供 `/api/health` 的 `workerOk` 读。

**Tech Stack:** Python 3.13、pg8000.native、kb.extract（R3 已交付）、ParseHub 单例

**Spec:** `docs/tech/2026-11-26-技术方案.md` §6.4（状态机与取任务 SQL）、§4.10（三层降级）

## Global Constraints

- 所有 SQL 留在 `kb/store/`，`kb/worker/` 只调用函数（架构检查强制）
- 抓取层失败永不抛异常，返回 `ExtractOutcome(ok=False, error=...)`（R3 契约）
- **ParseHub 必须复用单例**：实测首次冷启 18.49 秒、复用后 0.83 秒（R3 实测）
- `duration` 单位按平台判：`douyin`/`tiktok` 是毫秒，其余是秒（v9.12）
- 失败重试上限 3 次，退避 `1 分钟 × 2^attempts`
- `running` 状态超过 15 分钟视为崩溃，回退为 `pending`
- 单条任务失败不得中断 worker 循环（记录错误后继续下一条）

## Review Focus

以下五类是方案隐含但单靠「正常路径能跑」测不到的，每条都要有测试钉住：

1. **两个 worker 同时取任务**：必须一个拿到、一个空手，不能双跑同一 job（`SKIP LOCKED` 的正确性）
2. **抓取失败后 `attempts` 与 `run_after` 的变化**：第 1 次失败应回到 `pending` 且 `run_after` 往后推，第 3 次才 `failed`——退避算错会让任务永久卡住或疯狂重试
3. **`running` 卡死恢复**：worker 被 kill 后 15 分钟，任务必须回到 `pending` 而不是永远 `running`
4. **`kind='link'` 的降级条目**：抓不到内容时 `items` 该只更新 `title`/`url`，不该把 `kind` 从原值改成别的、也不该写空的 `props`
5. **媒体写入的 `seq` 与 `role`**：多图必须按顺序落 `attachments.seq`，且 `role` 要过 CHECK 约束（`attachments_role_allowed`）

**Interfaces:**

- Produces: `mark_failed(conn, job_id: int, error: str) -> str`
  返回新的 state：`"pending"`（还会重试）或 `"failed"`（已放弃）

```python
def test_第一次失败退回_pending_并且_run_after_往后推():
    state = jobs_store.mark_failed(conn, job_id=1, error="被风控拦截")
    assert state == "pending"
    assert "run_after = now() + interval" in conn.sql_log

def test_第三次失败标_failed_不再重试():
    """attempts 到 3 必须停，否则坏任务无限重试打爆上游。"""
    conn = FakeConn(attempts_before=2)
    state = jobs_store.mark_failed(conn, job_id=1, error="x")
    assert state == "failed"

def test_失败原因写进_error_列():
    """界面要靠它显示「处理失败，可重试」，空着等于没记。"""
```

- [ ] **Step 2: 跑测试确认失败**

- [ ] **Step 3: 实现 `mark_done` 与 `mark_failed`**

`mark_failed` 用方案 §6.4 的 SQL：`state = CASE WHEN attempts + 1 >= 3 THEN 'failed' ELSE 'pending' END`，
`run_after = now() + (interval '1 minute' * power(2, attempts))`。
`RETURNING state` 拿新状态，不要自己算——两次算术（SQL 一次、Python 一次）必然不一致。

### Task 4: 把抓取结果写回 items（含 attachments）

**Files:**
- Modify: `kb/store/items.py`
- Test: `tests/test_worker_persist.py`

**Interfaces:**
- Produces: `apply_extract(conn, item_id: int, outcome: ExtractOutcome) -> None`
- Consumes: R3 的 `ExtractOutcome`（`ok`/`kind`/`data`/`error`）
- Consumes: `normalize.ExtractResult`（`kind`/`title`/`content_text`/`media`）

**设计要点（写进代码注释）**：
- 成功时：更新 `title`、`content_text`、`props`（`duration_sec` 等）、`kind`；
  按 `media` 顺序插 `attachments`，`seq` 从 0 递增
- 失败时：**只更新 `title`**（若原本为空）与 `props.fetchError`，
  **不改 `kind`**——`kind='link'` 是降级结果，由 R4 入库时已定，抓取失败不该覆盖
- `props` 用 `||` 合并而不是整体覆盖，避免抹掉入库时写入的字段

- [ ] **Step 1: 写失败测试**

```python
def test_抓取成功写入标题正文与时长():
    items_store.apply_extract(conn, 1, outcome_ok)
    assert "content_text" in conn.sql_log
    assert "duration_sec" in conn.sql_log

def test_多图按顺序写_attachments_seq():
    """8 张图必须 seq 0..7，乱序会让详情页图片顺序错乱。"""
    items_store.apply_extract(conn, 1, outcome_image_8)
    assert conn.inserted_seqs == [0,1,2,3,4,5,6,7]

def test_抓取失败不改_kind_只记原因():

    assert "kind" not in conn.sql_log
```

## 执行方式

Task 1–4 是纯 SQL 层，互相依赖弱（1 独立，2/3 依赖 1 的表语义，4 独立于 1–3）。
Task 5 串起前四个。Task 6 是外壳。

建议 **Native** 执行：6 个 task 共约 400 行，接口在计划里已固定，改动集中在两个已有文件
（`jobs.py`、`items.py`）+ 三个新文件。派子代理会因上下文切换成本高于收益。
