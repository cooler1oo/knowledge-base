## 零、先说清比较的前提

**这个 demo 是原型，不是产品。** 没有后端、没有数据库、没有抓取、没有 AI，40 条数据写死在 HTML 里。

所以"差距"必须分三层看，混在一起比会得出错误结论：

| 层 | demo 应不应该体现 | 现状 |
|---|---|---|
| **L1 信息架构**：分几层、怎么组织、页面怎么分 | 应该，这是 demo 的全部意义 | 基本做到 |
| **L2 交互流程**：点下去发生什么、状态怎么变 | 应该，可以模拟 | 做了一部分 |
| **L3 能力实现**：抓取、AI、检索、存储 | 不应该，也做不到 | 0 |

**结论先说**：L1 大约完成 80%，L2 大约 40%，L3 是 0。所以"看起来像产品"和"能用"之间还差一整个后端。

## 二、对 Karakeep 逐条对照（20 项）

选它做主要参照，因为它是唯一同形态、开源、可拆开看的项目。

| # | Karakeep 的能力 | demo 现状 | 差距性质 |
|---|---|---|---|
| 1 | 自动抓标题 / 描述 / 封面 | ❌ 用的是写死的数据 | 后端 |
| 2 | 列表（Lists）+ 协作 | ⚠️ 有"筛子"，无自定义列表；无协作 | 交互 + 定位 |
| 3 | 全文搜索 | ⚠️ 只搜标题/摘要/标签，搜不到正文 | 后端 + 分词 |
| 4 | 语义搜索 | ❌ | 后端 + 向量 |
| 5 | LLM 自动标签 + 摘要 | ⚠️ 演了动画，标签是写死的 | 后端 |
| 6 | 规则引擎（按来源自动归类） | ❌ 只有一条 toast 假装"记住了" | 后端 |
| 7 | OCR（图片文字可搜） | ❌ | 后端 + 模型 |
| 8 | 浏览器插件 | ❌ | 需另做 |
| 9 | 手机 App + 系统分享菜单 | ❌ 未实现 share_target | 需实测 |
| 10 | 移动端离线阅读 | ❌ | 架构 |
| 11 | RSS 自动收录 | ❌ | 后端 |
| 12 | REST API / CLI / agent skills | ❌ | 后端 |
| 13 | 高亮 / 标注 | ❌ | 交互 + 后端 |
| 14 | 整页存档（防链接失效） | ❌ | 后端 + 存储 |
| 15 | yt-dlp 视频归档 | ❌ | 后端 |
| 16 | 批量操作 | ❌ 无多选 | 交互 |
| 17 | SSO | ❌ | 后端 |
| 18 | 暗色模式 | ✅ | — |
| 19 | 导入器（Chrome/Pocket 等） | ❌ | 后端 |

**但要注意**：Karakeep 是"收藏工具"，它的强项全在"收进来 + 不丢"，不在"看"。它在**浏览和回顾上几乎是空白**——没有主页、没有日历、没有时间轴视图、没有每日回顾。这几项恰恰是 demo 已经有的。

## 三、其余四家各取一点

| 产品 | 它的看家本领 | demo 有吗 | 该不该补 |
|---|---|---|---|
| **Cubox** | 微信转发收藏、中文分词搜索、标注漫游、全库问答 | 全无 | 分词要补；微信看实测；问答等有数据 |
| **Eagle** | 颜色筛选、以图找图、重复文件扫描、随机模式 | 只有"随机"（做成了主页推送） | 颜色/以图找图**不建议做**（见第六节） |
| **Readwise** | 每日回顾（间隔重复）、高亮、TTS、键盘操作 | 全无 | **每日回顾最该补**，成本极低 |
| **Capacities** | 类型/属性/标签/查询四积木、Related Content | 四积木做到了 3.5 个，缺"查询可自建" | 查询自建要补 |

## 四、demo 已经领先或做得不一样的三处

不能只列差距，这三处是竞品没有的：

1. **日历视图**：Karakeep / Cubox / Raindrop 都没有"按日期找"的界面（只有时间流）。而"想起哪天看的"是真实需求。
2. **主页随机推送**：Eagle 有"随机模式"，Readwise 有"每日回顾"，但没人把它做成**打开应用的第一屏**。这直接对应"每天随意翻看"。
3. **「没归好类的」筛子**：所有产品都有 AI 打标，但没人给"AI 也没把握的东西"一个固定去处。这是承认"AI 会错"的产品设计。

## 五、改进清单，按投入产出分四档

### T1 不用后端，改界面就能做（半天到两天）

| # | 改进 | 为什么值得 |
|---|---|---|
| 1 | **标签支持两级**（现在只有一级，"B 底 A 面"的证据不完整） | 决定信息架构能否成立 |
| 2 | **筛子可自建 + 可钉到侧栏**（现在写死 3 个） | 这是"场景即入口"能否落地的唯一证据 |
| 3 | **热力图格子可点**（点了直接进那天） | 现在只是装饰，点了没反应 |
| 4 | **卡片多选 + 批量操作条** | 库里超过 200 条后必需 |
| 5 | **键盘导航**（j/k 上下、Enter 打开、Esc 关） | 每天用的人会需要 |
| 6 | **三种空状态**（空库 / 筛选无结果 / 搜索无结果） | 现在只有一种文案 |
| 7 | **处理中 / 失败 / 重试的界面态** | 真实抓取一定失败，得先有界面 |
| 8 | **设置页骨架**（标签管理、规则列表、用量） | 现在完全没有"管理"入口 |
| 9 | **沉浸阅读视图**（详情里切"读全文"） | 存文章却读不了，说不过去 |
| 10 | **首次使用引导** | 空库第一眼最劝退 |

### T2 可以用假数据演（一到两天）

| # | 改进 | 说明 |
|---|---|---|
| 11 | **每日回顾**（每天推 3 条旧的，"X 年前的今天"） | 解"存了不看"的关键，成本最低 |
| 12 | **未读清理**（滑卡片：读 / 归档 / 删） | Cubox 和 Readwise 的做法 |
| 13 | **高亮 / 批注** | 界面搭好，逻辑后补 |
| 14 | **搜索历史 + 把常搜固化成筛子** | 这是"入口"的自然来源 |
| 15 | **合集 / 清单** | 把散的东西聚成一组 |

### T3 必须有后端才有意义

真实抓取、正文解析、封面落地、AI 摘要与标签、OCR、视频字幕、整页快照、中文分词检索、语义检索、去重、导入器、浏览器插件、share_target、导出、账号、备份。

**这一档不是"改进 demo"，是"开工做产品"。**

### T4 不建议做（投入产出比差）

| 功能 | 为什么不做 |
|---|---|
| 颜色筛选 / 以图找图 | 是 Eagle 的垂直领域，需要图像特征提取，对以文字为主的库价值低 |
| 知识图谱 / 双链 | Obsidian 的路，个人库里通常变成好看的装饰，没人真的用 |
| 协作 / 分享 | 单人使用，PRD 已明确排除 |
| 全库问答（RAG） | 现在只有 40 条假数据，问答没有意义。等真攒到 300 条再说 |
| TTS 朗读 | 需求没验证过，且是独立成本 |
| 视频语音转录 | 算力成本高。先只抓字幕（有就用，没有就留链接） |

## 六、我的判断：下一步最该补的三件

不是功能最多的，是**决定这产品能不能立住**的：

### 1. 两级标签（T1-1）
现在侧栏只有一级标签。但整个"B 的底子 + A 的外壳"就是押在"标签能像文件夹一样有层级"上。如果两级做出来看着乱，这个方案就得推翻重来。**这是最大的未验证假设。**

### 2. 筛子可自建（T1-2）
你说过"场景我讲不清，只有具体要做的时候才知道"。所以正确的做法不是现在设计 6 个入口，而是**给你一个能自己攒入口的工具**。筛子可自建，就是那个工具。如果做出来你还是不用，说明"入口"这个方向本身有问题。

### 3. 每日回顾（T2-11）
这是唯一能解决"存了不看"的机制，也是所有竞品里被验证过有效的（Readwise）。成本极低，一个卡片区就够。**没有它，前面所有采集优化都是往黑洞里扔东西。**

这三件都能在 demo 里做，不需要一行后端代码。

---

## 七、一句话总结

**界面骨架已经比 Karakeep 更懂"怎么找回来"，但能力实现是 0。**
下一步不该急着写后端——先把上面三件事验证掉，因为它们是设计假设，不是功能。假设错了，后端写得再好也得推倒。
