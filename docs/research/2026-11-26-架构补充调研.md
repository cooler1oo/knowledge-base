## 二、「什么都能放」的结构问题（本轮最重要）

### 2.1 问题陈述

v8.0 的做法：

```sql
type text NOT NULL CHECK (type IN ('article','image_text','video','image','file','link'))
props jsonb NOT NULL DEFAULT '{}'
files.kind text CHECK (kind IN ('cover','original','snapshot'))
```

三个结构问题：

| 问题 | 后果 |
|---|---|
| 6 个类型是**互斥且封闭**的枚举 | 加第 7 种形态（音频、代码片段、书摘、聊天记录导出）必须改 DDL + 改类型判定代码 |
| `props jsonb` 无 schema | 每种形态的专属字段（视频时长、文章字数、图片宽高）塞在同一个无约束字段里，写错不报错 |
| `files.kind` 只有 3 值，且**「文件」既是 `items.type` 的值、又是 `files` 的附件** | 一个 PDF 到底是 `type='file'` 的内容，还是某条内容的附件？两种身份混在一个模型里，导致 §8.1.1 的媒体白名单漏掉 pdf/zip |

### 2.2 成熟项目的做法：主表 + 按形态分表

karakeep 的 `packages/db/schema.ts`（1419 行）实测结构：

```
bookmarks                     ← 主表：所有形态的共性字段
  id, type("link"|"text"|"asset"), title, summary, note
  taggingStatus / summarizationStatus / embeddingStatus   ← 三个处理状态各自独立
  source("api"|"web"|"extension"|"cli"|"mobile"|"singlefile"|"rss"|"import")
  archived, favourited, createdAt(=lastSavedAt), dbCreatedAt

bookmarkLinks   (id → bookmarks.id, 一对一)   url, title, description, author,
                                              publisher, datePublished, imageUrl,
                                              htmlContent, readerViewStatus, crawlStatus
bookmarkTexts   (id → bookmarks.id, 一对一)   text, sourceUrl
bookmarkAssets  (id → bookmarks.id, 一对一)   assetType("image"|"pdf"), assetId, fileName
assets          (独立表)                      assetType(13 值), size, contentType,
                                              fileName, bookmarkId, userId
```

**关键设计点**（三条可直接借用）：

1. **主表的 `type` 只有 3 值，且它是「内容怎么装的」而非「内容是什么」**。`link` 有 URL、`text` 没 URL、`asset` 靠文件。视频/图文/文章这些**业务分类**不存在主表里，是由抓取结果推导出来的展示层概念。
2. **形态专属字段放各自的子表，不塞 jsonb**。链接的 `crawlStatus`、文本的 `text`、资产的 `assetType` 各自有类型约束。
3. **附件维度独立于内容维度**。`assets.assetType` 有 13 个值（封面、截图、PDF、整页存档、视频、HTML 内容、用户上传、头像、备份…），**PDF 是「一种附件」，不是「一种内容」**。这就是为什么 karakeep 能存 PDF 而不用担心「读不出来」——读取走统一的 asset 出口。

### 2.3 统一媒体模型：ParseHub 的 MediaRef 家族

`src/parsehub/types/media_ref.py`（109 行）实测：

```python
MediaRef      (基类)  url, ext, thumb_url, width, height, backup_urls[]
  ├─ ImageRef      ext="jpg"
  ├─ VideoRef      ext="mp4",  duration
  ├─ MusicRef      ext="m4a",  duration
  ├─ AniRef        ext="gif",  duration
  └─ LivePhotoRef  ext="jpg",  video_url, video_ext, duration=3
```

与 `post.py` 的 `PostType`（`unknown|image|video|multimedia|richtext|music`）配套。

**这套模型的价值**：它把「一条内容带几个媒体、每个媒体是什么」抽成了统一结构，且 `backup_urls[]` 处理了「抖音 CDN 多域名轮换」这个具体问题。本项目的 `items.cover_key` + `files` 两处结构，可以直接对齐成「一条内容 → N 个 MediaRef」的一对多。

### 2.4 三个可选方向（需用户拍板，本轮不定）

| 方案 | 做法 | 加新形态的代价 | 风险 |
|---|---|---|---|
| **A 继承式**（照搬 karakeep） | `items` 主表 + `item_links`/`item_texts`/`item_assets` 三张子表；`type` 收敛为 `link\|text\|asset`；业务分类移到展示层 | 加一张子表，主表不动 | 表从 10 涨到 13+；查询要 join；对非技术背景的维护者，理解成本上升 |
| **B 单表 + 开放 type** | 保留单表，去掉 `type` 的 CHECK，`props` 加 JSON Schema 校验 | 只改 schema 定义 | 约束从 DDL 退到应用层，违反 AGENTS.md 第八节「约束下沉」；类型写错在数据库层查不出来 |
| **C 单表 + 附件维度分离** | `items.type` 保留（作为**展示分类**，允许扩展）；新增 `attachments` 表承载所有媒体/文件；PDF 归 `attachments` 而非 `type` | 加形态只改 `type` 的枚举值 + 展示层 | 改动最小；但「type 到底封不封闭」这个问题被推迟而非解决 |

**本轮结论：不替用户选。** 三个方案对应三种「什么都能放」的理解，需要用户定义边界（见末节待确认项）。

## 三、URL 去重：可直接照搬的实现

linkding 的迁移序列里有 `0046_add_url_normalized_field` → `0051_fix_normalized_url`，说明它在第 46 个迁移才补上这个字段，且补完还要再修一次。这是真实踩坑记录。

### 3.1 字段

```python
url_normalized = models.CharField(blank=True, db_index=True, max_length=2048)
```

独立列 + 索引，**不覆盖原 `url`**（原 URL 保留用于展示与回跳）。

### 3.2 归一化算法（`bookmarks/utils.py` 实测）

```
1. url 去首尾空白，空则返回 ""
2. urlparse 拆解
3. scheme 转小写
4. hostname 转小写；有 port 则拼上；有 user:pass 则拼成 user:pass@host
5. path 去掉所有尾部斜杠
6. query 用 parse_qsl(keep_blank_values=True) 拆开，按 (key, value) 排序后重新 urlencode
7. fragment 原样保留
8. 重新拼接
```

**与本项目的差异必须注意**：这套算法**不处理**中文平台特有的等价形态——抖音的 `v.douyin.com/xxx/` 短链与 `www.douyin.com/video/<id>` 长链是同一内容但字符串不同；微信的 `mp.weixin.qq.com/s?__biz=...&mid=...&idx=...&sn=...` 的 query 顺序变化会被排序解决，但 `&chksm=` 这类追踪参数不会被去掉。

因此照搬 linkding 只能解决「同一 URL 写法不同」，解决不了「短链 vs 长链」。后者需要**抓取后回填规范 URL**：抓完拿到真实内容 ID 后，用平台自己的规范形式（如 `douyin.com/video/{aweme_id}`）作为第二去重键。
