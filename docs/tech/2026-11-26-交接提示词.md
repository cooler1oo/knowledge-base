## 你的任务

你接手一个**已经进行到第 8 版**的技术方案设计工作。本会话只做设计，**不施工**。

项目：个人知识库（单人自用，个人非商用）。当前状态：技术方案 `v8.0` 已写完并按独立审计修订，**等你复检或推进**。

## 先做这三件事，再开口

1. 读 `AGENTS.md`（项目硬规矩，尤其第八节「工程约束」）
2. 读 `docs/tech/2026-11-26-技术方案.md`（1538 行，本次工作主体）
3. 读 `deliverables/engineering-assurance/code-review-tech-plan-v7-2026-11-26.md`（35 条审计意见，v8.0 就是按它改的）

**不要**先读 PRD 和设计文档再回头读技术方案，会浪费上下文。技术方案 §0 有摘要，够你用。

## 项目是什么

一台**联想 Y900 13 平板**（8GB+6GB / 256GB / Android 14）当常驻服务端，跑 Termux + proot Debian 13；手机装 APK 负责系统分享入口；电脑用浏览器访问。三端通过 **Tailscale** 组网，不注册域名、不备案、不暴露公网。

核心链路：手机分享一条抖音 → 平板抓取（标题/封面/原图或原视频/时长/作者/发布时间）→ AI 出摘要与标签 → 存 Postgres → Meilisearch 建索引 → 列表出现卡片。

## 最该关注的六件事（按优先级）

### 1. G0' 关卡没跑过——这是最大的未验证风险

`§10.1` 列了 8 步真机验证。**其中 G0'-2（Python 3.12 可用）与 G0'-3（`pip install parsehub` 成功）是所有后续的前提。** 不过则 §4 的整套抓取方案要切到 §4.9 的自写 CDP（那条路只需 Python 3.10+）。

⚠️ **这些是设计结论，不是实测。** 本会话没有设备，一步都没跑过。

### 2. 审计的 6 项阻塞，修了 5 项，第 6 项就是这个 G0'

已修的 5 项：Python 版本冲突、Postgres 18 不存在、媒体无读取端点、自签证书 APK 打不开、首账号无法创建。

### 3. 有一处我可能判断错了，你要复核

`signerpy` 是 parsehub 的依赖，**只有 sdist 没有轮子**。我判断「它是纯 Python 包，`setup.py` 构建不需要 gcc」，**这个判断没实跑验证**。若你要严谨，先验这一条。

### 4. 三处主动取舍可以推翻

`§7.2`：Starlette 代替 FastAPI、pg8000 代替 psycopg、bcrypt 代替 argon2。**这三条不是被迫的**——实测那三个包都有 aarch64 轮子。选保守组合的理由是「减少 G0' 可能失败的面」。G0' 通过后可以换回去。

### 5. 抖音的先天局限（不是 bug）

抖音可读文本只有标题一句，所以 **AI 摘要只能产出「标题的同义改写」**，检索主战场是标题不是正文。这个质量是否可接受，用户在 §13 的 Q3 里已答「接受」。

### 6. 三个问题等用户拍板

见 `§13`：Q1 要不要 ASR、Q2 原视频全存还是按需、Q3 摘要质量可接受吗（已答接受）。

## 本项目的「机器约束」比文档约束优先

仓库里已经装了自动检查，**改动必须过它们**：

```bash
python -m tools.doc_checks --all --cross-refs   # 文档规则（含复用调研表七列）
python -m pytest -q                              # 47 个测试
ruff check . && ruff format --check .            # 代码风格
```

`docs/tech/` 下的文档由 `tools/doc_checks/reuse.py` 强制：必须有 `## 复用调研` 章节，七列表 `组件 | 候选 | 星数 | 许可 | 结论 | 运行环境 | 理由`，结论须在「复用/参考/不采用/自写」内，理由禁敷衍词，复用项必须写运行环境。

**提交前钩子会自动跑这些。别用 `--no-verify` 绕过。**

## 必须遵守的工作方式（来自项目 AGENTS.md 与用户要求）

1. **动手三问**：根因是什么、证据是什么、用哪个工具 —— 缺一项不动手
2. **不确定就标**：未经验证写 ⚠️ 并给验证方法，不许用「应该/大概/理论上/通常」当结论
3. **禁止搪塞句**：「建议后续考虑」「可酌情优化」这类不许写
4. **不擅自扩缩需求**：发现矛盾写进「待确认问题」，不自行改需求
5. **测试与验证是核心，不是收尾**：判断「做完」看检查输出，不看主观感觉
6. **注释从简**：只写为什么，不复述代码在做什么
7. **每轮汇报三态**：✅ 已验证（贴命令输出）/ ⚠️ 未验证（说明原因）/ ❌ 失败（报错原文 + 已试方案）
8. **技术前必做开源调研**：先查 GitHub 有没有能复用的，再决定自写。这条已机器化，不写复用调研表就提交不了

## 已知的坑（踩过了，别重踩）

| 坑 | 后果 | 正确做法 |
|---|---|---|
| `git diff --name-only` 不加 `-z` | **中文路径被转义，检查永远静默全绿** | 必须 `-z` 按 NUL 读 |
| 命令以 `cd` 开头 | Stop gate 不认作验证，判「没跑验证」 | 把 `python -m pytest` 放命令首位 |
| ruff format 会格式化 Markdown 里的 Python 代码块 | 文档被改乱 | `pyproject.toml` 已配 `extend-exclude = ["docs/**"]` |
| 只看检查「通过」不验它真的解析了 | 表格解析失败也显示通过 | 用 `parse_audit()` 断言行数 > 0 |
| 用「大概率/通常」描述外部事实 | 被禁用词规则拦下 | 改成可核验的判断标准或标 ⚠️ |
| 反向测试注入未确认字符串精确匹配 | 「没拦住」其实是注入失败 | 先 `assert old in text` |
