## 3. 内容模型决策（D1–D3、D6 的合并解法）

### 3.1 三种范式的实证对比

| 范式 | 代表项目 | 结构 | 加新形态的代价 | 检索能力 | 本项目适用性 |
|---|---|---|---|---|---|
| **继承式**（Class Table Inheritance） | karakeep-app/karakeep（30862★） | `bookmarks`（type 3 值）+ `bookmarkLinks`/`bookmarkTexts`/`bookmarkAssets` 各一张一对一子表 | 加一张子表，主表不动 | 各子表字段有类型约束，按字段查快 | 形态**有限且稳定**时最优；本项目「无边界」要求下，子表会持续增加 |
| **EAV**（实体-属性-值） | TriliumNext/Trilium（39097★） | `notes(id, title, type TEXT, mime, blobId)` + `attributes(noteId, type, name, value TEXT, isInheritable)` | 插一行数据，零 DDL | 值全是 TEXT，比较退化为字典序；多属性过滤需多次自连接 | 适合「用户运行时定义字段」；本项目字段由开发者定义，用不上这个灵活性 |
| **JSONB + 强约束** | 无单一代表项目，是 PostgreSQL 官方推荐做法 | 核心字段做列，长尾字段进 `jsonb`，配 CHECK + 生成列 + GIN | 改 CHECK 表达式，**不改表结构** | 生成列可建索引；GIN 支持包含查询；`jsonb_typeof` 可强校验 | 形态**无边界**且需要类型校验时最优 |

**关键实证（来自公开基准与生产迁移记录）**：

- EAV 的代价：一属性一行（行数约 3 倍、存储约 3.5 倍），每次过滤需 pivot 或自连接；`value` 存 TEXT 导致 `8 > 16` 为真（字典序）。Benchling 曾用 EAV，2021 年因摄取性能下降**迁移到 JSONB**，理由正是「稀疏行 + 元数据开销 + 读取需跨多行」。
- JSONB 的代价：默认无 per-key 统计（规划器估算 100 行而实际匹配 4000）；更新整文档；无外键。**缓解手段**：表达式索引（同时给规划器统计）、GIN 索引、生成列提升热键、CHECK 约束校验类型。
- 决策规则（业界共识）：**凡要过滤/排序/连接的属性提升为真实列；只展示、少查询的进 JSONB；EAV 只在「终端用户运行时定义字段」时才用**。

### 3.2 本项目的选择：JSONB + 强约束（不是「最轻」，是「最优」）

**理由三条，逐条对本项目**：

1. **形态无边界 ⇒ 排除继承式**。继承式在形态固定时最优（karakeep 用它装了 link/text/asset 三种），但用户要求「不固定类型」。每加一种形态就加一张表，表的数量随形态线性增长，迁移与 join 复杂度同步增长。
2. **字段由开发者定义 ⇒ 排除 EAV**。EAV 的唯一优势是「终端用户运行时加字段」，本项目没有这个需求（字段是我们自己定的）。却要付「值退化为 TEXT、需自连接、行数 3 倍」的全部代价。且本项目**核心动作是模糊搜索**，EAV 的 TEXT 比较正好伤在这里。
3. **「什么都查不了」必须修 ⇒ 选 JSONB 但补全四个机制**。现方案的 `props jsonb` 只做到「能存」，没做到「能查、能校验」。补全后即达最优：

```sql
-- 内容主体：核心字段仍是真实列（这些是确定会过滤/排序的）
CREATE TABLE IF NOT EXISTS items (
  id            bigserial PRIMARY KEY,
  kind          text NOT NULL,              -- 可扩展，无 CHECK 枚举（见下）
  url           text,                        -- 可空：纯文字/上传文件无 URL
  url_norm      text,                        -- 去重键（N3）
  title         text NOT NULL DEFAULT '',
  author        text,
  source_domain text NOT NULL DEFAULT '',
  summary       text,
  content_text  text,                        -- 正文/字幕
  ocr_text      text,                        -- 图片 OCR（N17 要求独立，不与 content_text 混用）
  primary_media bigint,                      -- 主视觉（封面/首图），指向 attachments
  props         jsonb NOT NULL DEFAULT '{}', -- 长尾属性，带校验（见下）
  saved_at      timestamptz NOT NULL DEFAULT now(),
  published_at  timestamptz,
  status        text NOT NULL DEFAULT 'unread',
  deleted_at    timestamptz,
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now(),
  -- 核心校验：kind 必须非空且是小写标识符（格式约束，不是枚举约束）
  CONSTRAINT items_kind_format CHECK (kind ~ '^[a-z][a-z0-9_]{0,31}$'),
  -- props 必须是对象，不是数组/标量
  CONSTRAINT items_props_is_object CHECK (jsonb_typeof(props) = 'object')
);

-- 生成列：把「经常按它筛」的长尾属性提升为可索引
ALTER TABLE items
  ADD COLUMN duration_sec int GENERATED ALWAYS AS ((props->>'duration_sec')::int) STORED;

-- 索引三件套
CREATE UNIQUE INDEX IF NOT EXISTS items_url_norm_uniq
  ON items (url_norm) WHERE url_norm IS NOT NULL AND deleted_at IS NULL;
CREATE INDEX IF NOT EXISTS items_props_gin ON items USING gin (props jsonb_path_ops);
CREATE INDEX IF NOT EXISTS items_kind_saved ON items (kind, saved_at DESC);
```

**为什么 `kind` 不加 CHECK 枚举**：这是「不固定类型」的唯一实现方式。但仍加**格式约束**（小写标识符），防止写入脏值；合法值集合由 `item_kinds` 表登记，应用层校验，DDL 不锁死。这不是「放弃约束」，是「把枚举约束换成格式约束 + 注册表」，加新类型只需插一行。

```sql
-- 类型注册表：加新形态 = 插一行，不改任何表结构
CREATE TABLE IF NOT EXISTS item_kinds (
  kind         text PRIMARY KEY REFERENCES items(kind) ON DELETE RESTRICT,
  display_name text NOT NULL,
  is_preset    boolean NOT NULL DEFAULT false,
  sort_order   int NOT NULL DEFAULT 0,
  created_at   timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT item_kinds_kind_format CHECK (kind ~ '^[a-z][a-z0-9_]{0,31}$')
);
```

### 3.3 附件维度（D3、D6 一并解决）

```sql
-- 附件：任何形态内容都可挂任意多个（图片/视频/PDF/压缩包/整页快照）
CREATE TABLE IF NOT EXISTS attachments (
  id          bigserial PRIMARY KEY,
  item_id     bigint NOT NULL REFERENCES items(id) ON DELETE CASCADE,
  role        text NOT NULL,              -- cover | video | image | doc | snapshot | audio
  storage_key text NOT NULL,
  mime        text NOT NULL,              -- 真实 MIME，读取端点按它判类型
  size_bytes  bigint NOT NULL DEFAULT 0,
  width       int, height int, duration_sec int,
  sha256      text NOT NULL,              -- 备份恢复要逐个比对（B3）
  sort_order  int NOT NULL DEFAULT 0,
  created_at  timestamptz NOT NULL DEFAULT now(),
  -- 附件路径只允许这些 mime 前缀：解决 D6「PDF 存得进读不出」
  CONSTRAINT attachments_mime_allowed CHECK (
    mime ~ '^(image/|video/|audio/|application/(pdf|zip|msword|vnd\.|octet-stream)|text/)'
  )
);
CREATE INDEX IF NOT EXISTS attachments_item ON attachments (item_id, sort_order);
CREATE UNIQUE INDEX IF NOT EXISTS attachments_key_uniq ON attachments (storage_key);
```

**D6 的解法**：读取端点不再用「文件扩展名白名单」（`\.(webp|jpg|png|mp4|html)$` 这种写法必然漏），改为**按 `attachments.mime` 查表放行**。mime 是入库时校验过的，白名单在 DDL 里，不在 URL 正则里。这样加任何新格式只需改一行 CHECK，不需要同步改两个地方。

### 3.4 该方案的取舍代价（明写，不藏）

| 代价 | 具体 | 为什么接受 |
|---|---|---|
| `kind` 失去 DDL 级枚举 | 写入 `kind='foo'` 不会在 DB 层被拒（格式对就通过），要靠应用层查 `item_kinds` | 这是「不固定类型」的必付成本。用注册表 + 外键把风险降到「能查出来」而不是「能写进去」 |
| `props` 键无 schema | 不同 kind 的 props 结构不同，DB 不知道 | 用 `CHECK (jsonb_typeof(...))` 管住顶层类型；每 kind 的字段校验放应用层（Pydantic 模型，一个 kind 一个模型） |
| 生成列需显式维护 | 新增热键要 `ALTER TABLE ADD COLUMN ... GENERATED` | 这是「热键提升为列」的正常操作，一次一条；比 EAV 的自连接便宜得多 |
| 表数从 10 涨到 12 | `items` + `item_kinds` + `attachments`（原 `files` 表被 `attachments` 取代） | 净增 2 张。相对继承式（每形态一张）是常数级，不随形态增长 |

## 5. 重制时的执行顺序（依赖关系，不能乱）

```
第 1 步：定 Python 版本（B1）           ← 独立，先做，因为它决定 G0' 判据
第 2 步：重写 §6 数据模型（§3 决策）     ← 依赖用户「不固定类型」已定
第 3 步：按新模型重写 §6.1 DDL + 迁移   ← 含 R1/R4/R5
第 4 步：重写 §8 接口（媒体读取按 mime） ← 含 D5/D6
第 5 步：重写 §11 测试（按形态配比）     ← 含 B4/D10/D11/D12
第 6 步：重写附录 A 落点               ← 依赖第 2–5 步的新章节号
第 7 步：全文回扫数字与交叉引用         ← R7/R8/R9/R16
```

**为什么第 2 步必须在第 3 步前**：数据模型一改，`items`/`files` 的所有 DDL、所有端点契约、所有测试断言都要跟着改。先改 DDL 再改模型等于改两遍。
