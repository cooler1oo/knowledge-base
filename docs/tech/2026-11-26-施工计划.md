## 0. 这份计划解决什么

技术方案 v9.0 回答了「做成什么样」。它回答不了三件事：

1. **按什么顺序做** —— 方案 §10 的 G0'–G6 是验证关卡，不是施工顺序
2. **每轮交付什么** —— PRD §8 有 M0–M3 四个阶段，但方案里没有映射（实测：`里程碑` 0 次、`分期` 0 次）
3. **会话之间怎么交接** —— 实测：`交接` 0 次

本计划补这三件事，并且**只补这三件事**。技术细节一律指向方案，不复制。

## 1. 施工形态的硬约束

| 约束 | 内容 | 后果 |
|---|---|---|
| S1 | **一个轮次 = 一个独立会话** | 每轮必须自带交接包，不依赖上一轮的记忆 |
| S2 | **每轮有独立可验收产出** | 不允许「本轮铺地基，下轮才看得见」 |
| S3 | **决策一旦偏离技术方案，必须回写方案并升版** | 不允许「代码是A、文档写B」 |
| S4 | **每个最小验收单元一个 commit** | AGENTS.md §7 只有「每次改动后必须 commit」，本计划补粒度 |
| S5 | **禁止跨越轮次边界改动** | 每轮只能改「本轮文件清单」内的文件 |
| S6 | **技术方案不封死** | 施工发现更优做法 → 改方案 → 升版 → 改计划，三者同步 |

### 1.1 commit 粒度（对 S4 的定义）

AGENTS.md §7 写「每次改动完成后，都必须创建一个对应的 Git commit」。本计划把它具体化为：

| 规则 | 内容 |
|---|---|
| 粒度 | **每个可独立验收的最小单元一个 commit**（一个 Task，或一个 Task 内的一组 Step） |
| message 必含 | ① 做了什么 ② 本轮判据是什么 ③ 验证命令 |
| 禁止 | 一个 commit 混两件事；`--no-verify` 绕过钩子 |
| 每个 commit 后 | 必须能跑过 `python -m pytest -q` 与 `python -m tools.doc_checks --all` |

**为什么这么定**：施工阶段最贵的错误是「改了一堆，出问题不知道回滚到哪」。粒度细 + message 带判据，回滚与追因成本最低。

## 2. 架构：分层骨架 + 功能切片

### 2.1 问题

技术方案 §7.5 的目录是**按技术层切**的：

```
store/  extract/  ai/  api/  worker/  web/
```

这个切法对「架构约束」是对的（三条 AST 边界靠它成立），但对「多会话施工」有一个真问题：

> 做「存一条抖音」这一个功能，要同时改 `extract/`+`ai/`+`store/`+`api/`+`worker/` 五个包。每个会话都在这五个包里各改一点，**会话之间会互相踩**。

### 2.2 解法：两个维度并用

| 维度 | 用途 | 不动 |
|---|---|---|
| **技术分层** | 架构约束（谁能 import 谁、谁能写库） | 保持方案 §7.5 原样 |
| **功能切片** | 会话边界（本轮改哪些文件） | 新增：每轮声明精确文件清单 |

**具体做法**：目录仍按层，但**施工按功能切轮**，每轮的文件清单精确到单个 `.py`。这样：

- 架构约束不破（层边界还在）
- 会话不打架（每轮只碰清单内文件）
- 交接清晰（下一轮知道哪些文件已被谁改过）

### 2.3 每轮的文件清单格式

每轮必须列出三类文件，不多不少：

```markdown
**本轮可改**（新增或修改，共 N 个文件）
- Create: kb/store/xxx.py
- Modify: kb/api/app.py:12-30

**本轮只读**（需要参考但不许改）
- docs/tech/2026-11-26-技术方案.md §6.2

**本轮禁止碰**
- kb/extract/（下一轮才建）
```

## 3. 轮次总览

### 3.1 「先 MVP 后加功能」的落地

PRD 的四阶段与技术方案的技术关卡是两套编号，本计划把它们对齐：

| 轮次 | 会话 | 对应 PRD 阶段 | 对应技术关卡 | 交付物 | 可验收产出 |
|---|---|---|---|---|---|
| **R0** | 部署验证 | M0 前置 | **G0' 全 8 步** | 一份 G0' 实测报告 | 平板上四服务能起来、重启能自恢复 |
| **R1** | 数据层骨架 | M0 骨架 | —— | 迁移脚本 + store 基础 | 12 张表在真库建出来；迁移可重入 |
| **R2** | 首个可运行服务 | M0 骨架 | G1 | api 骨架 + 健康检查 + 登录 | 手机浏览器能打开并登录 |
| **R3** | 抓取层 | M1 能存 | G2c | extract + 三层降级 | 命令行能抓到一条抖音的完整元数据 |
| **R4** | 入库与队列 | M1 能存 | —— | items/attachments/jobs + worker | 存一条链接，卡片出现在列表 |
| **R5** | AI 层 | M1 能存 | —— | 摘要 + 标签 + 额度 | 卡片自动补上摘要与 1–3 标签（**M1b 达标**） |
| **R6** | 检索 | M2 能找 | G3、G4 | Meilisearch + index 步 | 凭片段能搜到 |
| **R7** | 组织 | M2 能找 | —— | 标签树 + 筛子 + 日期视图 | 凭标签能点进去 |
| **R8** | 手机入口 | M1 能存 | —— | APK + 分享桥 | 从抖音分享 ≤3 次点击入库（**V4 达标**） |
| **R9** | 运维闭环 | M0/M3 | G5、G6 | 备份 + 告警 + 导出 | 备份能恢复；运行 72h 不掉 |

**R0 是唯一的例外**：它不是写代码，是拿平板实测。**它不通过，R1 之后全部悬空**——因为若 Postgres 在 proot 起不来要换 SQLite，§6 的 12 张表要重做。

### 3.2 轮次依赖图

```
R0 (G0' 部署验证)
 └─> R1 (数据层)  ← 依赖 R0 的 Postgres 结论
      └─> R2 (api 骨架 + 登录)
           ├─> R4 (入库 + 队列)  ← 依赖 R2 的鉴权 + R1 的表
           │    └─> R5 (AI)  ← 依赖 R4 的 jobs 状态机
           │         └─> R6 (检索)  ← 依赖 R5 的 summary/tags 字段
           │              └─> R7 (组织)
           └─> R3 (抓取层)  ← 只依赖 R0 的 Python 环境，不依赖 R2
                └─> R4 用 R3 产出的 ExtractResult
R8 (APK)     ← 依赖 R2 的登录 + R4 的入库端点
R9 (运维)    ← 依赖 R4/R6 的服务全在
```

**可以并行的两处**（若你有余力开两个会话）：
- R3（抓取层）与 R2（api 骨架）互不依赖，可并行
- R7（组织）与 R6（检索）后半段可交错，但建议串行以免 Meilisearch 索引反复改

### 3.3 每轮的固定产出（交接包）

每个会话结束前必须留下这四样，写在 `deliverables/construction/R{n}-{名称}.md`：

| # | 内容 | 给谁看 |
|---|---|---|
| 1 | **本轮实测输出**（验收命令 + 原始输出） | 下轮 + 人 |
| 2 | **与设计的偏离清单**（哪一节改了、为什么、方案是否已升版） | 下轮 + 人 |
| 3 | **下一轮的已知坑**（本轮踩过什么、别重踩） | 下轮 |
| 4 | **未完成项**（本轮没做完的，明确标） | 人 |

**为什么强制第 2 项**：这份 v9 方案本身就是因为上一会话「结论下太早、没回写」才重制的。不设这道闸，施工阶段会重演。

## 6. R0：部署验证轮（G0' 八步）

> **本轮不写产品代码。** 本轮的唯一产出是「平板上这套环境到底能不能立起来」的实测结论。
>
> **本轮是人机协作**：命令要你在平板上敲，AI 给命令与判据、读你贴回的输出、写结论报告。

### 6.1 本轮为什么必须第一个做

技术方案 §10.1 的 8 步一步都没跑过。而其中两步会**推翻设计**：

| 步骤 | 若失败 | 后果 |
|---|---|---|
| G0'-4 Postgres 起不来 | 换 SQLite | **§6 的 12 张表全部重做**（失去 `jsonb`、GIN、生成列、部分 CHECK）；R1 及之后全部重写 |
| G0'-3 parsehub 装不上 | 切 §4.9 自写 CDP | 需 Chromium 约 400MB；§2.5 内存预算重算；§4 整节改写 |

**所以先跑 R0，拿到结论再写 R1。** 这就是本计划 §7 D2 的建议。

### 6.2 本轮可改 / 只读 / 禁止碰

**本轮可改**
- Create: `deliverables/construction/R0-部署验证.md`（本轮的实测报告）

**本轮只读**
- `docs/tech/2026-11-26-技术方案.md` §2.2、§2.4、§2.5、§7.1、§7.3、§10.1

**本轮禁止碰**
- `docs/tech/2026-11-26-技术方案.md`（**除非 G0' 失败需要回写**，见 §6.6）
- `tools/`、`tests/`、任何 `kb/` 下的代码（本轮还没有代码）

### 6.3 八步的执行细则

> 每一步都给：**命令** / **通过判据** / **失败怎么办**。你只需照做并把输出贴回来。

#### G0'-1 proot Debian 13 能装上并进得去

```bash
# 在 Termux 里
pkg update && pkg install proot-distro
proot-distro install debian   # 装的是 Debian 13（trixie）
proot-distro login debian
cat /etc/debian_version
```

| 项 | 内容 |
|---|---|
| 通过判据 | `cat /etc/debian_version` 输出以 `13.` 开头 |
| 若输出 12.x | `proot-distro` 版本过旧，`pkg upgrade proot-distro` 后重装 |
| 失败怎么办 | **不用 pyenv 编译 Python**（方案 §7.1 已删这条路，因为 Debian 13 自带 3.13） |

#### G0'-2 Python 版本

```bash
# proot 内
python3 -V
apt-cache policy python3 | head -5
```

| 项 | 内容 |
|---|---|
| 通过判据 | `python3 -V` 输出 `Python 3.13.x` |
| 查证依据 | Debian 13 的 `python3` 包 = `3.13.5-2+deb13u5`（技术方案 §7.1 C4） |
| 若低于 3.12 | 先 `apt update`，再 `apt install python3 python3-venv python3-pip` |

#### G0'-3 装 parsehub


#### G0'-4 Postgres 17 能起来

```bash
apt install -y postgresql-17
# 关键：改共享内存策略（方案 §7.3）
PGVER=$(ls /etc/postgresql)
echo "shared_memory_type = mmap"           >> /etc/postgresql/$PGVER/main/postgresql.conf
echo "dynamic_shared_memory_type = posix"  >> /etc/postgresql/$PGVER/main/postgresql.conf
echo "max_connections = 20"                >> /etc/postgresql/$PGVER/main/postgresql.conf
echo "shared_buffers = 128MB"              >> /etc/postgresql/$PGVER/main/postgresql.conf
pg_ctlcluster $PGVER main start
pg_isready
```

| 项 | 内容 |
|---|---|
| 通过判据 | `pg_isready` 输出 `accepting connections` |
| 若报 System V 共享内存错 | 把 `dynamic_shared_memory_type` 改成 `mmap` 再试一次 |
| 若两次都失败 | **这是设计级问题，停手报我**。退路是 SQLite，但会让 §6 全部重做 |
| 要记录的数字 | `psql -c "SHOW shared_memory_type"` 的返回值；`psql -c "SELECT pg_size_pretty(pg_database_size('postgres'))"` |
