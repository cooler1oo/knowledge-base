## 0. 一页摘要

### 0.1 系统是什么

一台**联想 Y900 13 平板**（8GB+6GB / 256GB）当常驻服务端，跑 Termux + proot Debian；手机装 APK 负责系统分享入口；电脑用浏览器访问。三端通过 **Tailscale** 组网，不需要域名、不需要备案、不暴露公网。

**核心链路**：手机分享一条抖音 → 平板抓取（标题/封面/原图或原视频/时长/作者/发布时间）→ AI 出摘要与标签 → 存入 Postgres → Meilisearch 建索引 → 列表里出现卡片。

### 0.2 与技术选型相关的决定

| # | 决定 | 一句话理由 | 依据档位 | 详见 |
|---|---|---|---|---|

## 1. 约束（方案必须满足的条件）

| # | 约束 | 对设计的强制影响 |
|---|---|---|
| C1 | 单人自用，无协作、无权限体系 | 不做多用户、不做 RBAC、不做 CRDT；冲突用后写覆盖 |
| C2 | 只有 Windows + 安卓，无 Mac / 无 iPhone | 不考虑 iOS；APK 侧载，不上应用商店 |
| C3 | 非技术背景，出问题要能靠 AI 修 | 组件越少越好；不引入需要人工解三方合并的技术债（这条否决了 fork karakeep） |
| C4 | 成本几元到几十元/月 | 硬件用现有平板，零新增；AI 按量，必须有月度上限 |
| C5 | **平板持续在线**（用电池，不受宿舍断电影响） | 服务可常驻平板；断电只影响电脑 |
| C6 | 不注册域名、不备案 | Tailscale 组网；证书走 Tailscale `ts.net`（真证书，不用自签，见 §10.3） |
| C7 | **主力内容是抖音**（视频 + 图文；文章极少） | 抓取是必需项而非增强项；抖音抓不通则整个产品不成立 |
| C8 | 能复用就别造 | 每个技术实现前必须做开源调研，由 `tools/doc_checks/reuse.py` 强制 |
| C9 | 本会话只设计，不施工 | 本文不含执行动作 |

**C7 的推论（必须写清）**：抖音是唯一主力来源，因此它的抓取质量决定了产品的及格线。而实测显示抖音的**可读文本只有标题一句**——这意味着检索主要靠**标题 + 封面 + 时间**，而不是正文语义。这一点在设计检索与 UI 时必须体现（§8.2）。

### 2.1 为什么是 proot Debian 而不是 Termux 原生

| 环境 | libc | 能装 ParseHub 吗 | 结论 |
|---|---|---|---|
| Termux 原生 | bionic | ❌ 多个 C 扩展（opencv / cryptography / curl-cffi）无 bionic 轮子 | 不可用 |
| **proot Debian** | glibc | ✅ manylinux aarch64 轮子可直接用 | **采用** |

**代价（必须写清）**：

| 代价 | 量级 | 缓解 |
|---|---|---|
| 磁盘 | Debian rootfs 约 400MB + 依赖约 1GB ≈ 1.4GB | 256GB 可忽略 |
| 内存 | proot 本身约 50MB 额外开销 | 可忽略 |
| 性能 | proot 用 ptrace 拦截系统调用，IO 密集型约慢 5–15% | 推断，未实测（§12.1 推断档） |
| 保活 | Termux 被 Android 杀则整条链路中断 | 四道保险（§2.3） |

### 2.2 端口与可达性

| 服务 | 监听 | 谁能访问 |
|---|---|---|
| Caddy | **`tailscale0` 的 100.x 地址 `:8443`** | 仅 Tailscale 网段 |
| api | `127.0.0.1:8000` | 仅本机（Caddy 反代） |
| meilisearch | `127.0.0.1:7700` | 仅本机 |
| postgres | `127.0.0.1:5432` | 仅本机 |

**为什么不用 80/443**：Android 非 root 无法绑定 1024 以下端口。8443 是唯一现实选择，代价是 URL 带端口号——对 APK 无感（地址写死在应用内），只在电脑浏览器上手输一次。

**为什么绑 `tailscale0` 而不是 `0.0.0.0`**：`0.0.0.0` 会同时监听平板所连 WiFi 的局域网地址，同网段设备（宿舍/图书馆的其他人）可通过 `平板局域网IP:8443` 访问登录页。绑 `tailscale0` 让防火墙层面就不可能被非 Tailscale 设备触及。

### 2.3 保活：四道保险（缺一不可）

| # | 措施 | 不做会怎样 |
|---|---|---|
| 1 | `termux-wake-lock` 常驻，前台通知不可划掉 | 息屏 10 分钟后进程被冻结 |
| 2 | Termux 电池优化设为「不受限制」 | 系统在低电量时优先杀它 |
| 3 | 装 Termux:Boot 并手动打开一次 | 重启后不自启，必须手动敲命令 |
| 4 | **proot Debian 内的 `supervisord` 守护 api / worker / meilisearch / postgres** | 单个进程崩了不会自己起来 |

⚠️ **第 4 条在 v7.0 是错的**：原文写 `termux-services`（runit）守护 api/worker，但 api/worker 跑在 **proot Debian 内**，而 `termux-services` 是 Termux（bionic）侧的包，proot 内既装不上也管不到。proot 内也没有 systemd（无 PID 1 命名空间）。**正确做法是用 Debian 源里的 `supervisor`**，四张 `[program:]` 配置，`autostart=true`。

⚠️ **联想 ZUI 的后台管理比原生安卓更激进**，这四道能否扛住必须真机验证（G6）。**若 G6 反复失败，结论是「这台设备不适合当主机」，换 T3 年付 VPS（约 ¥10/月），不要继续调设置。**

### 2.4 Postgres 在 proot 下必须改的两个参数

proot 提供 System V IPC 与 POSIX 共享内存的**模拟**（`proot-distro` 的 `--no-sysvipc` 开关反证了默认开启模拟），但模拟层不完整，Postgres 默认的 `dynamic_shared_memory_type=posix` 在部分 proot 版本下会启动失败。

**启动前必须写入 `postgresql.conf`**：

```ini
shared_memory_type = mmap              # 绕开 System V 共享内存
dynamic_shared_memory_type = posix     # 若失败改为 mmap
max_connections = 20                   # 单用户不需要默认 100
shared_buffers = 128MB                 # 8GB 设备上的保守值
```

⚠️ **这三行必须在 G0' 里实测**。若 `shared_memory_type=mmap` 仍启动失败，退路是改用 SQLite（见 §12.2 A2）——但那会连带影响 §6 的 DDL（`bigserial`、`jsonb`、触发器语法都要改），代价不小。

### 2.5 内存预算（8GB 平板）

v7.0 从未算过这笔账，而它决定了四个服务能否共存。

| 进程 | 预估常驻 | 依据 |
|---|---|---|
| Android 系统 | 2.0–3.0 GB | 推断（Y900 13 实际占用未测） |
| proot Debian 基础 | 0.05 GB | 推断 |
| Postgres 17 | 0.15–0.25 GB | `shared_buffers=128MB` + 工作内存 |
| Meilisearch | 0.20–0.50 GB | 官方无明确下限；索引期峰值更高 ⚠️ |
| api（Starlette） | 0.08–0.12 GB | uvicorn 单 worker |
| worker（抓取 + AI） | 0.15–0.40 GB | 抓取时含 opencv/PIL 加载 |
| **合计** | **2.6–4.3 GB** | 8GB 物理内存下留 3.7–5.4GB 余量 |

**结论：能跑，但余量不宽裕。** 索引高峰期（Meilisearch + worker 同时吃内存）是最危险时刻，必须真机实测（G0'）。若超限，第一刀砍 Meilisearch（降级到 Postgres ILIKE，见 §8.2 的 L3）。

### 4.1 结论：用 ParseHub，不自写

`z-mio/ParseHub`（206★，MIT，2026-11-21 仍在更新）是 Python 社交媒体聚合解析库，**支持抖音视频与图文，且已处理完反爬细节**。

| 项目 | 自写 CDP 方案 | ParseHub |
|---|---|---|
| 代码量 | 约 120 行（CDP 连接、等待、注入 JS、下载） | **3 行** |
| 视频标题 | ✅ | ✅ 一致 |

### 4.9 退路：自写 CDP + `_ROUTER_DATA`

**只在 G2c 失败时启用。** 核心原则：**数据从 `window._ROUTER_DATA` 取，不从 DOM 取**——DOM 会掺入评论区与相关推荐。

```python
ROUTER_JS = r"""
(() => {
  const findAweme = (o, depth) => {
    if (depth > 8 || !o || typeof o !== 'object') return null;
    if (o.awemeId || o.aweme_id || o.desc !== undefined) return o;
    for (const k of Object.keys(o)) {
      const r = findAweme(o[k], depth + 1);
      if (r) return r;
    }
    return null;
  };
  const a = findAweme(window._ROUTER_DATA, 0);
  if (!a) return null;
  return {
    desc: a.desc ?? null,
    author: (a.author || {}).nickname ?? null,
    createTime: a.createTime ?? null,
    duration_ms: (a.video || {}).duration ?? 0,
    images: (a.images || []).map(i => ({
      url: (i.url_list || [])[0] ?? null, w: i.width, h: i.height,
    })).filter(i => i.url),
    video_url: ((a.video || {}).play_addr || {}).url_list?.[0] ?? null,
    hashtags: (a.textExtra || []).map(t => t.hashtagName).filter(Boolean),
    stats: {
      digg: (a.statistics || {}).digg_count ?? 0,
      comment: (a.statistics || {}).comment_count ?? 0,
    },
  };
})()
"""

async def extract_douyin_fallback(url: str) -> dict:
    kind = "note" if "/note/" in url else "video"
    page = await cdp.open_page(url, mobile_ua=True)
    await page.wait(12)                      # 实测需 8–13s

    a = await page.eval(ROUTER_JS)
    if a is None:
        raise ExtractFailed("_ROUTER_DATA 不存在，页面可能被风控")

    out = {
        "kind": kind,
        "title": (a["desc"] or "").strip(),
        "author": a["author"],
        "published_at": epoch_to_date(a["createTime"]),
        "likes": a["stats"]["digg"],
        "hashtags": a["hashtags"],
    }
    if a["duration_ms"]:
        out["duration_sec"] = a["duration_ms"] // 1000
    if kind == "video" and a["video_url"]:
        out["video_bytes"] = await download(
            a["video_url"], referer="https://www.douyin.com/")
    if kind == "note":
        out["images"] = [
            await download(img["url"], referer="https://www.douyin.com/")
            for img in a["images"][:9]
        ]
    await page.close()
    return out
```

**四条硬约束**：

| 约束 | 原因 | 违反后果 |
|---|---|---|
| 从 `_ROUTER_DATA` 取，不从 DOM 取 | DOM 掺入评论区与相关推荐 | 存进别人的内容 |
| 图片数用 `images.length`，不用 `<img>` 计数 | DOM 数到 12 个，实际只有 3 张 | 存一堆无关图 |
| 移动 UA | 桌面 UA 无 `<video>` | 抓不到视频 |
| 封面/原图/视频当场下载 | URL 带 `x-expires` 签名 | 过期 403 |

```python
def decide_type(meta: ExtractResult) -> str:
    # 域名修正规则优先，高于自动判断（PRD M3-08）
    if rule := domain_rule(meta.source_domain):
        return rule
    if meta.kind == "video" or meta.duration_sec:
        return "video"
    if len(meta.images) >= 3 and meta.word_count < 300:
        return "image_text"
    if meta.word_count >= 300:
        return "article"
    if meta.images and not meta.images[0].is_cover_only:
        return "image"
    if meta.file_bytes:
        return "file"
    return "link"          # 6 类里的兜底：抓取失败或判不出来
```

**为什么 AI 不参与判类型**：判断依据是结构化特征（有无视频流、图片数、字数），规则可解释、可测试、可修正。让 AI 判会引入不确定性，且 `domain_type_rules` 的「改一次就记住」无法实现。

单人使用，不做协作，**不用 CRDT**；冲突用后写覆盖。**Postgres 为唯一权威源**，不做本地全量缓存（MVP 不做离线）。

-- 修复1：同级重名须大小写与空白不敏感，否则「AI相关」与「ai相关」会并存
CREATE UNIQUE INDEX tags_sibling_name_idx
  ON tags (coalesce(parent_id, 0), lower(btrim(name)));

-- 修复2：原触发器只查「新父节点是否一级」，漏了 UPDATE 方向——
--        把已有子标签的一级节点 A 挂到 B 下，A 变二级、A 的子标签变三级，原逻辑放行
CREATE OR REPLACE FUNCTION tags_enforce_two_levels() RETURNS trigger AS $$
BEGIN
  IF NEW.id = NEW.parent_id THEN
    RAISE EXCEPTION '标签不能以自己为父节点';
  END IF;

  IF NEW.parent_id IS NOT NULL THEN
    -- 方向 A：新父节点本身必须是一级
    IF (SELECT parent_id FROM tags WHERE id = NEW.parent_id) IS NOT NULL THEN
      RAISE EXCEPTION '标签只允许两级，% 已是二级标签', NEW.parent_id;
    END IF;
    -- 方向 B：自己若已有子节点，就不能再被别人收为子节点
    IF EXISTS (SELECT 1 FROM tags WHERE parent_id = NEW.id) THEN
      RAISE EXCEPTION '标签 % 已有子标签，不能再降为二级', NEW.id;
    END IF;
  END IF;
  RETURN NEW;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER tags_two_levels
  BEFORE INSERT OR UPDATE OF parent_id ON tags
  FOR EACH ROW EXECUTE FUNCTION tags_enforce_two_levels();

### 6.2 异步流水线的状态机（v7.0 缺失）

v7.0 只有 `jobs.step` 枚举与 `jobs_pending_uniq`，**没写谁在 fetch 成功后创建 summarize**，也没写 `attempts>=3 → failed` 在哪判。这一节补上。

**推进方式：worker 单步推进，每步完成后在同事务内插入下一步。**

| 步骤 | 做什么 | 成功后插入的下一步 |
|---|---|---|
| `fetch` | 抓元数据 + 下载媒体 | `summarize` |
| `summarize` | 文本模型出摘要，写 `items.summary` | `tag` |
| `tag` | 同一调用出标签，校验词表后写 `item_tags` | 无（终态） |
| `ocr` | 图片类专用，可并行于 summarize | 无（终态） |

**worker 取任务的 SQL**（必须用 `FOR UPDATE SKIP LOCKED`，否则两个 worker 抢同一条）：

```sql
WITH picked AS (
  SELECT id FROM jobs
   WHERE state = 'pending' AND run_after <= now()
   ORDER BY run_after
   LIMIT 1
   FOR UPDATE SKIP LOCKED
)
UPDATE jobs SET state = 'running', updated_at = now()
 WHERE id IN (SELECT id FROM picked)
RETURNING id, item_id, step, attempts;
```

**失败与退避**：

```sql
-- 失败时：未到 3 次则回到 pending 并延迟；达到 3 次则永久 failed
UPDATE jobs
   SET attempts = attempts + 1,
       state    = CASE WHEN attempts + 1 >= 3 THEN 'failed' ELSE 'pending' END,
       run_after = now() + (interval '1 minute' * power(2, attempts)),
       error    = $2,
       updated_at = now()
 WHERE id = $1;
```

**worker 崩溃导致 job 卡 `running` 的清理**（v7.0 未考虑）：

```sql
-- 每次 worker 启动时执行：running 超过 15 分钟视为已死
UPDATE jobs SET state = 'pending', error = 'worker 失联，重置'
 WHERE state = 'running' AND updated_at < now() - interval '15 minutes';
```

### 6.3 必须写进 DDL 的业务约束

| 约束 | 落在哪里 | 为什么不能只靠应用层 |
|---|---|---|
| 类型只有 6 种（含 `link` 兜底） | `items.type` 的 `CHECK` | 应用层漏校验会写入脏数据，检索与渲染全崩 |
| 标签只能两级（含 UPDATE 方向） | `tags_enforce_two_levels` 触发器 | 挂第三级会让左侧树的遍历逻辑无限递归 |
| 同级标签名大小写不敏感唯一 | `tags_sibling_name_idx` 用 `lower(btrim())` | 否则「AI相关」「ai相关」并存，撞 PRD 的反目标 |
| 同任务不重复入队 | `jobs_pending_uniq` 部分唯一索引 | 并发点两次保存会抓两遍，浪费且可能触发风控 |
| 每表有 `created_at` | 各表 DDL | PRD §7 硬要求，缺了排查问题没有时间锚点 |

### 6.4 定时任务清单（v7.0 只写了两项）

| 任务 | 频率 | 做什么 | v7.0 是否有 |
|---|---|---|---|
| 备份 | 每日 22:30（+ 开机补跑） | `pg_dump` + `restic backup media/` | 有 |
| **回收站清理** | 每日 22:40 | `deleted_at < now() - 30 days` 的条目：先删 `files` 对应的磁盘文件，再删 `items` 行 | **缺** |
| **Meilisearch 对账** | 每日 23:00 | 比对 `items` 计数与索引文档数，不一致则告警（不自动重建） | **缺** |
| **job 卡死清理** | 每次 worker 启动 | 见 §6.2 末 | **缺** |

**删除顺序必须是「先磁盘文件，后数据库行」**：反了会在删文件前失败，留下孤儿文件；这样最坏留下孤儿 row，可以重跑。

### 6.5 存储布局（含异地备份）

```
data/
├── pg/                        # Postgres 数据目录
├── media/
│   ├── cover/<hash>.webp      # 封面，统一转 webp，长边 ≤1280
│   ├── orig/<hash>.<ext>      # 原图 / 原视频
│   └── snapshot/<hash>.html   # monolith 整页归档
└── backups/                   # restic 仓库（本地副本）
```

**⚠️ v7.0 的致命缺陷**：`backups/` 与 `pg/`、`media/` 同盘。平板损坏或丢失时，备份与数据一起消失——PRD M9-06 要求「云端每日快照」，同盘备份等于没备份。

**修正后必须有两个 restic 目标**：

| 目标 | 位置 | 作用 |
|---|---|---|
| 本地 | `data/backups/` | 快速回滚（误删当天就能恢复） |
| **异地** | 三选一：① 电脑用 `rclone sync` 每日拉取；② 网盘（WebDAV/S3 兼容）；③ 另一块可移动盘 | **抗设备损坏/丢失**，这是 M4「防丢失」的实际落点 |

restic 支持多 backend，只是 `-r` 目标不同，成本极低：

```bash
restic -r /data/backups backup /data/pg /data/media        # 本地
restic -r rclone:remote:kb-backup backup /data/pg /data/media   # 异地
```

**为什么用 hash 做文件名**：同一条内容重复抓取时自然去重；也避免原始文件名里的中文与特殊字符在 proot 下出问题。

### 7.2 三处取舍的真实理由（v7.0 的理由写错了）

**v7.0 的错误**：D4/D6 用「`pydantic-core` / `psycopg` / `argon2-cffi-bindings` 无 Android 轮子」作为否决理由。**这是错的**——实测这三个包都有 aarch64 轮子：

| 包 | 实际轮子 |
|---|---|
| pydantic-core 2.50.5 | `cp312-cp312-manylinux2014_aarch64`（共 19 个 aarch64 轮子）|
| psycopg-binary 3.3.9 | `cp312-cp312-manylinux_2_27_aarch64`（共 12 个）|
| argon2-cffi-bindings 26.2.0 | `cp310-abi3-manylinux_2_26_aarch64`（abi3，Python 3.10+ 通用）|

所以选 Starlette/pg8000/bcrypt **不是被迫的**。真实理由如下，**这三条是主动取舍，复检可以推翻**：

| 原选择 | 换成 | **真实代价** | 是否可接受 |
|---|---|---|---|
| FastAPI | Starlette | 失去自动 OpenAPI 生成与请求体校验（FastAPI 在 proot 里**能装**，只是多一层 `pydantic-core` 的 ABI 依赖） | 是。接口契约写在 §8，不依赖自动生成；校验用 Pydantic v2 手写中间件 |
| psycopg | pg8000 | 性能略低（纯 Python 实现，无二进制协议加速） | 是。单用户，单条插入差距毫秒级 |
| argon2id | bcrypt cost=12 | **安全强度确实略降**。OWASP 把 bcrypt 列为「遗留系统可用，work factor ≥ 10」，本项目取 12 | 是但须记录。若要 argon2，`argon2-cffi-bindings` 有 abi3 轮子，**可以换回去** |

**为什么仍选这条更「保守」的组合**：少两个需要 ABI 匹配的 C 扩展，等于少两个 G0' 可能失败的点。在「能否在平板跑起来」本身还没验证的阶段，减少失败面比压榨性能重要。**G0' 通过后如果想换回 FastAPI/psycopg/argon2，是有路的**，不是单向门。

### 7.3 终端必须注意点（含 v7.0 的三处硬错误修正）

| 项 | 说明 |
|---|---|
| 系统包来源 | **Debian 13 源**：`apt install python3.12 postgresql-17 python3-pip ffmpeg`。**不用 `pkg install`** |
| Python 版本 | **3.12**，Debian 13 主源自带（`python3.12`）。v7.0 说「用 Debian 12 自带 3.11」，与 `parsehub` 要求冲突 |
| PostgreSQL | **17**，Debian 13 主源自带。v7.0 说「Postgres 18」，**Debian 12 与 13 都没有 18**，只能加 PGDG 第三方源——那就不叫「全部走 Debian 源」了 |
| ffmpeg | **必须装**（约 70MB）。T9 的 `ffprobe` 依赖它，v7.0 的依赖清单与系统包清单都漏了 |
| Meilisearch | 下官方 `meilisearch-linux-aarch64` 静态包，`chmod +x` 后直接跑，不装 |
| Caddy | 官方 aarch64 静态包（proot 内运行） |
| Supervisor | `apt install supervisor`，用于守护四个进程（见 §2.3 第 4 条） |

**v7.0 这一节自相矛盾的三句话**（审计 #32）：

1. 第 1 行 `apt install postgresql-18 python3.12`
2. 第 2 行「改用 Debian 12 自带 3.11 更稳」
3. 第 3 段「终版统一为 3.11」

三句三个状态，且两句与 `parsehub` 的 `>=3.12.0` 冲突。本版统一为 **Debian 13 + Python 3.12 + Postgres 17**，四处一致。

⚠️ **这仍是设计决定，不是实测**。G0' 必须在平板上下载 trixie rootfs 并验证 `python3.12 -V` 输出 `3.12.x`、`psql --version` 输出 `17.x`。

### 7.4 AI 层设计（v7.0 完全缺失）

PRD 的 M3-02/03/04/05 都是 P0，而 v7.0 全文没有模型名、没有 prompt、没有失败降级、没有额度上限。这一节补上。

**分工原则：一次文本调用同时产出摘要与标签**（省一半 token，也避免两次结果不一致）。

| 项 | 决定 | 依据 |
|---|---|---|
| 模型 | 单一 OpenAI 兼容端点，可配 base_url | 不锁定厂商，换模型只改环境变量 |
| 摘要 | ≤100 字，中文 | PRD M3-02 |
| 标签 | **1–3 个，只能从数据库已有标签里选** | PRD M3-04 明确禁止 AI 造词 |
| 结构化输出 | 要求返回 JSON：`{"summary": str, "tags": [str], "confidence": float}` | 便于校验 |
| 失败降级 | 3 次退避后放弃摘要与标签，条目仍入库（`summary` 为空，落进「没归好类的」筛子） | PRD V9「AI 没把握时不硬猜」 |
| 额度上限 | `settings` 表存 `ai_monthly_budget_cny`，worker 每次调用前累加当月消耗，超限则跳过 AI 步骤并记 `jobs.error='额度超限'` | C4「几元到几十元」必须可兜底 |

**prompt 骨架**（落地时按此改，不要现场发明）：

```
你是内容归档助手。下面是用户保存的一条内容：

标题：{title}
来源：{source_domain}
类型：{type}
正文（可能为空）：{content_text 截断到 2000 字}

请输出 JSON：
{
  "summary": "不超过 100 字的中文摘要，只陈述内容本身，不加评价",
  "tags": ["从下列标签中选 0-3 个，不要发明新词", ...],
  "confidence": 0.0-1.0
}

可选标签（父子用 > 连）：
{从 tags 表读出的完整词表，两级展开}

规则：
- 若内容信息不足以概括，summary 返回空字符串，不要编造。
- tags 只能来自上面的列表；没有合适的就返回空数组。
```

**落库前的二次校验**（PRD M3-04 的「只能从词表挑」实际落点）：

```python
def validate_tags(raw: list[str], allowed: dict[str, int]) -> list[tuple[int, float]]:
    """把模型返回的标签名映射成 id。不在词表里的一律丢弃，不报错。"""
    out = []
    for name in raw[:3]:
        key = name.strip().lower()
        if key in allowed:              # 大小写不敏感匹配
            out.append(allowed[key])
    return out
```

**视觉模型**（M3-05 图片 OCR + 描述）：独立一次调用，只对 `type='image'` 与图文的原始图触发。同样是 OpenAI 兼容的 vision 端点。**若该端点未配置，图片只存不解析**，不阻塞。

**用量记录**（M9-07 落点）：每次 AI 调用写一行到 `settings` 的 `ai_usage_2026_11` 键（jsonb 累加），或在 `jobs.error` 里记失败原因。**v7.0 没有这张表，用 `settings` 避免加表。**

### 8.1.1 三个关键端点的约定

**`GET /api/media/{key}`**（🆕，v7.0 的最大功能缺口）

- 鉴权：必须带有效会话 Cookie，否则 401。**不要做成静态目录**，否则同网段未登录者也能读图。
- 路径校验：`key` 必须匹配 `^(cover|orig|snapshot)/[a-f0-9]{32,64}\.(webp|jpg|png|mp4|html)$`，否则 400。防目录穿越。
- 响应头：`Cache-Control: private, max-age=31536000, immutable`（key 含内容 hash，永不变）
- 大文件：视频用 `StreamingResponse` 分块，不整读进内存。

**`POST /api/auth/bootstrap`**（🆕，v7.0 的鉴权死锁）

```
仅在 SELECT count(*) FROM users = 0 时可用。
成功创建一个用户后，此端点永久返回 410 Gone。
用户名与密码由请求体给出；密码立即 bcrypt(cost=12) 后存储。
```

**`GET /api/health`**（扩展）

```jsonc
// v7.0 只回 dbOk，服务挂了用户只能看到"打不开"
{
  "ok": true,
  "dbOk": true,
  "meiliOk": true,              // 🆕 Meilisearch 是否可达
  "workerHeartbeatAt": "2026-11-26T08:10:00Z",  // 🆕 worker 最后一次心跳
  "diskFreeGb": 198.4           // 🆕 剩余磁盘（8GB 设备上磁盘满也会挂）
}
```

### 8.2 上传、分页与导出的上限（v7.0 全缺）

8GB 内存平板上，以下任一不设限都可能 OOM：

| 项 | 上限 | 超限行为 |
|---|---|---|
| 单文件上传大小 | 100 MB | 413 |
| 允许的 MIME | `image/*`、`video/mp4`、`application/pdf`、`application/zip` | 415 |
| 列表分页 `limit` | 默认 30，最大 100 | 超过则夹到 100，不报错 |
| 导出 | **必须 `StreamingResponse`**，逐条写 zip | 不允许在内存里拼完整 zip |
| 抓取响应体 | 20 MB（超过则放弃正文，只存链接） | 记 `jobs.error` |

### 8.3 搜索的降级阶梯（重要）

因为抖音的可读文本只有标题一句，**检索的主战场是标题**，不是正文。因此搜索按三级降级：

| 级 | 机制 | 覆盖什么 | 何时用 |
|---|---|---|---|
| L1 | Meilisearch 全文（标题 + 摘要 + 正文 + 标签 + 作者） | 正常情况 | 默认 |
| L2 | Meilisearch 前缀 + 拼写容忍 | 用户记错一个字 | L1 返回 0 条时 |
| L3 | Postgres `ILIKE '%词%'` 扫标题 | Meilisearch 挂了，或中文分词不理想 | L1/L2 都 0 条，或 Meilisearch 不可用 |

**G3 关卡的可判定判据**（v7.0 写「排序合理」，无法判定）：

> 准备 50 条已入库内容，其中 3 条标题含「矩阵」。搜「矩阵」时，**这 3 条必须出现在前 5 条内**，且总结果数 ≥ 3。三遍一致才算通过。

**索引一致性修复**（v7.0 缺）：Meilisearch 挂了会导致 items 已入库但搜不到，且没有自愈机制。

```bash
# 全量重建索引（从 Postgres 重灌），可随时执行
python -m kb.index rebuild

# 每日对账（§6.4 的定时任务）：count 不一致则告警，不自动重建
```

### 8.4 POST /api/items 的请求与响应

```jsonc
// 请求
{ "url": "https://v.douyin.com/xxx/", "raw_text": "可选，分享文案原文" }

// 响应 202
{ "id": 1234, "state": "pending", "deduped": false }
```

**行为**：

1. 解析 URL（从分享文案里提取短链）
2. 按 `url` 查重（规范化后）；命中则返回已有 id 且 `deduped: true`
3. 写 `items`（`type` 先用 `link` 兜底，`title` 先用域名），写 `jobs(step='fetch')`
4. **立即返回 202**，不等待抓取

### 8.5 鉴权

| 项 | 做法 |
|---|---|
| 形式 | HttpOnly + Secure + SameSite=Lax Cookie，值是不透明随机串 |
| 存储 | `sessions.token_hash` 存 SHA-256，**不存明文** |
| 有效期 | 30 天，滑动续期 |
| APK 内 | Capacitor 的 Cookie 管理，登录一次长期有效 |
| 首账号 | **由 `POST /api/auth/bootstrap` 创建**（v7.0 只写「首个注册者即唯一用户」却无注册端点，实际无法完成） |
| 写入限流 | **应用层中间件**（内存计数 + Postgres 持久化），**不用 Caddy `rate_limit`**——该模块官方明写「does not come with Caddy」，需 `xcaddy` 自编译，违反 C3「组件越少越好」 |

### 10.3 G1 专项：证书为什么必须用 `ts.net`

**v7.0 的错误**：用 Caddy `tls internal`（自签），并在 §2.2 写「对 APK 无感」——**混淆了「地址」与「证书信任」**。

**事实**（查证）：

| 事实 | 来源 |
|---|---|
| 面向 Android 7.0+ 的应用**仅信任系统证书，不再信任用户安装的 CA** | Android 7.0 官方更新日志原文 |
| 应用要信任自定义 CA，必须配 `network_security_config.xml` 并打包 CA | 同上 |
| **Android 14 起证书由 Google Play 更新，从 `/apex/com.android.conscrypt/cacerts/` 读取，对旧路径的修改无效** | 公开报道（HTTP Toolkit 披露） |

这台平板是 **Android 14**，所以「让用户在系统里装个根证书」这条路在新系统上已不可行。

**两条可行路线**：

| 路线 | 做法 | 代价 |
|---|---|---|
| **推荐：Tailscale `ts.net` 证书** | `tailscale cert <host>.<tailnet>.ts.net` 签 Let's Encrypt 真证书，Caddy 加载它 | 无额外代价；证书被系统信任，APK 直接可用 |
| 备选：打包 CA | APK 内放根证书 + `network_security_config.xml` 声明信任 | 要维护证书有效期；换设备要重新打包 |

**G1 的判据必须包含「无证书警告」**，不能只测「能打开」——用户点「继续访问」也能打开，但那是每一条请求都要点一次。

**「M1 能存进去」是产品的第一个可用里程碑**，它不依赖 Meilisearch（G3）也不依赖 AI 质量——只要抓取与入库通。**建议 G0' 之后直奔 M1，先让产品能用，再优化检索与标签。**

⚠️ **V3「500 条按下就出结果」缺毫秒阈值**：PRD 自己称这是「唯一必须量化的」。本方案取 **P95 < 800ms**（单用户、局域网/Tailscale 场景），作为 G3 的补充判据。若 G3 通过但 P95 超 800ms，先优化索引再考虑加机器。

### 11.1.1 并发测试的确切含义（v7.0 未定义）

「连点两次」不等于「并发」。两种测法，都要做：

| 测法 | 怎么做 | 断言 |
|---|---|---|
| 顺序重放 | 同一请求体连发两次 | 第二次返回 `deduped: true`，`items` 计数不变 |
| **真并发** | 两个独立连接**同一毫秒**发同一 URL（`asyncio.gather` + 两个连接） | 一条成功、一条 conflict 或 deduped；`jobs` 里只有 1 条 pending |

真并发才是 `jobs_pending_uniq` 存在的理由——顺序重放靠应用层查重就能过，测不出索引的必要性。

### 11.2 新增测试（v7.0 缺失的六类）

审计指出 T1–T12 全是单点功能测试，**没有一条覆盖「跨步骤串起来」**。补六条：

| # | 测试 | 为什么必须有 |
|---|---|---|
| **T13** | **主链路端到端** | 存一条真实抖音 → 等 worker 跑完 → `items.summary` 非空 → `item_tags` 至少 0 条 → 搜得到。**这是产品是否成立的唯一总判据**，T5/T6 只测抓取单步 |
| **T14** | **worker 崩溃恢复** | 手动把 job 置为 `running` 且 `updated_at` 调早 20 分钟 → 重启 worker → 该 job 回到 `pending` 并被重新执行（§6.2 末的清理 SQL） |

### 11.4 架构约束（写成检查，不写进文档）

| 约束 | 检查方式 | 为什么用检查而不是注释 |
|---|---|---|
| 抓取层不得直接写库 | **AST 扫描** `extract/` 出现 `db.` 或 `execute(` 即失败（**不要用 grep**，注释与字符串会误报） | 分层靠 import 边界强制，不靠自觉 |
| 只有 `capture` 能写 `items` | AST 扫描其他模块的 SQL 字符串含 `INSERT INTO items` 即失败 | 同上 |
| 前端不得直连数据库 | 扫描 `web/` 出现 `postgres://` 即失败 | 防止把连接串打进 APK |
| 标签只能两级 | `tests` 里插入三级标签断言抛异常 | DDL 触发器 + 测试双重保险 |
| 类型只有 6 种 | `tests` 里插入非法类型断言被 `CHECK` 拒绝 | 同上 |

**这五条都用 pytest 实现，不用 lint 注释。** 依据 AGENTS.md 第八节：能用一条测试表达的约束，不写成文档。

### 11.5 反向测试（验证检查本身有效）

| 检查 | 反向验证 |
|---|---|
| 类型 `CHECK` | 手动插入 `type='podcast'`，断言报错 |
| 两级标签触发器（INSERT 方向） | 手动挂第三级，断言报错 |
| **两级标签触发器（UPDATE 方向）** | **把已有子标签的一级节点挂到另一节点下，断言报错**——这正是 v7.0 漏的分支 |

**为什么必须有反向测试**：一个永远返回「通过」的检查，比没有检查更危险。这一点在文档规则那边已经踩过一次（`git diff` 中文路径转义导致检查静默全绿）。

**Q2 的容量算术（v7.0 算错了）**

v7.0 原文：「3.9MB/条，一天 10 条 ≈ 1.2GB/月，256GB 撑不到一年」。这三句里最后一句与前面自相矛盾——`1.2GB × 12 = 14.4GB`，256GB 能用约 **17 年**，不是「撑不到一年」。

按同一口径重算：

| 项 | 数值 | 算式 |
|---|---|---|
| 单条视频体积 | 3.9 MB | 实测（`size_download=4076253`） |
| 单条封面 | 约 82 KB | 实测原图 83,388 字节 |
| 单条图文（3 张原图） | 约 250 KB | 按单张 83KB 估 |
| 日均条数与比例 | 10 条（7 视频 + 3 图文） | 用户口述 |
| 每天占用 | **约 28 MB** | `7×3.9 + 10×0.082 + 3×0.25 ≈ 27.3 + 0.8 + 0.75` |
| 每月占用 | **约 840 MB** | `28 × 30` |
| 每年占用 | **约 10 GB** | `840 × 12` |
| 256GB 可用（扣系统与库） | 约 200 GB | 保守值 |
| **可用年限** | **约 20 年** | `200 ÷ 10` |

**所以「按需存」的真实理由是「备份与迁移体积」，不是「磁盘会满」**——原文的结论对，理由错。

而 **restic 的增量去重会让异地备份的体积远小于 10GB/年**（封面与视频内容 hash 不同，去重主要省重复抓取的部分）。

值得担心的是另一个数：**`ffmpeg` 生成的视频快照**与 **monolith 整页归档**若对每条都开，占用会翻倍。建议：整页归档只对文章类做，视频不做。

## 附录 B：术语表（给非技术背景的验收方）

> AGENTS.md 第五节要求「术语首次出现配一句人话解释」。本文大量使用技术词，为便于验收方判断，集中解释在此。

| 术语 | 一句人话 | 在本文哪里用 |
|---|---|---|
| **proot Debian** | 在安卓上套一个「假 Linux」环境。不是虚拟机，不用 root，但能让 Linux 程序以为自己跑在正常 Linux 上 | §2.1、§7.1 |
| **glibc / bionic** | 两套不同的「系统基础库」。安卓用 bionic，普通 Linux 用 glibc。为 glibc 编译的软件装不进 bionic | §2.1 |
| **轮子（wheel）** | Python 的「预编译安装包」。有轮子就能直接装；没有就得现场编译，常常失败 | §4.7、§7.2 |
| **abi3** | 一种「一次编译、多版本通用」的轮子。看到 `cp310-abi3` 表示 Python 3.10 及以上都能用 | §4.7、§7.2 |
| **CDP** | Chrome 的「遥控接口」。能让程序远程指挥浏览器翻页、取数据 | §4.9、§10 |
| **`_ROUTER_DATA`** | 抖音网页里藏着结构化数据的一个变量。从它取数据比从页面文字里抠更准 | §4.9 |
| **Tailscale** | 一个组网工具。让手机在外面也能连到家里的平板，不需要公网 IP、不需要域名 | §2、§10.3 |
| **`ts.net` 证书** | Tailscale 免费签发的「真」HTTPS 证书。手机系统认它，所以 APK 不会报证书错误 | §10.3 |
| **restic** | 备份工具。增量、加密、能去重，适合每天跑 | §3.2、§6.5 |
| **Meilisearch / Charabia** | 搜索引擎 / 它内置的中文分词器。分词准不准直接决定能不能搜到 | §8.3、§10.2 |
| **supervisor** | 一个「进程看门狗」。服务挂了自动拉起来 | §2.3 |
| **迁移（migration）** | 数据库结构的版本管理。改表结构时按顺序执行，可回滚 | §11.2 T16 |
| **幂等（idempotent）** | 同一个操作做多次，结果和做一次一样。重试不会重复入库 | §8.1、§11.1.1 |
| **部分唯一索引** | 只在满足条件的数据上查重。用来「同一条目的同一步骤只允许一个待办」 | §6.1 |
| **触发器（trigger）** | 数据库里的门卫。不合规的数据直接拒绝写入 | §6.1、§11.5 |
| **软删除** | 不真删，只打个「已删除」标记。能进回收站、能恢复 | §6.1 |
| **P0 / P1** | 必须有 / 可以以后有。P0 缺一条产品就不成立 | 全文 |
| **关卡（G0'–G6）** | 施工时必须逐个通过的验证点。不过就得改方案或换路线 | §10 |
