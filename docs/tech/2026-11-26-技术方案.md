## 0. 一页给用户的话

**这一版最大的变化：先找现成的，不再从零造。**

调查后发现 `karakeep`（3.09 万星，TypeScript，AGPL-3.0）已经实现了我们 41 条 P0 里的 28 条，包括 AI 自动打标签、全文搜索、整页归档、浏览器扩展、安卓 App。**另起一套自研等于重复造轮子，而这正是你明确反对的。**

所以方案改成：**能复用的一律复用，只补本项目的个性缺口。**

| 结论 | 内容 |
|---|---|
| 复用 | karakeep 作为底座（41 条 P0 里直接命中 28 条） |
| 自造 | 4 个差异化模块：抖音深度抓取、两级标签树、日期视图、类型修正记忆 |
| 部署 | 从「4 容器自研」变成「karakeep 3 容器 + 1 个旁挂服务」 |
| 内存 | 约 1.2GB（karakeep 约 1GB + 旁挂约 200MB），平板 8GB 可承受 |
| 关键风险 | **抖音是主力，但 karakeep 对抖音只有通用抓取** —— 这是全案最大不确定点，第 5 节单独处理 |

**你现在只需要知道三件事**：

1. 方案从「全自研」改成「复用为主的混装」，工作量从约 3 个月降到约 3 周。
2. 抖音能不能抓稳，决定这套东西值不值得做。第 5 节给了实测结论和退路。
3. 我这一轮只写方案，不动手。你验收后叫复检会话审，审完再开工。

## 1. 目标与边界

### 1.1 一句话目标

在安卓平板（联想 Y900 13，8GB）上自托管一个私人内容库，主力入口是**抖音链接的系统分享**，能凭模糊记忆找回。

### 1.2 硬约束（来自 AGENTS.md 与本轮明确要求）

| # | 约束 | 对设计的直接限制 |
|---|---|---|
| C1 | 单人自用，无协作、无权限体系 | 不建多用户模型，不做 RBAC |
| C2 | 只有 Windows 电脑 + 安卓手机/平板，无 Mac/无 iPhone | 不考虑 iOS 构建链 |
| C3 | 非技术背景，出问题要能靠 AI 修 | 组件越少越好；不引入需要长期调参的自研服务 |
| C4 | 成本几元到几十元/月，不满意几十元固定开销 | 优先零成本；不买云主机作为首选 |
| C5 | 宿舍 23:30–06:00 断电 | 备份必须 22:30 前完成；平板靠电池 |
| C6 | 不注册域名、不备案 | 内网 + Tailscale，不用公网域名 |
| C7 | **主力内容是抖音**，公众号/知乎几乎不用 | 抖音抓取能力是必需项，不是加分项 |
| C8 | 能复用成熟体系就别造，个性化才自造 | 复用优先；自造部分必须自建测试 |
| C9 | 本会话只设计，不施工 | 本文不含执行动作 |

### 1.3 明确不做

多人协作、公开分享页、知识图谱、以图找图、离线优先、内容推荐算法、富文本编辑器。

### 3.2 各组件的角色

| 组件 | 来源 | 职责 | 改动 |
|---|---|---|---|
| karakeep web | 上游镜像 | 抓取、存储、AI 标签、搜索、基础 UI | 仅配置 + 1 处源码补丁 |
| meilisearch | 上游镜像 | 全文与语义检索（Charabia 中文分词） | 无 |
| Chromium | 上游镜像 | 页面渲染（抖音必需） | 无 |
| **kb-ext** | **自建** | 类型判定、属性补全、类型修正记忆 | 新增 |

**为什么自建部分不塞进上游**：上游是 Next.js + tRPC + Drizzle 的 monorepo，改一处要跟着它的发布节奏走。旁挂服务只依赖它的 HTTP API，上游升级不受影响。**唯一例外是两级标签**——它必须改数据模型，绕不过去（代价见 4.2）。

### 3.3 与 v1.8 自研方案的取舍对照

## 4. 自建模块设计

### 4.1 kb-ext：类型与属性服务

**职责**：karakeep 抓完内容后，kb-ext 判定类型、补属性、记修正。

```
karakeep 抓取完成
   → webhook 触发 kb-ext
   → kb-ext 读内容结构（有视频? 字数? 图数?）
   → 判类型（6+1）
   → 写回 karakeep 的书签（通过 API 写 tags + 自定义字段）
   → 写 kb_ext.item_props（时长/字数/评分等）
```

**类型判定规则**（替换 PRD M3-01 的"按结构不按域名"）：

```python
def decide_type(has_video: bool, text_len: int, image_count: int,
                upload_kind: str | None) -> str:
    if upload_kind == "image": return "image"
    if upload_kind == "file":  return "file"
    if has_video:              return "video"
    if image_count >= 3 and text_len < 300: return "image_text"
    if text_len >= 300:        return "article"
    if text_len > 0:           return "image_text"
    return "link"
```

**修正记忆**（M3-08）：用户改类型 → 写 `kb_ext.domain_type_rules(domain, type)` → 下次同域名优先用规则。

**测试要求**（对应你第 6 条，测试是核心）：

| 测试 | 类型 | 断言 |
|---|---|---|
| 7 种输入组合各判出正确类型 | 单元 | 表驱动，覆盖 6+1 |
| 空内容不崩 | 单元 | `text_len=0, image_count=0` → `link` |
| 有视频但字数很多 → video 优先 | 单元 | 规则优先级 |
| 域名规则覆盖自动判定 | 单元 | 建规则后同类域名走规则 |
| webhook 幂等 | 集成 | 同一 bookmk 触发两次不重复写 |
| karakeep API 超时降级 | 集成 | 超时后本地记 pending，重试 3 次 |

### 4.2 两级标签（唯一需要改上游的）

**为什么绕不过**：karakeep 的 `bookmarkTags` 是扁平表，无 `parentId`。PRD M5-03 要求「两级标签，界面上呈现为树」。用「标签名前缀 `AI/skill`」能凑出视觉分组，但**父级计数、拖拽移动、改名传播**全部要自己实现，反而比加一列更麻烦。

**改动范围**（fork 后）：

| 层 | 改动 | 行数估计 |
|---|---|---|
| `packages/db/schema.ts` | `bookmarkTags` 加 `parentId`（自引用，nullable） | +2 |
| 迁移 | 新增一列 + 索引 + 约束（父级必须 parentId 为空 → 强制两层） | 迁移文件 |
| tRPC 路由 | 创建/改名/删除时处理父子关系 | +80 |
| Web UI | 侧栏标签渲染成树 | +150 |
| 搜索过滤 | 点父标签 = 含所有子标签 | +30 |

**升级代价**（必须写清）：每次上游发版要 rebase 一次。上游约 2 个月一个 minor，冲突面集中在 `schema.ts` 与标签相关路由。**如果上游某天原生支持层级标签，这个 fork 就可以丢掉**——所以每个补丁要单独一个 commit，便于丢弃。

**替代方案与淘汰理由**：

| 替代 | 代价 | 为什么不选 |
|---|---|---|
| 用 Lists 做层级 | Lists 是可嵌套的，视觉上能满足 | 语义是「收藏夹」，一条内容进 List 需要手动/规则；而标签是「主题」，AI 可自动打。两者不能互换 |
| 前缀模拟（`AI/skill`） | 不改上游 | 父级计数、改名传播、拖拽全要自己造，工作量反而更大 |
| 只用扁平标签 | 零改动 | 违反 M5-03，且 100+ 标签时侧栏无法用 |

### 4.4 AI 标签词表约束（M3-04，改配置即可）

karakeep 的提示词可自定义。做法：

1. 在 karakeep 设置里把标签语言设为中文。
2. 自定义提示词，把「只能从以下词表选」作为硬约束，词表从 karakeep 现有标签动态注入。
3. 校验：打完后用脚本扫一遍，凡不在词表的标签告警（不自动删，避免误伤）。

**测试**：喂 20 条真实内容，断言产出标签 100% 在词表内；不在则告警计数为 0。

## 5. 抖音：全案最大不确定点

### 5.1 已实测的三条路径（2026-11-26，本机 Chrome 138）

| 路径 | 结果 | 证据 |
|---|---|---|
| karakeep 内置的 yt-dlp | ❌ | `DouyinIE._real_extract` 直接调 `aweme/v1/web/aweme/detail/`，缺 `s_v_web_id` 抛 `Fresh cookies are needed`；源码 TODO 明写需运行验证挑战 |
| 纯 Python 签名（f2 的 `ABogus`） | ❌ | 签名生成成功，服务端返回 **`403 Blocked by ArgusSecurityPlugin Uifid Not Found`**；补 `ttwid`（可获取）后仍 403，缺 `uifid` |
| **Chromium 渲染 + 移动 UA** | ✅ | `<title>` 拿到真实文案；`video.src` 拿到播放地址；封面 URL `curl` 返回 `200 image/webp 21186` |

**关键细节**：桌面 UA 下 `body.innerText` 仅 366 字符（导航+页脚），拿不到 `<video>`；**移动 UA 下才有**。这一条决定实现写法，不是可选优化。

### 5.2 与 karakeep 的衔接方式

karakeep 支持注入 cookie（`BROWSER_COOKIE_PATH`）与自定义 yt-dlp 参数（`CRAWLER_YTDLP_ARGS`），但**它的抓取流程是通用的**，没有抖音适配器。

三条可选路线：

| 路线 | 做法 | 风险 | 判定 |
|---|---|---|---|
| A. 靠 karakeep + cookie | 导出抖音 cookie 注入，让它用浏览器抓 | cookie 会过期（数周）；抖音改版即失效；需手工重导 | ❌ 对「主力是抖音」不可接受 |
| B. kb-ext 接管抖音 | 抖音链接不走 karakeep 抓取，交给 kb-ext 用 CDP 抓，抓完回写 | 要多维护一个抓取器；但完全可控 | ✅ **采纳** |
| C. 提交上游适配器 | 给 karakeep 提 PR 加抖音 provider | 上游未必接受（反爬合规）；周期不确定 | ❌ 不作为主路径 |

**B 的实现**（4.1 的 kb-ext 扩一个抓取器）：

```
用户分享抖音链接
   → karakeep 收到（URL 落库，标记待处理）
   → webhook 通知 kb-ext
   → kb-ext 用移动 UA 启动 Chromium，CDP 取 title/video.src/封面
   → 下载封面落盘（签名 URL 有 x-expires，必须当场下载）
   → 回写 karakeep 书签（标题、描述、封面）
   → 调 karakeep 的 AI 打标（用它现成能力）
```

**我必须说清的**：这条路**只在本机 x86 Chrome 上验证过**。平板 ARM + Termux 里的 Chromium 158 是否表现一致，**未验证**。这是开工前必须先验证的第一件事（第 8 节）。

### 5.3 如果平板 Chromium 不行，退路是什么

| 退路 | 代价 | 何时启用 |
|---|---|---|

## 6. 数据模型

### 6.1 分工

| 数据 | 存在哪 | 理由 |
|---|---|---|
| 书签、标签、列表、内容、资产 | karakeep 的 SQLite | 上游管，不重复存 |
| 条目属性（时长/字数/评分）、类型规则 | **kb-ext 的 SQLite** | 上游没有这些字段 |
| 搜索索引 | meilisearch | 上游管 |

**不做双写**：kb-ext 只存「上游没有的」，其余通过 API 读写。避免两套数据打架。

### 6.2 kb-ext 的表

```sql
-- 条目属性：上游没有的字段
CREATE TABLE item_props (
  bookmark_id TEXT PRIMARY KEY,        -- karakeep 的 bookmark id
  item_type   TEXT NOT NULL CHECK (item_type IN
                ('article','image_text','video','image','file','link')),
  word_count  INTEGER,
  duration_sec INTEGER,
  rating      SMALLINT CHECK (rating BETWEEN 1 AND 5),
  source_domain TEXT,
  extra       TEXT NOT NULL DEFAULT '{}',
  created_at  TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at  TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX item_props_type_idx ON item_props(item_type);

-- 类型修正记忆（M3-08）
CREATE TABLE domain_type_rules (
  domain     TEXT PRIMARY KEY,
  item_type  TEXT NOT NULL CHECK (item_type IN
               ('article','image_text','video','image','file','link')),
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

**为什么 SQLite 不是 Postgres**：与 karakeep 一致，备份就是拷文件，单用户量级足够。两级标签在 karakeep 侧（4.2），不在这些表里。

### 6.3 标签树（karakeep fork 的改动）

```sql
-- 在 karakeep 的 bookmarkTags 上加一列
ALTER TABLE bookmarkTags ADD COLUMN parentId TEXT REFERENCES bookmarkTags(id);
CREATE INDEX bookmarkTags_parent_idx ON bookmarkTags(parentId);

-- 强制只有两层：父标签的 parentId 必须为空
CREATE TRIGGER bookmarkTags_two_levels
BEFORE INSERT ON bookmarkTags
WHEN NEW.parentId IS NOT NULL
BEGIN
  SELECT CASE WHEN (SELECT parentId FROM bookmarkTags WHERE id = NEW.parentId) IS NOT NULL
    THEN RAISE(ABORT, 'tags 只允许两层') END;
END;
```

### 7.1 平板（首选）

| 项 | 做法 |
|---|---|

**这是本版最大的技术风险**：karakeep 官方只发 Docker 镜像，而 Termux 跑不了 Docker。用 proot-distro 手工还原三个服务，**可行性未验证**。第 8 节把它列为开工前第一道验证。

### 7.2 备选：Windows 常开（白天）

如果平板路线失败，退到 Windows。代价是 23:30 后不可用，但白天完全够。

### 10.3 AGPL 的实际影响（写清，避免误判）

AGPL-3.0 的关键义务是：**若你修改了软件并通过网络向他人提供服务，须向使用者提供源码**。

- 单人自用、不对外提供服务 → **不触发该义务**。
- 自己改自己用，不分发 → 无义务。
- 只有当你把改过的版本开放给别人用 → 须开源你的改动。

**结论**：对本项目无实际约束。但如果将来想让别人也用，要么开源你的 fork，要么换实现。
