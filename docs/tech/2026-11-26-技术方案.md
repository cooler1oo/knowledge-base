## 0. 一页摘要

### 0.1 系统是什么

一台**联想 Y900 13 平板**（8GB+6GB / 256GB / Android 14）当常驻服务端，跑 Termux + proot Debian 13；手机装 APK 负责系统分享入口；电脑用浏览器访问。三端通过 **Tailscale** 组网，不注册域名、不备案、不暴露公网。

**核心链路**：手机分享任意内容 → 平板抓取 → AI 出摘要与标签 → 存 Postgres → Meilisearch 建索引 → 列表出现卡片。

### 0.2 本版相对 v8.0 的实质变更

| # | 变更 | 为什么必须改 |
|---|---|---|
| 1 | **Python 3.12 → 3.13** | Debian 13 无 `python3.12` 包。tracker 原文「package is gone」（查证） |
| 2 | **内容类型从「6 类固定枚举」改为「可扩展 + 注册表」** | 用户明确要求「不固定类型、什么都能放」；固定枚举每加一种形态就要改 DDL |
| 3 | **新增 `attachments` 表，文件不再是一种「内容类型」** | 原模型里「文件」既是 `items.type` 的值又是附件，两种身份混用，导致 PDF 存得进读不出 |
| 4 | **`props jsonb` 补全四机制**（CHECK + 生成列 + GIN + 注册表） | 原方案只有「能存」，没有「能查、能校验」：`GIN` 0 次、`GENERATED` 0 次、`jsonb_typeof` 0 次 |
| 5 | **媒体读取改按 `attachments.mime` 放行** | 原方案用文件扩展名正则白名单，必然漏格式，且要两处同步改 |
| 6 | **`jobs.step` 加 `index` 步** | 原方案索引写入链路断开，入库后无人建索引，只能靠手动全量重建 |
| 7 | **备份改为 `pg_dump` 后再 restic** | 原命令直备运行中的数据目录，拿到撕裂副本；且判据测不出 |
| 8 | **T13 判据去恒真** | 原写法「`item_tags` 至少 0 条」对任何结果都成立，等于不断言 |
| 9 | **恢复 M6-01 的 OCR 检索字段与 M1 的摘要标签判据** | 两处 P0 被静默缩减 |
| 10 | **平台覆盖 8 → 16**（附可用性标注） | `Platform` 枚举实测 25 个，原方案只写 8 个 |

**C7 的推论（与 v8.0 的区别）**：v8.0 写「抖音抓不通则整个产品不成立」，并据此把检索设计成「主战场是标题」。这是错的。

正确表述：

1. 抖音是**优先级**，不是**存在性**。它先打通，但不通只影响该来源。
2. 抖音条目的可读文本只有标题，所以该条目的检索靠标题——这是**条目的属性**，不是全库的设计前提。
3. **全库检索必须覆盖标题、正文、摘要、标签、OCR 文字五路**（PRD M6-01）。

**C8 的推论**：模型不能是「6 类固定枚举」。见 §6.2。

## 2. 部署形态

### 2.1 整体结构

```
                    Tailscale 私有网络（WireGuard，端到端加密）
                                  │
        ┌─────────────────────────┼─────────────────────────┐
        │                         │                         │
  安卓手机（APK）            平板（服务端）            Windows 浏览器
  ACTION_SEND 分享桥    ┌──────────────────────────┐
                       │  Termux 层（bionic）       │
                       │   ├ Postgres 18.7  :5432   │  ← 实测必须在此层（§2.2.1）
                       │   └ proot Debian 13        │
                       │       ├ Caddy :8443        │
                       │       ├ kb-api             │
                       │       ├ kb-worker          │
                       │       └ Meilisearch        │  ← glibc 动态二进制，只能在 proot（§8.3.2）
                       └──────────────────────────┘
```

**两个进程的层级是实测逼出来的，不是设计偏好**：Postgres 只能跑在 Termux 原生层（proot 的 ptrace 让它卡死），Meilisearch 只能跑在 proot（Termux 层缺 glibc 解释器）。这两条约束方向相反，正好把四个服务分成两层，而两层通过 `127.0.0.1` 互通（已实测）。

### 2.2 为什么是 proot Debian 而不是 Termux 原生

| 环境 | libc | 能装 ParseHub 吗 | 结论 |
|---|---|---|---|
| Termux 原生 | bionic | 不能。`opencv-python-headless`、`lxml`、`pydantic-core` 只有 glibc 轮子，bionic 下需源码编译 | ❌ |
| **proot Debian 13** | **glibc** | **能。G0'-3 真机实测：57 个依赖全部装上，零编译** | ✅ 采纳 |

Android 内核不向非 root 应用暴露 namespace，**Docker 不可用**。这是否决 karakeep 等只发 Docker 镜像的产品的主因。

### 2.2.1 例外：Postgres 不能跑在 proot 里（G0'-4 实测推翻原设计）

v9.1 原设计把 Postgres 也放进 proot Debian，用 `pg_ctlcluster` 启动。**真机实测证明这条路走不通。**

| 尝试 | 结果 | 证据 |
|---|---|---|
| proot 内 `pg_createcluster 17 main` | ❌ `data directory has wrong ownership` | proot 的 UID 映射让 initdb 判定目录所有者不符 |
| proot 内 `su postgres -c initdb` | ❌ 卡死 5 分钟不返回 | 进程状态 `t (tracing stop)`，`wchan = ptrace_stop`——proot 的 ptrace 机制把 Postgres fork 出的子进程永久停在跟踪态 |
| **Termux 原生 `pkg install postgresql`** | ✅ **`initdb` 返回 `Success`，`pg_isready` 接受连接** | PG 18.7 `aarch64-unknown-linux-android`，依赖含 `libandroid-shmem`（Android 专用共享内存适配） |

**结论**：Postgres 装在 **Termux 原生层**（bionic），Python 服务留在 proot（glibc），两层通过 TCP 互通。

**跨层连通性已实测**：

```
proot 内 psql -h 127.0.0.1 -p 5432 -U u0_a201 -d postgres
→ PostgreSQL 18.7 ... | current_user = u0_a201   （1 row）
```

proot 与 Termux 共享同一网络命名空间，`127.0.0.1:5432` 双向可达。配置要求：`listen_addresses='*'`，`pg_hba.conf` 加 `host all all 0.0.0.0/0 trust`（仅本地 Tailscale 网络，无公网暴露）。

**这带来三处连带修改**：

1. **版本从 17 变 18.7**。Termux 仓库只提供 18.x；Debian 13 的 17.12 装得进 proot 但跑不起来。DDL 已在 18.7 上实跑通过（见 §6.2 注）
2. **`pg_ctlcluster` 全部从方案里删除**，改用 `pg_ctl -D <datadir>`。集群由 `initdb` 直接创建，不经过 Debian 的 cluster 机制
3. **Postgres 的数据目录在 Termux 侧**（`$HOME/pgdata`），不在容器内。备份脚本要同时覆盖两层

⚠️ **未验证**：Postgres 在 Termux 原生层的开机自启（G0'-7）。Termux:Boot 尚未安装。

### 2.3 网络与证书

| 项 | 做法 | 理由 |
|---|---|---|
| 组网 | Tailscale（WireGuard） | 不注册域名、不备案、不暴露公网 |
| 监听地址 | **`100.x.y.z:8443`（Tailscale 接口地址），不是 `0.0.0.0`** | `0.0.0.0` 会监听所有网卡，同 WiFi 设备可通过局域网 IP 访问登录页 |
| 证书 | `tailscale cert` 签发的 `ts.net` 证书 | 自签证书 Android 7+ 的 WebView 默认不信任（App 私有信任库），APK 会报 `ERR_CERT_AUTHORITY_INVALID` |
| 端口 | 8443（非 root 不能绑 <1024） | proot 内无 CAP_NET_BIND_SERVICE |

### 2.4 服务守护（统一用 runit，G0'-7 实测定型）

**原设计写的是「Termux 层用 `pg_ctl`、proot 层用 `supervisor`」两层方案。实测证明这是错的**，问题在于两层之间没有任何东西看守：`pg_ctl` 起的进程和 `proot-distro login` 起的会话都不抗会话结束。

**正确做法：所有服务统一交给 Termux 的 `termux-services`（runit）托管。**

`termux-services` 是 Termux 官方的服务管理方案，自带 `openssh` 和 `postgresql` 的服务脚本。它比自建方案好在三点：状态、日志、自动重启都有固定入口。

三个 runit 服务：

| 服务 | 来源 | 作用 |
|---|---|---|
| `postgres` | **官方自带**（仅改 `DATADIR`） | Termux 原生层 PG 18.7 |
| `sshd` | **官方自带**（原样使用） | 8022 |
| `kb-container` | **自写**（见下） | proot 容器，容器内由 supervisord 管 Meilisearch 等 |

`kb-container` 的 run 脚本（关键在 `exec`，让 proot 成为 runsv 的直接子进程）：

```sh
#!/data/data/com.termux/files/usr/bin/sh
exec proot-distro login debian -- bash -c \
  'exec /usr/bin/supervisord -c /etc/supervisor/supervisord.conf' 2>&1
```

**为什么 `postgres` 要改 `DATADIR`**：官方脚本用 `$PREFIX/var/lib/postgresql`，那是空目录（我们没在那里 initdb）。改为指向初始化过的 `$HOME/pgdata`。

### 2.4.0 为什么不能手动起 proot 进程（G0'-5/G0'-7 反复踩坑）

**现象**：在 proot 里用 `nohup ... &` 或 `setsid` 起 Meilisearch，**当前 `proot-distro login` 会话一结束，进程立刻消失**；从 Termux 侧 `nohup proot-distro login ... &` 起容器，SSH 断开后同样消失。

```
$ proot-distro login debian -- bash -c "nohup ./meilisearch ... &"
$ # 会话退出后
$ pgrep meilisearch
（无输出）
```

**根因**：`proot-distro login` 用 `--kill-on-exit` 启动，会话结束时清理整棵子进程树。`nohup` 只挡 SIGHUP，`setsid` 只脱离控制终端，都改变不了「它是该会话的后代」这个事实。

**唯一可靠做法**：把整个 proot 容器做成一个 runit 服务（`kb-container`），由 runsv 守着它。它挂了 runsv 会自动重启，且不依赖任何交互会话。

容器内仍然用 supervisord，但配置必须 `nodaemon=true`（daemonize 会让它自己脱离，同样被杀）：

```ini
[supervisord]
nodaemon=true
```

**实测验证（重启后）**：

```
run: postgres:     (pid 11534) 125s
run: sshd:         (pid 11535) 125s
run: kb-container: (pid 11538) 125s
pg_isready: accepting connections
meilisearch /health: {"status":"available"}
```

### 2.4.2 开机自启链路（部分验证，仍有缺口）

**已证实的一条链路**（从「Termux 被启动」到「服务就绪」）：

```
com.termux 主进程
  → bash -l 登录 shell
  → $PREFIX/etc/profile.d/start-services.sh   ← termux-services 安装时写入
  → runsvdir → postgres / sshd / kb-container
```

**实测数据**（用户手动打开 Termux 后 296 秒采样）：

```
11463  1574  296s  com.termux
11510  11463 296s  bash -l
11526  1     296s  runsvdir
11534  ...   296s  postgres -D $HOME/pgdata
11535  ...   296s  sshd
11538  ...   296s  proot (kb-container)
```

六个进程的 `etimes` 几乎相同，说明它们是在同一次会话里被串起来的。**这条链路成立。**

⚠️ **但「设备重启后自动走到这条链路」这一步尚未证实。** 本次观测到 `com.termux` 只有 296 秒寿命，说明它是被**用户手动打开**的，不是开机自启。见 §10.1 的「G0'-7 复查方法」。

**前置条件（缺一不可）**：

| # | 前提 | 怎么设 | 不设的后果 |
|---|---|---|---|
| 1 | **Termux 允许自启** | 设置 → 应用 → Termux → 自启动 → 允许 | 重启后 Termux 不启动，全部服务不起 |
| 2 | **Tailscale 允许自启** | 同上，对 Tailscale 操作 | 重启后 Tailscale 离线，虽然服务在跑但**外部连不进来** |
| 3 | 电池优化白名单 | 设置 → 应用 → Termux → 电池 → 无限制 | 后台被节流 |
| 4 | 不划掉 Termux | 最近任务列表里保留 | 前台服务终止，全部子进程退出 |

⚠️ **第 2 条是实际踩到的**：用户平板上 Tailscale 与 Termux 原本都是「禁止自启」，重启后 Tailscale 离线 7 分钟不恢复，表现为「设备 ping 不通」，很容易误判成服务挂了。**排查时必须先看 Tailscale 是否在线，再看服务。**

**Termux:Boot 的疑点（未查清）**：本次采样到 `com.termux.boot` 进程（295s），但它启动后 `$HOME/kb-boot.log` 没有新增记录。两种可能：① `BOOT_COMPLETED` 广播在 Android 17 上没送达，进程是别的原因起来的；② 脚本执行了但输出没写进日志。**未定位，列为待查项。**

**`~/.termux/boot/00-kb-start.sh` 的职责**（即使 Termux:Boot 不生效也值得保留）：

| 它做的事 | `profile.d/start-services.sh` 做不做 |
|---|---|
| 拿 `termux-wake-lock` | ❌ 不做 |
| 清 PG 残留 `postmaster.pid` | ❌ 不做（断电后 PG 会因此拒绝启动） |
| 启 `runsvdir` | ✅ 做 |
| 等 PG 就绪并自检 | ❌ 不做 |

实测手动执行该脚本，输出 `[STEP] postgres 就绪，耗时 2s`，且**幂等**（服务已在时不重复启动）。所以它可作为「断电恢复后的补偿脚本」使用。

### 2.4.1 保活：五项机制缺一不可（G0'-7 实测修正为五项）

查证 Termux 社区实践 + 本次真重启实测后确认：**「开机自启」不是一件事，是五件事**。缺任一项都会在某类场景下失效。

| # | 机制 | 解决什么 | 怎么开 | 实测状态 |
|---|---|---|---|---|
| 1 | **`termux-wake-lock`** | 息屏后 CPU 深休眠，进程被冻结 | 执行一次，通知栏出现 wakelock 提示 | ✅ boot 脚本已调用，实测输出 `wakelock OK` |
| 2 | 前台服务通知 | 内存紧张时 Termux 整个进程被回收 | 保持 Termux 通知存在；**不要从最近任务划掉 Termux** | ⚠️ 行为已知，未专项验证 |
| 3 | 电池优化白名单 | 系统对后台应用的额外节流 | 设置 → 应用 → Termux / Tailscale → 电池 → 无限制 | ⚠️ 需用户确认当前设置 |
| 4 | **Termux 允许自启** | 重启后 Termux 不启动，服务全不起 | 设置 → 应用 → Termux → 自启动 → 允许 | ✅ 用户已设为允许（原为禁止），但**自启是否真的生效未验证**（见 §10.1 G0'-7） |
| 5 | **Tailscale 允许自启** | 重启后 Tailscale 离线，**服务在跑但外部连不进来** | 同上，对 Tailscale 操作 | ✅ 用户已设为允许（原为禁止），**同样未验证重启后是否自动上线** |

**第 4、5 项是本次实际踩到的坑，也是原设计完全没写的。**

用户平板原本 Termux 与 Tailscale 都是「禁止自启」。真重启后的现象是：

```
$ tailscale status | grep y900-13
100.124.156.47  y900-13  android  active; relay "gz"; offline, last seen 7m ago, tx 2028 rx 0
$ tailscale ping 100.124.156.47
ping timed out
```

表现为「设备 ping 不通」，**极易误判成服务挂了**。实际是 Tailscale 没起来，服务可能好好的。

**排查顺序必须固定**：

1. 先 `tailscale status` 看设备**是否在线**
2. 在线再看 8022 端口**是否监听**（`ConnectionRefused` = Termux 起来了但 sshd 没起；超时 = Termux 没起）
3. 端口通再看 `sv status` 三个服务
4. 最后看 PG 与 Meilisearch 的 health

**对本项目（C5：平板持续在线）的影响**：第 1、3、4、5 项全是硬需求。

⚠️ **Android 12+ 的额外风险**：查证到 Android 12 之后对 `proot` 的信号管理更严（`signal 9` 更常见）。本机是 **Android 17**，比查证样本更新。本次只验证了「重启后冷启动」，「息屏 2 小时后是否仍在服务」未验证。

⚠️ **仍未验证**：`termux-wake-lock` 对续航的实际影响；长时间息屏（2 小时以上）后进程是否被回收；厂商 ROM 是否还有额外的杀后台策略。

### 2.4.3 G0'-7 两次验证均失败（结论与证据）

**结论：联想 Y900 13（TB522FU / Android 17）上，用户在系统设置里把 Termux 与 Tailscale 都设为「允许自启」后，重启设备两个 App 都不会自动启动。**

#### 第一次验证：误判为通过

判据用了 `boot_id` 变更 + 服务 `run` + pid 换新，三条全绿就下了结论。

**漏掉的是唯一有效的判据**——`com.termux` 自己的 `etimes`：

```
11463  1574  296s  com.termux
```

整机已开机约 15 分钟，`com.termux` 只有 296 秒。**服务是被「用户手动打开 Termux → bash -l → profile.d → runsvdir」连带拉起的，不是自启。**

#### 第二次验证：判据补齐，明确失败

重启前基线：

```
MARK_BOOT_ID=c5ecf1c8-e92d-47bb-a44e-472b4bdea076
kb-boot.log 行数 = 23
com.termux etimes = 528s
```

重启后监控（每 15 秒）：

```
[  0s] ACTIVE
[ 45s] IDLE      ← 设备开始重启
[105s] OFFLINE
[210s] OFFLINE   last seen: 1m ago
[315s] OFFLINE   last seen: 3m ago   ← 5 分钟后仍离线
```

用户确认：**「应用自启也没成功」**。

**失败定位**：系统层，不是脚本层。`runit` 架构本身已验证可用（手动跑 boot 脚本，三个服务全绿），失败的是「开机时谁来拉起 Termux」。

#### 两个方法论教训

| # | 错误 | 正确做法 |
|---|---|---|
| 1 | 判据不全就下「通过」：只看 `boot_id` 与服务状态，没看**被自启对象自己**的寿命 | 判断「X 是自启的」必须验 X 自己的 `etimes`，不能只看 X 生出来的子进程 |
| 2 | 监控间隔设成 15s × 20（5 分钟），而设备重启只要 20 秒 | 20–60 秒内应出结论；超过 2 分钟无响应即可判失败 |

### 2.4.4 应用自启失败的五条可选方向（待用户决策）

| # | 方案 | 代价 | 判断 |
|---|---|---|---|
| 1 | 逐项确认厂商 ROM 的三个独立开关：「自启动」「关联启动」「后台运行」（联想 ZUI 分得比原生 Android 细） | 低，纯用户操作 | 不确定，但成本最低，应先试 |
| 2 | 用 Tasker / MacroDroid 在 `BOOT_COMPLETED` 时拉起 Termux | 中，多装一个 App | 成功率较高，但引入新组件，与 C3 有张力 |
| 3 | root 方案（Magisk + 开机脚本） | 高，需解锁刷机 | 成功率最高，但**严重违反 C3** |
| 4 | **接受「开机后手动点一下 Termux」** | 极低 | 100%（不依赖自启） |
| 5 | 查社区是否有 ZUI / Android 17 已验证的自启配方 | 低 | 需调研，结果不确定 |

**方案 4 的合理性**：C5 的原文是「平板持续在线」，真实诉求是「**平时不用管它**」，不是「每次重启都零操作」。平板一旦起来可连续运行数周，重启属低频事件。若重启后只需点一次 Termux 图标，实际体验成本极低，且**完全不引入新组件**，比方案 2/3 更贴合 C3（非技术背景、出问题能靠 AI 修）。

⚠️ 这条需要用户拍板，技术方不代决。

#### 2.5.1 zRAM（内存扩展）的影响

设备开启了「+6G 内存扩展」。查证其机制后，对本项目的影响分三层：

| 层 | 机制 | 对本项目 |
|---|---|---|
| zRAM | 把不活跃页压缩后**仍留在物理内存**，压缩率 2:1–3:1，不碰闪存 | **正向**。我们的 4–5 个进程长期驻留、极少切换，正是 zRAM 最擅长保住的场景 |
| 闪存 swap | 物理内存连压缩后都装不下时，写到 UFS | **中性偏负**。若频繁触发，说明物理内存已不足，此时应先减服务而不是依赖 swap |
| 对数据库 | 压缩/解压引入延迟抖动 | **负向**。Postgres 需要稳定低延迟 |

**三条据此定下的施工约束**：

1. **`shared_buffers` 保持 128MB**，不因有 zRAM 而调大（§7.3）。zRAM 不是真内存，速度与 LPDDR 差数量级
2. **G0'-6 必须测两次**（zRAM 关 / 开），两组数据才会说明 zRAM 的实际贡献
3. **内存扩展建议开 2–3G，不必开满 6G**。每多开一档就多占存储写入；有实测数据：长期开 2GB 以上，闪存写入量增 15%–30%

**G0'-8 已消除的疑虑**：`import cv2` 的常驻内存原被标为「待测，若超 150MB 预算要重算」。实测 `VmRSS = 78.7 MB`（含 parsehub + numpy），**无需重算**。详见 §2.5。

### 4.9 退路：自写 CDP + `_ROUTER_DATA`

**只在 G2c 失败时启用。** 核心原则：**数据从 `window._ROUTER_DATA` 取，不从 DOM 取**——DOM 会掺入评论区与推荐。

```python
ROUTER_JS = r"""
(() => {
  const findAweme = (o, depth) => {
    if (depth > 8 || !o || typeof o !== 'object') return null;
    if (o.awemeId || o.aweme_id || o.desc !== undefined) return o;
    for (const k of Object.keys(o)) {
      const r = findAweme(o[k], depth + 1);
      if (r) return r;
    }
    return null;
  };
  const a = findAweme(window._ROUTER_DATA, 0);
  if (!a) return null;
  return {
    desc: a.desc ?? null,
    author: (a.author || {}).nickname ?? null,
    createTime: a.createTime ?? null,
    duration_ms: (a.video || {}).duration ?? 0,
    images: (a.images || []).map(i => ({
      url: (i.url_list || [])[0] ?? null, w: i.width, h: i.height,
    })).filter(i => i.url),
    video_url: ((a.video || {}).play_addr || {}).url_list?.[0] ?? null,
    hashtags: (a.textExtra || []).map(t => t.hashtagName).filter(Boolean),
    stats: {
      digg: (a.statistics || {}).digg_count ?? 0,
      comment: (a.statistics || {}).comment_count ?? 0,
    },
  };
})()
"""
```

**三条硬约束**：

| 约束 | 原因 | 违反后果 |
|---|---|---|
| 从 `_ROUTER_DATA` 取，不从 DOM 取 | DOM 含评论区与推荐 | 抓到别人的内容 |
| 必须移动 UA | 桌面 UA 返回的 body 仅 366 字符，无 `<video>` | 抓空 |
| 等待 8–13 秒 | 实测页面数据就绪时间 | 取到 `null` |

**这条路需要 Chromium（约 400MB 内存）**，只在主选失效时按需启动、抓完即退，不是常驻。

### 4.10 第三层降级（两层都失败时）

按 PRD M2-09，**记录不能丢**：

1. 卡片仍然入库，`kind='link'`
2. 保留 `url` + `source_domain` + 分享文案原文（`raw_text`）
3. `jobs.error` 记录失败原因，界面上「处理失败，可重试」可见
4. 用户可在详情页手动补标题

这一层成本近乎为零，且是「用户确实见过它」这条产品底线的落点。

def decide_kind(meta: ExtractResult) -> str:

## 6. 数据模型

### 6.1 为什么不是「6 类固定枚举」

三种建模范式的实证对比：

| 范式 | 代表 | 结构 | 加新形态的代价 | 检索能力 | 适用条件 |
|---|---|---|---|---|---|
| **继承式** | karakeep（30862★） | `bookmarks`（type 3 值）+ `bookmarkLinks`/`bookmarkTexts`/`bookmarkAssets` 各一张一对一子表 | 加一张子表，主表不动 | 子表字段有类型约束，按字段查快 | 形态**有限且稳定** |
| **EAV** | Trilium（39097★） | `notes(type TEXT 无 CHECK)` + `attributes(noteId, name, value TEXT)` | 插一行数据，零 DDL | 值全 TEXT，比较退化为字典序；多属性过滤需自连接 | 「终端用户运行时定义字段」 |
| **JSONB + 强约束** | PostgreSQL 官方推荐 | 核心字段做列，长尾进 `jsonb`，配 CHECK + 生成列 + GIN | 改 CHECK 表达式，**不改表结构** | 生成列可索引；GIN 支持包含查询 | 形态**无边界**且需类型校验 |

**本项目的三个判据**：

1. **形态无边界（C8）⇒ 排除继承式**。每加一种形态加一张表，表的数量随形态线性增长。
2. **字段由开发者定义 ⇒ 排除 EAV**。EAV 的唯一优势是「用户运行时加字段」，本项目没有这个需求，却要付「值退化为 TEXT + 自连接」的全部代价。而核心动作是模糊搜索，EAV 的 TEXT 比较正好伤在这里。
3. **必须能查 ⇒ JSONB 要补全四机制**。只做到「能存」不够。

**外部实证**：EAV 的代价是「一属性一行」（行数约 3 倍、存储约 3.5 倍），且 `value` 存 TEXT 导致 `'8' >= '16'` 为真（字典序）。Benchling 曾用 EAV，2021 年因摄取性能下降迁到 JSONB，理由是「稀疏行 + 元数据开销 + 读取需跨多行」。JSONB 的代价是「默认无 per-key 统计、整文档更新」，缓解手段正是表达式索引、GIN、生成列、CHECK。

### 6.2 核心表 DDL

```sql
-- 类型注册表：加新形态 = 插一行，不改任何表结构
CREATE TABLE IF NOT EXISTS item_kinds (
  kind         text PRIMARY KEY,
  display_name text NOT NULL,
  is_preset    boolean NOT NULL DEFAULT false,
  sort_order   int NOT NULL DEFAULT 0,
  created_at   timestamptz NOT NULL DEFAULT now(),
  -- 格式约束代替枚举：允许扩展，但不允许脏值
  CONSTRAINT item_kinds_format CHECK (kind ~ '^[a-z][a-z0-9_]{0,31}$')
);

-- 内容主体
CREATE TABLE IF NOT EXISTS items (
  id            bigserial PRIMARY KEY,
  kind          text NOT NULL REFERENCES item_kinds(kind) ON UPDATE CASCADE,
  url           text,                          -- 可空：纯文字/上传文件无 URL
  url_norm      text,                          -- 去重键，见 §6.6
  title         text NOT NULL DEFAULT '',
  author        text,
  source_domain text NOT NULL DEFAULT '',
  summary       text,                          -- AI 摘要 ≤100 字
  content_text  text,                          -- 正文/字幕全文
  ocr_text      text,                          -- 图片 OCR 文字（独立列，见 §6.7）
  primary_media bigint,                        -- 主视觉，指向 attachments.id
  props         jsonb NOT NULL DEFAULT '{}',   -- 长尾属性
  saved_at      timestamptz NOT NULL DEFAULT now(),
  published_at  timestamptz,
  status        text NOT NULL DEFAULT 'unread'
                  CHECK (status IN ('unread','reading','read','archived')),
  rating        smallint CHECK (rating BETWEEN 1 AND 5),
  deleted_at    timestamptz,
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now(),
  -- props 必须是对象，不是数组/标量
  CONSTRAINT items_props_object CHECK (jsonb_typeof(props) = 'object')
);

-- 生成列：把「经常按它筛」的长尾属性提升为可索引
-- 用 NULLIF 防空串转型报错：(('')::int) 会抛 invalid input syntax
ALTER TABLE items
  ADD COLUMN IF NOT EXISTS duration_sec int
  GENERATED ALWAYS AS (
    NULLIF(props->>'duration_sec', '')::int
  ) STORED;

-- 附件：任何形态内容都可挂任意多个
CREATE TABLE IF NOT EXISTS attachments (
  id          bigserial PRIMARY KEY,
  item_id     bigint NOT NULL REFERENCES items(id) ON DELETE CASCADE,
  role        text NOT NULL,          -- cover|video|image|doc|snapshot|audio
  storage_key text NOT NULL,
  mime        text NOT NULL,          -- 入库时校验，读取时按它放行
  size_bytes  bigint NOT NULL DEFAULT 0,
  width       int,
  height      int,
  duration_sec int,
  sha256      text NOT NULL,          -- 备份恢复时逐个比对
  sort_order  int NOT NULL DEFAULT 0,
  created_at  timestamptz NOT NULL DEFAULT now(),
  -- 只允许这些 MIME 前缀。加新格式改这一行，不用改读取端点
  CONSTRAINT attachments_mime_allowed CHECK (
    mime ~ '^(image/|video/|audio/|text/'
         || '|application/(pdf|zip|msword|vnd\.|octet-stream))'
  ),
  CONSTRAINT attachments_role_allowed CHECK (
    role IN ('cover','video','image','doc','snapshot','audio')
  )
);

CREATE INDEX IF NOT EXISTS attachments_item ON attachments (item_id, sort_order);
CREATE UNIQUE INDEX IF NOT EXISTS attachments_key_uniq ON attachments (storage_key);

-- 索引三件套
CREATE UNIQUE INDEX IF NOT EXISTS items_url_norm_uniq
  ON items (url_norm) WHERE url_norm IS NOT NULL AND deleted_at IS NULL;
CREATE INDEX IF NOT EXISTS items_props_gin ON items USING gin (props jsonb_path_ops);
CREATE INDEX IF NOT EXISTS items_kind_saved ON items (kind, saved_at DESC);
CREATE INDEX IF NOT EXISTS items_duration ON items (duration_sec) WHERE duration_sec IS NOT NULL;
```

**外键方向（关键）**：官方文档明确「A foreign key must reference columns that either are a primary key or form a unique constraint」（查证）。所以是 **`items.kind REFERENCES item_kinds.kind`**，不是反过来。加新类型的顺序天然正确：先插 `item_kinds`，再插 `items`。

**`jsonb_path_ops` 的选择（查证）**：

| opclass | 支持的算子 |
|---|---|
| 默认 `jsonb_ops` | `?` `?|` `?&` `@>` `@?` `@@` |
| `jsonb_path_ops` | **仅** `@>` `@?` `@@` |

本项目 `props` 的查询只用到 `@>`（按 duration 筛选走生成列，不靠 props 算子），所以选更小更快的 `jsonb_path_ops`。**若将来需要 `?`（键存在判断），必须换成默认 opclass。**

### 6.4 流水线状态机

| 步骤 | 谁创建 | 做什么 | 成功后插入的下一步 |
|---|---|---|---|
| `fetch` | `POST /api/items` | 抓取元数据 + 下载媒体 | `summarize`；若 `kind='image'` 或图文，**同时**插 `ocr` |
| `ocr` | `fetch` 完成时（图片类） | 视觉模型出「图中文字 + 一句话描述」→ `items.ocr_text` | `index` |
| `summarize` | `fetch` 完成时 | 文本模型出摘要 → `items.summary`（**同一调用出标签**） | `tag` |
| `tag` | `summarize` 完成时 | 校验词表后写 `item_tags` | `index` |
| `index` | `summarize` 或 `ocr` 完成时 | 写 Meilisearch 索引 | 无（终态） |

**`index` 步的必要性（修 N1）**：没有这一步，入库后无人建索引，只能靠每日对账或手动全量重建，最长 24h 搜不到新内容。

**「取最后一个完成的」实现**：`index` job 用 `ON CONFLICT DO NOTHING` 插入；worker 取到 `index` 任务时先查该 item 是否还有未完成的 `summarize`/`ocr`/`tag`，若有则把自己 `run_after` 推后 30 秒重试（不计 attempts）。这样保证索引写入时字段已齐。

**取任务 SQL**（必须 `FOR UPDATE SKIP LOCKED`，否则两个 worker 抢同一条）：

```sql
WITH picked AS (
  SELECT id FROM jobs
   WHERE state = 'pending' AND run_after <= now()
   ORDER BY run_after
   LIMIT 1
   FOR UPDATE SKIP LOCKED
)
UPDATE jobs SET state = 'running', updated_at = now()
  FROM picked WHERE jobs.id = picked.id
  RETURNING jobs.*;
```

**失败与退避**：

```sql
UPDATE jobs
   SET attempts = attempts + 1,
       state = CASE WHEN attempts + 1 >= 3 THEN 'failed' ELSE 'pending' END,
       run_after = now() + (interval '1 minute' * power(2, attempts)),
       error = $2
 WHERE id = $1;
```

**崩溃恢复**（worker 被杀导致 `running` 卡住）：

```sql
UPDATE jobs
   SET state = 'pending'
 WHERE state = 'running' AND updated_at < now() - interval '15 minutes';
```

### 6.5 备份

**备份对象必须是 `pg_dump` 产物，不是运行中的数据目录**（修 N2）。

```bash
# 1. 逻辑备份（拿到事务一致的快照）
pg_dump -Fc -f "/data/dump/kb-$(date +%F).dump" kb

# 2. 备份 dump + 媒体（不含 pg/ 目录）
restic -r "$RESTIC_REPO" backup /data/dump /data/media

# 3. 清理 7 天前的 dump（restic 已有增量，这里只清工作目录）
find /data/dump -name 'kb-*.dump' -mtime +7 -delete
```

**为什么不能直备 `pg/`**：运行中的数据目录处于不断写入状态，直接拷贝得到的是**页级撕裂副本**（各文件来自不同时间点），`initdb` 恢复时会因 WAL 不一致拒绝启动。而空闲期备份 + 立刻恢复能「成功」，让判据给出假绿灯（N16）。

**异地副本（必须，修 v7 审计 #7）**：

| 副本 | 位置 | 频率 |
|---|---|---|
| 主副本 | 平板本地 `/data/backups` | 每日 22:30 |
| **异地副本** | Windows 电脑通过 Tailscale 拉取（`restic -r sftp:...` 或计划任务） | 每周一次 |

同盘的备份不解决「平板损坏/丢失」这个场景。

### 6.6 URL 去重

两级去重键：

| 键 | 内容 | 解决什么 |
|---|---|---|
| `url_norm` | 归一化后的 URL（照搬 linkding 算法） | 同一 URL 写法不同（大小写、尾斜杠、query 顺序） |
| `props.canonical_id` | 抓完后回填的平台规范 ID（如 `douyin:aweme:7xxxx`） | **短链 vs 长链**（`v.douyin.com/xxx` 与 `www.douyin.com/video/<id>`） |

归一化算法（linkding 的 `normalize_url`，可直接照搬）：

```
1. 去首尾空白，空则返回 ""
2. urlparse 拆解
3. scheme 转小写
4. hostname 转小写；有 port 则拼上；有 user:pass 则拼成 user:pass@host
5. path 去掉所有尾部斜杠
6. query 用 parse_qsl(keep_blank_values=True) 拆开，按 (key, value) 排序后重新 urlencode
7. fragment 原样保留
8. 重新拼接
```

写入用 `ON CONFLICT DO NOTHING`：

```sql
INSERT INTO items (kind, url, url_norm, title, source_domain)
VALUES ($1, $2, $3, $4, $5)
ON CONFLICT (url_norm) WHERE url_norm IS NOT NULL AND deleted_at IS NULL
DO NOTHING
RETURNING id;
-- 返回 0 行表示重复，用 url_norm 查回已有 id
```

### 6.7 检索字段

PRD M6-01 要求搜「标题 / 正文 / 摘要 / 标签 / 图片 OCR 文字」五路。Meilisearch 索引字段：

| 字段 | 来源 | 权重 |
|---|---|---|
| `title` | `items.title` | 最高 |
| `summary` | `items.summary` | 高 |
| `content_text` | 正文/字幕 | 中 |
| `ocr_text` | **图片 OCR（独立字段，修 N17）** | 中 |
| `tags` | `item_tags` 聚合出的标签名数组 | 高 |
| `author` | `items.author` | 低 |

**为什么 `ocr_text` 要独立列**：v8.0 把 OCR 文字塞进 `content_text`，导致索引字段表里「OCR」被「作者」顶掉（N17）。独立列后两条路径互不干扰，且能单独统计 OCR 覆盖率。

### 6.8 表清单

**12 张表**：`item_kinds`、`items`、`attachments`、`tags`、`item_tags`、`queries`、`domain_type_rules`、`settings`、`users`、`sessions`、`jobs`、`schema_migrations`。

> 相对 v8.0 的 10 张：删 `files`（被 `attachments` 取代），增 `item_kinds`、`schema_migrations`。

**迁移原则**：

1. 所有 DDL 用 `IF NOT EXISTS`，可重复执行（修 N7）
2. 每个版本一个编号，跑完写 `schema_migrations`
3. 启动时检查版本，落后则按序执行
4. **T16 判据**：连续跑两次迁移无报错、`schema_migrations` 行数不变

### 6.9 `updated_at` 维护

加通用触发器，避免「忘了写 `updated_at`」：

```sql
CREATE OR REPLACE FUNCTION touch_updated_at() RETURNS trigger AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS items_touch ON items;
CREATE TRIGGER items_touch BEFORE UPDATE ON items
  FOR EACH ROW EXECUTE FUNCTION touch_updated_at();

DROP TRIGGER IF EXISTS jobs_touch ON jobs;
CREATE TRIGGER jobs_touch BEFORE UPDATE ON jobs
  FOR EACH ROW EXECUTE FUNCTION touch_updated_at();

DROP TRIGGER IF EXISTS settings_touch ON settings;
CREATE TRIGGER settings_touch BEFORE UPDATE ON settings
  FOR EACH ROW EXECUTE FUNCTION touch_updated_at();
```

**为什么必须有**：`jobs` 的 15 分钟卡死判定依赖 `updated_at`。若无触发器且应用层忘了更新，正常的长任务会被误杀。

## 7. 技术栈

### 7.1 部署环境

| 层 | 选择 | 理由 | 档位 |
|---|---|---|---|
| 宿主 | Termux（Android 14） | 无需 root | 查证 |
| 容器层 | proot Debian 13（trixie） | glibc 轮子可用；Docker 在 Android 不可用 | 查证 |
| Python | **3.13**（Debian 13 的 `python3`） | `3.13.5-2+deb13u5`，有 arm64。parsehub 要 `>=3.12.0` | 查证 + 实测 |
| Postgres | **17**（Debian 13 源） | `17+278+deb13u1` | 查证 |

**Python 版本的关键事实**（修 N24/N26）：

- `python3.12` 在 Debian 13 **不存在**。`tracker.debian.org/pkg/python3.12` 原文：「**package is gone**」「This package is **not part of any Debian distribution**」
- 时间线：2025-03-14 移出 testing，2025-07-30 移出 unstable
- 对照：`trixie/python3.13` = `3.13.5-2+deb13u5`，arm64 可下载
- **本机实测**：Python 3.13.14 上 `parsehub` 导入成功，`Platform` 25 个，`cv2` 5.1.0 + `numpy` 2.5.5 均可用

**因此删除 v8.0 的 pyenv 编译退路**——它是为一个不存在的包准备的，且 ARM 全量编译 40–120 分钟，缺 `libssl-dev` 会静默编译出无 `_ssl` 的残废 Python。

### 7.2 后端

| 项 | 选择 | 备选 | 取舍理由 |
|---|---|---|---|
| Web 框架 | **Starlette** | FastAPI | 少一层依赖注入与自动文档；本项目 28 个端点不需要自动 OpenAPI |
| DB 驱动 | **pg8000** | psycopg3 | 纯 Python，无 binary 轮子依赖。**注：psycopg-binary 有 aarch64 轮子，所以这是主动取舍不是被迫** |
| 密码哈希 | **bcrypt** | argon2-cffi | 同上，argon2-cffi-bindings 有 aarch64 轮子；bcrypt 依赖更少 |
| 校验 | Pydantic v2 | — | 每个 kind 一个模型，props 的结构校验在这里 |
| 迁移 | 自写 `store/migrate.py` | alembic | 12 张表 + 单机，自写编号迁移足够；引 alembic 多一层 |

**D6 的更正**：v8.0 把「选保守组合」的理由写成「那三个包没有 aarch64 轮子」，这是错的。它们都有。真实理由是「减少 G0' 可能失败的面」——少两个 ABI 依赖，少两个可能装不上的东西。G0' 通过后可以换回 psycopg/argon2。

### 7.3 Postgres 配置

**Postgres 装在 Termux 原生层，不在 proot 内**（理由见 §2.2.1）。因此不需要 `shared_memory_type=mmap` 这类绕开 System V 共享内存的补丁——Termux 的 PG 构建自带 `libandroid-shmem`，已在 Android 上适配。

`$HOME/pgdata/postgresql.conf` 的有效配置（G0'-4 实测生效）：

```ini
listen_addresses = '*'        # proot 内的 127.0.0.1 是同一命名空间，必须监听 TCP
port = 5432
shared_buffers = 128MB        # 7.2GB 物理内存上的保守值（实测实际占用仅 63MB）
max_connections = 20          # 单用户不需要默认 100
```

`pg_data/pg_hba.conf` 追加：

```
host all all 0.0.0.0/0 trust
```

⚠️ `trust` 是因为只监听 Tailscale 内网、无公网暴露。若将来开放端口必须改成 `scram-sha-256`。

**启动与验证命令**（实测通过）：

```bash
initdb -D $HOME/pgdata -E UTF8 --locale=C.UTF-8
pg_ctl -D $HOME/pgdata -l $HOME/pg.log start
pg_isready -h 127.0.0.1 -p 5432
# → 127.0.0.1:5432 - accepting connections
```

**已实测的版本**：

```
PostgreSQL 18.7 on aarch64-unknown-linux-android
compiled by Android (16134705, +pgo, +bolt, +lto, +mlgo, based on r574158c) clang version 21.0.0
```

**为什么不是 17**：Termux 官方仓库只提供 18.7。Debian 13 的 17.12 能装进 proot，但 `initdb` 在 proot 下卡死（§2.2.1）。两者相权取「能跑」的 18.7。DDL 已在 18.7 上逐条实跑验证（§6.2）。

### 8.2 关键端点契约

**`POST /api/items`**：

```json
// 请求（url 与 text 至少给一个）
{ "url": "https://v.douyin.com/xxx/", "raw_text": "可选，分享文案原文" }
{ "text": "一段不想丢的话" }
```

```json
// 响应 202
{ "id": 123, "kind": "link", "status": "pending" }
// 重复时返回 200 + 已有 id
{ "id": 88, "kind": "video", "duplicate": true }
```

**`GET /api/media/{key}`**（修 D6）：

```
1. 校验 key 形如 <2位hex>/<32位hex>.<ext>（防路径穿越）
2. 查 attachments WHERE storage_key = key → 取 mime
3. 若查不到 → 404（不是 400）
4. 按 mime 设置 Content-Type
5. 视频/大文件用 StreamingResponse
6. Cache-Control: private, max-age=31536000, immutable
```

**不再用文件扩展名正则白名单**。白名单在 `attachments.mime_allowed` 的 CHECK 里，入库时已校验。

**`GET /api/health`**（修 N5，五项口径）：

```json
{
  "ok": true,
  "dbOk": true,
  "meiliOk": true,
  "workerOk": true,
  "diskFreeGb": 42.1,
  "workerHeartbeatAt": "2026-11-26T18:30:00+08:00"
}
```

`workerOk = now - workerHeartbeatAt < 90s`。**心跳写入方：worker 每 30s 写 `settings('worker_heartbeat')`**。没有写入方的话这个字段永远 `null`，健康检查永远通过。

### 8.3 搜索

**三级降级**：

| 层 | 条件 | 实现 | 中文可用性（实测） |
|---|---|---|---|
| 1 | Meilisearch 可用 | 五字段检索 + 内置中文分词 | ✅ 设计目标 |
| 2 | Meili 挂了 | Postgres `ILIKE '%q%'` 兜底（慢但能返回结果） | ⚠️ 能返回结果，但无相关性排序、走 Seq Scan |
| 3 | 两者都挂 | 列表接口不带 q，前端提示「搜索暂不可用」 | — |

索引字段与权重见 §6.7。

#### 8.3.1 PG 原生中文检索的实测结论（决定了 Meilisearch 不可替代）

2026-11-26 在真机 PG 18.7 上跑了三种 PG 原生方案，**全部不适用于中文**：

| 方案 | 实测结果 | 原因 |
|---|---|---|
| `pg_trgm` 的 `%` 相似匹配 | ❌ 0 行 | `similarity('看完这篇你就懂了三体问题', '三体') = **0.000**`。中文无空格，三字母片段无法命中短查询 |
| 降阈值到 0.05 后重测 | ❌ 仍 0 行 | 分数本身就是 0，与阈值无关 |
| PG 原生 `simple` 分词 | ❌ 0 行 | 中文整句被当成单个 token，`plainto_tsquery('simple','三体')` 匹配不到 |
| `ILIKE '%三体%'` | ✅ **命中 1 行** | 子串匹配有效，但 `EXPLAIN` 显示 **`Seq Scan`**，GIN 索引用不上 |

**这条结论改变了降级策略的权重**：

- 第 2 层（PG ILIKE）只能保证「有结果」，不能保证「按相关性排序」。数据量到 500 条以上时 Seq Scan 会明显变慢
- **因此 Meilisearch 不是「可选优化」，而是「中文搜索的必需件」**。它挂掉时搜索质量会实质下降，这一点必须写进用户可见的提示，不能假装无损降级
- 也正因此，§10.1 G0'-5 不过关时**不能简单降级**，要评估替代搜索引擎（见 §8.3.2）

#### 8.3.2 Meilisearch 的运行位置：必须在 proot 里（已实测确认）

**原设计写的是「Meilisearch aarch64 静态包」，这个描述本身是错的。** 2026-11-26 通过 ELF 头解析推翻：

```
e_type:     0x3  ET_DYN (PIE)
e_machine:  0xB7 aarch64
PT_INTERP:  存在
解释器:     /lib/ld-linux-aarch64.so.1     ← glibc 动态链接器
```

**它是 glibc 动态链接的二进制，不是静态包。** 因此：

| 运行位置 | 结论 | 证据 |
|---|---|---|
| Termux 原生层（bionic） | ❌ **必然失败** | Termux 官方 Wiki：「Dynamically linked programs from Linux distributions will not run」；本机实测把容器里的 glibc 二进制拷到 Termux 层执行 → `cannot execute: required file not found` |
| **proot Debian 内（glibc）** | ✅ **可行** | proot 内 `/lib/ld-linux-aarch64.so.1` 存在（软链到 `aarch64-linux-gnu/`），`/bin/echo` 正常执行 |

**所以这不是「降级方案」，而是唯一位置。** Meilisearch 与 kb-api / kb-worker 一样跑在容器里，同一个 supervisor 管。

**另一条被排除的路径**：Termux 官方 Wiki 明确写着「On non-rooted Android 8 or newer, statically linked programs will not run due to issues with seccomp」。因此即使是静态二进制也走不通——这条把「换静态版本」这条路彻底封死了。

**连带修正 §2.1 结构图**：Meilisearch 在 proot 内，与 Caddy/kb-api/kb-worker 同层。

⚠️ **仍未验证**：Meilisearch 在 proot 下能否**实际启动并响应 `/health`**。已确认的是「glibc 环境具备、解释器路径匹配」，不是「跑起来了」。这是 G0'-5 的剩余部分。

**G0'-7 的复查结论（重要：曾误判，已纠正）**

第一次判断「通过」的依据是：`boot_id` 变了、三个服务状态是 `run`、pid 是新的。**这个判断是错的**，缺了最关键的一项——**Termux App 自己的启动时刻**。

补测 `ps -eo pid,etimes,comm` 后的真实证据：

```
11463  1574  296s  com.termux          ← App 主进程
11510  11463 296s  bash -l             ← 登录 shell
11526  1     296s  runsvdir
11627  1574  295s  com.termux.boot     ← Termux:Boot 也起来了
```

整机已开机约 15 分钟，但 `com.termux` 只有 **296 秒**寿命。**结论：Termux 是用户手动打开的，服务是被连带拉起的，不是开机自启。**

⚠️ **`/proc/uptime`、`/proc/stat`（btime）、`dumpsys` 在该设备上全部不可读**（Android 权限限制）。因此**无法直接读出整机开机时长**，只能通过「进程 etimes 的最大值」间接判断——这是本次踩到的取证障碍，后续复查必须知道这一点。

| 步骤 | 命令 | 判据 |

## 附录 B：术语表（给非技术背景的验收方）

| 术语 | 一句话解释 |
|---|---|
| proot | 在安卓上模拟一个普通 Linux 环境，让 Linux 的软件能装能跑，不需要 root |
| glibc / bionic | 两套不同的「基础库」。Linux 用 glibc，安卓用 bionic；大部分现成软件只提供 glibc 版本 |
| aarch64 / arm64 | 平板和手机的 CPU 架构，与电脑的 x86 不同，所以软件要专门的版本 |
| abi3 轮子 | 一种「一次编译、多个 Python 版本通用」的软件包格式 |
| 轮子（wheel） | Python 软件的预编译打包，有轮子就不需要现场编译 |
| sdist | 只有源码、需要现场编译的包 |
| DDL | 建表、改表结构的 SQL 语句 |
| jsonb | Postgres 的一种字段类型，可以存结构不固定的数据（类似一个 JSON 对象） |
| GIN 索引 | 专为 jsonb 这类「内含多个键值」的字段设计的索引，让「查里面有没有某个值」变快 |
| 生成列 | 由其他列自动算出来的列，不用手动填，可以建索引 |
| 外键 | 数据库层的「这个值必须在另一张表里存在」的约束 |
| 触发器 | 在插入/更新前后自动执行的检查或动作 |
| SKIP LOCKED | 多个后台进程取任务时互不抢同一条的机制 |
| 幂等 | 同一个操作做多次，结果与做一次相同 |
| pg_dump | Postgres 官方的备份工具，导出一份「一致快照」 |
| restic | 增量、加密、去重的备份工具 |
| Tailscale | 一个把设备连成私有网络的工具，不用买域名、不暴露公网 |
| ts.net 证书 | Tailscale 免费签发的、被系统信任的 HTTPS 证书 |
| Meilisearch | 一个搜索引擎，「打字就出结果」 |
| Charabia | Meilisearch 内置的分词器，支持中文 |
| CDP | Chrome 调试协议，用代码控制一个真浏览器 |
| `_ROUTER_DATA` | 抖音网页里内嵌的数据对象，比抓页面元素更干净 |
| EAV | 「一行存一个属性」的建表方式，灵活但查询慢 |
| 继承式建表 | 主表 + 每种类型一张子表的结构 |
| P95 | 100 次里有 95 次比这个数快 |
| marker | pytest 的标签，用来分组跑测试 |
